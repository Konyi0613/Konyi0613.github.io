Standard I/O Library (Buffered I/O)
Unit 05

ch03 page-02 和 page-10 已經把分工講好了：open／read／write 是 unbuffered I/O，直接對 kernel 開口；fopen／fread／printf 是 buffered I/O，先在你的 process 裡暫存，累積夠了才呼叫 write。ch03 講的是底下那層，這章講上面這層：C 標準函式庫的 standard I/O library（標準 I/O 函式庫，也就是 <stdio.h> 裡那些函式）。

章號照課本 APUE 和投影片檔名（sp_ch5）編；投影片的課程目錄把這個主題排在第 4 章，上課時改看 NTU COOL 的錄影，期中考會考（ch04 開頭的說明）。

page-03#

Standard I/O Library#

  • Major revision by Dennis Ritchie in 1975：C 語言的設計者之一重新整理過的版本，之後大致沒變過。
  • An ANSI C standard：它屬於 C 語言標準（ch03 page-03），不屬於 POSIX，所以 Windows 上的 C 編譯器也有一模一樣的 printf、fopen。這就是投影片說的 portable（可攜）。
  • Easy to use：它替你處理掉這些細節：
    • buffer allocation：buffer 由 library 自己配置（page-13）。
    • optimal-sized I/O chunks：每次呼叫 read／write 搬多少，library 會挑一個有效率的大小，通常是 ch04 page-07 的 st_blksize。ch03 page-42 的實驗結論「buffer 取 block 大小最好」，用 standard I/O 就自動做到了。
    • better interface：可以一次讀一行（fgets）、印出格式化的數字（printf("%d")），不必自己處理 byte。

page-04#

跟 File I/O（Unbuffered I/O）的差別#

file I/O（ch03）standard I/O（這章）
操作對象file descriptor（一個 int）file pointer（一個 FILE *）
開檔openfopen
開檔之後得到fd table 裡的一格一個 stream

stream（串流）是 standard I/O 對「一個開著的檔案」的稱呼：fopen 開檔或建檔時，會建立一個 stream 跟這個檔案連在一起，之後所有讀寫都透過它。

代表 stream 的是一個 FILE object，fopen 回傳的 FILE * 就指向它。它在 user space（ch03 page-11），裡面記著：

欄位用途
file descriptor真正要 read／write 時用的 fd
pointer to buffer、buffer sizebuffer 在哪、多大
# of remaining charsbuffer 裡還有幾個字元沒被讀走（或已經寫進幾個）
error flag、end-of-file flag上次操作有沒有出錯、是不是讀到檔尾（page-23）

每個程式一開始就有三個開好的 stream：stdin、stdout、stderr，定義在 <stdio.h>，分別包著 fd 0、1、2，也就是 STDIN_FILENO、STDOUT_FILENO、STDERR_FILENO（投影片的 STDIO_FILENO 是筆誤，ch03 page-14）。

page-05#

Buffering#

又是 ch03 page-09 那張全圖，這次紅圈圈著最左邊的 FILE object：它裝著一個 fd 和一塊 buffer，屬於 C standard I/O lib，在 process 自己的記憶體裡。

  • A wrapper of unbuffered I/O：standard I/O 是包在 ch03 那些 system call 外面的一層，不是另一條路（ch03 page-10）。資料最後一定還是經過 read／write 進出 kernel。
  • Linux shell command: strace：strace 會把一支程式呼叫的每個 system call 都印出來，用它就能親眼看到 buffer 省掉了多少次 write。

page-06#

Unbuffered I/O#

user process 每呼叫一次 read()，就進一次 kernel（ch03 page-04）。程式要多少就讀多少：圖上紅色方塊大小不一，有時一小塊、有時一大塊、有時只有一條細線。

每次呼叫都要付 system call 的固定成本（ch00 page-16），所以程式如果一次只要幾個 byte，就會付很多次。

page-07#

Buffered I/O#

中間多了一塊 Standard I/O Buffer，跟 User Process 一起框在 User Space 裡：

  • 程式每次 gets() 只拿一小塊，直接從 buffer 裡拿，不進 kernel，就是普通的記憶體複製。
  • buffer 空了，library 才呼叫一次 read，向 kernel 要一大塊（圖上那條長長的紅色方塊），把 buffer 補滿。

程式的呼叫次數沒變，進 kernel 的次數卻少很多。寫的方向也一樣，見下一頁。

page-08#

printf 的資料去了哪裡#

六次 printf 只是把字元依序放進 buf，直到 flush 才真的送出去。flush 在 ch03 page-10 出現過：把 buffer 裡累積的資料一次用 write() 交給 kernel，再清空 buffer。flush 的時機有三種：buffer 滿了、遇到換行（stream 是 line buffered 時，page-14），或是程式主動呼叫 fflush（page-16）。程式正常結束時也會自動 flush。

page-09#

打開 pathname，回傳一個 FILE *；失敗回傳 NULL。type 是一個字串，指定要怎麼開：

每一種其實就是 ch03 page-17 的 open 旗標組合：

type等於 open 的

wO_WRONLY | O_CREAT | O_TRUNC

+ 代表「讀寫都要」。新建的檔案權限固定是 0666 & ~umask（ch04 page-26），fopen 沒辦法指定權限；需要的話就自己 open 再 fdopen（page-11）。

投影片的兩點：

  • b（rb、wb、ab、r+b……）代表 binary file，在 UNIX 上沒有作用：只有 Windows 這種會轉換換行符號的系統才分 text 和 binary（ch03 page-42 的 note）。
  • Append mode supports multiple access：a 用的是 O_APPEND，每次寫入時 kernel 都 atomic 地把 offset 移到檔尾再寫，好幾個 process 同時 append 也不會互相蓋掉（ch03 page-47～49）。

page-11#

fdopen、fileno、fclose#

fdopen：把一個 已經開好的 fd 包成 stream。有些 fd 不是用 open 拿到的，例如 pipe、網路連線的 socket（ch16 page-39），就沒辦法用 fopen 打開；用 fdopen 包起來之後，就能用 fgets、fprintf 讀寫它們。

  • 這個函式是 POSIX.1 定義的，不在 ANSI C 裡：ANSI C 根本沒有 fd 的概念。
  • type 給 "w" 也 不會清空檔案：檔案早就開好了，fdopen 只是包一層，不會重新開檔，O_TRUNC 這種開檔時才有的動作已經來不及做。

fileno：反過來，從 stream 拿出它裡面的 fd。要對 stream 做 standard I/O 沒有提供的事時用，例如 fcntl、dup、fstat，或把它交給 select（ch14 page-12）。

fclose：關掉 stream。

  • Flush buffered output：buffer 裡還沒寫出去的資料，先 write 出去。
  • Discard buffered input：buffer 裡讀進來但還沒被程式拿走的資料，直接丟掉。
  • 再 close 底下的 fd，釋放 library 配的 buffer。
  • All I/O streams are closed after the process exits：程式正常結束（return from main 或呼叫 exit）時，所有 stream 都會自動 flush 再關掉。但如果是當掉，或用 _exit（直接結束 process、跳過所有清理動作的 system call，Ch8）結束，就沒有這一步，buffer 裡的資料就不見了（ch03 page-10 的例子）。
  • The relocated buffers must be valid before the stream is closed：如果你用 setvbuf 給 stream 換上自己的 buffer（page-17），那塊記憶體在 stream 關掉之前都必須有效，例子見下一頁。

page-12#

Potential problem when using fclose#

setvbuf 把 databuf 設成這個 stream 的 buffer（細節 page-17，就是投影片的 Explain later）。問題在於 databuf 是 區域變數，放在 open_data 的 stack frame 裡（ch01 page-51；stack frame 是 Ch7 的內容）。open_data 一 return，那塊記憶體就交還出去，下一個被呼叫的函式會拿來放它自己的區域變數。

可是 fp 被 return 出去了，呼叫者還會繼續用它，standard I/O 會繼續把讀進來的資料寫進那塊記憶體，等於在亂改別的函式的變數，而且錯誤出現的地方往往離這裡很遠，很難查。

修法：buffer 改用 static 或 malloc 配置，或者乾脆傳 NULL 讓 library 自己配（page-18）。

page-13#

Buffering：目標、配置、種類#

  • Goal：use the minimum number of read and write calls，盡量少呼叫 read／write，理由就是 page-06～07。
  • Allocation：
    • 預設在 stream 第一次做 I/O 時，由 library 用 malloc 自動配置。
    • 也可以在那之前呼叫 setbuf 或 setvbuf 自己指定（page-17）。

Types：buffer 什麼時候 flush，分三種：

種類什麼時候真的 write預設用在
fully bufferedbuffer 滿了磁碟檔案、pipe、socket
line buffered遇到換行（page-14）接到終端機的 stdin、stdout
unbuffered每次都馬上（page-15）stderr

不管哪一種，呼叫 fflush 都會立刻 flush（page-16）。

page-14#

Line Buffered#

line buffered：遇到換行字元才做真正的 I/O，通常用在接到終端機的 stream。人看終端機是一行一行看的，所以湊滿一行再送出去剛好。

兩個要注意的地方：

1. buffer 的大小是固定的。 一行如果比 buffer 還長，buffer 滿了就會先送出去，不會等到換行。

2. 要向 kernel 要輸入時，所有 line-buffered 的輸出 stream 都會先 flush。 投影片的例子：

"$ " 沒有換行，照規則會一直留在 buffer 裡。可是使用者需要先看到提示符號才知道要輸入，所以 scanf 要去 kernel 讀資料之前，library 會先把 stdout flush 出去，$ 才會出現在畫面上。

「從 kernel」這幾個字是關鍵：如果 stdin 的 buffer 裡本來就有資料，scanf 不必呼叫 read，就不會觸發這個 flush。

page-15#

Unbuffered 與 ANSI C 的規定#

unbuffered：每次呼叫都直接 write，希望輸出越快出去越好。典型的例子是 stderr：錯誤訊息要是留在 buffer 裡，程式接著當掉，訊息就永遠看不到了。ch14 page-06～07 的實驗把每次 write 的結果用 fprintf(stderr, …) 記下來，靠的也是這點：每一行都會馬上出去。

ANSI C 的規定只有兩條：

  • stdin 和 stdout：只有在沒有接到互動裝置（終端機）時，才是 fully buffered。
  • stderr：絕對不是 fully buffered。

SVR4、4.3+BSD，以及現在的 Linux 都採用更具體的做法：

stream接到終端機接到檔案或 pipe
stdin、stdoutline bufferedfully buffered
stderrunbufferedunbuffered

所以 同一支程式，輸出接到哪裡，行為就不一樣：直接在終端機上跑，printf 每印一行就出現；改成 ./a.out > file 或 ./a.out | less，stdout 變成 fully buffered，要等 buffer 滿了或程式結束才寫出去。如果程式中途當掉，導到檔案的輸出就會少掉最後那一段。

page-16#

Way to Synchronize Data：fflush#

  • 把 fp 的 buffer 裡還沒寫出去的資料交給 kernel（呼叫 write）。
  • fp 是 NULL 時，flush 所有 輸出 stream。

圖上有兩段箭頭，分別由不同的函式負責：

函式從哪裡到哪裡
fflush()FILE object 的 buffer（user space）kernel 的 buffer cache
sync()、fsync()、fdatasync()buffer cacheDisk

fflush 只把資料交到 kernel，這時資料仍在記憶體裡，還沒到磁碟（ch03 page-08 的 delayed write）。要確保資料寫到磁碟，就在 fflush 之後再呼叫 fsync(fileno(fp))（ch03 page-61）。

順序不能省：只呼叫 fsync 而不先 fflush，資料可能還全部留在 C library 的 buffer 裡，kernel 根本沒看到，fsync 等於什麼都沒做。

page-17#

Build up your own buffer：setbuf、setvbuf#

必須在 stream 做任何操作之前呼叫：buffer 在第一次 I/O 時就配好了（page-13），之後才換會把裡面的資料弄亂。

setbuf 只能開或關：

  • buf 不是 NULL：用你給的這塊記憶體當 buffer，長度必須是 BUFSIZ（<stdio.h> 定義的常數；投影片寫 1024，glibc 是 8192）。至於是 fully 還是 line buffered，由系統決定，例如接到終端機的就是 line buffered。
  • buf 是 NULL：關掉 buffering，變成 unbuffered。

setvbuf 可以指定種類：mode 是 _IOFBF（fully buffered）、_IOLBF（line buffered）或 _IONBF（unbuffered）。buf 給 NULL 時由 library 自己配一塊 size 大小的 buffer；size 也可以省事地交給 library 決定，一般就是 st_blksize（ch04 page-07）。成功回傳 0。

page-19#

Positioning a Stream#

stream 版的 lseek（ch03 page-32）：

  • ftell：回傳目前的位置，從檔頭算起第幾個 byte。這是 程式看到的位置，會扣掉 buffer 裡還沒被讀走的部分，所以跟 kernel 裡的 current file offset 不一定相同。
  • fseek：移動位置，whence 跟 lseek 一樣是 SEEK_SET、SEEK_CUR、SEEK_END。成功回傳 0。
  • rewind：回到檔頭，等於 fseek(fp, 0, SEEK_SET)。

fseek 不只是改一個數字：它會先 flush 還沒寫出去的資料、丟掉已經讀進 buffer 的資料，再呼叫 lseek，這點在 page-37 很重要。

Assumption: a file’s position can be stored in a long：32-bit 系統上 long 只有 32 bit，超過 2 GB 的檔案就表示不了。所以有另外兩組：

函式位置的型別來源
ftello、fseekooff_t，可以是 64 bitPOSIX（投影片的 fello 是筆誤）
fgetpos、fsetposfpos_t，內容不公開ANSI C

fpos_t 是給非 UNIX 系統用的：有些系統的檔案位置不是一個單純的 byte 數，ANSI C 就用一個不透明的型別裝起來，只能存起來、之後原樣交回 fsetpos。

ANSI C 對 whence 的限制（在 UNIX 上都不存在）：

  • binary file：不保證支援 SEEK_END，因為有些系統會在檔尾補 padding，「檔尾」在哪不明確。
  • text file：只能用 SEEK_SET，offset 也只能是 0 或之前 ftell 回傳的值，因為換行符號的轉換（ch03 page-42 的 note）讓「第幾個字元」和「第幾個 byte」對不上。

page-20#

Reading／Writing：三種 unformatted I/O#

前面講的是 stream 怎麼開、buffer 怎麼運作、位置怎麼移；從這頁開始是真正讀寫資料的函式。

unformatted I/O 是指只搬字元，不做格式轉換（相對於 page-35 的 printf、scanf）。依一次搬多少分三種：

種類一次搬例子投影片的說明
character-at-a-time I/O一個字元getc、putcbuffering 由 standard I/O library 處理，一次一個字元也不會每次都進 kernel
line-at-a-time I/O一行fgets、fputs要指定 buffer 能裝多長的一行
direct I/O指定大小的物件若干個fread、fwrite也叫 binary I/O、object-at-a-time I/O、record-oriented I/O 或 structure-oriented I/O

這裡的 direct I/O 是 ANSI C 的用語，跟 Linux 上 open 的 O_DIRECT（繞過 buffer cache）無關。

page-21#

Character-at-a-Time I/O：輸入#

三個都是讀一個字元。getchar() 就是 getc(stdin)。

getc 和 fgetc 的差別：getc 可以是 macro（巨集），fgetc 一定是函式。 macro 在編譯時直接展開成程式碼，省掉函式呼叫，但有三個後果：

  • 參數可能被算不只一次：macro 展開時參數可能出現好幾次，所以參數不能有 side effect（副作用，例如會改變變數）。投影片的例子應該是 getc(*f++)（寫成 f*++ 是筆誤）：f++ 若被算兩次，指標就多跳了一格。
  • 執行時間：macro 省掉了函式呼叫，可能比較快。
  • 不能取 address：要把它當成函式指標傳給別的函式時，只能用 fgetc。

回傳型別是 int，不是 char：讀到的字元先轉成 unsigned char（0～255），再轉成 int 回傳，這樣 256 種 byte 都是非負數，就不會跟代表錯誤的 -1 撞在一起（page-22）。

讀到檔尾和出錯都回傳 -1（EOF）。那要怎麼知道是哪一種？用 page-23 的 feof、ferror 查。

page-22#

為什麼不能用 char 接 getchar 的回傳值#

這支程式在某些機器上正常，在其他機器上卻有問題。原因是 C 標準沒有規定 char 是 signed 還是 unsigned，由各平台決定（x86 上的 Linux 是 signed，ARM 上的 Linux 是 unsigned）：

char 是會發生什麼
unsignedgetchar 回傳 -1 時，存進 c 變成 255；拿 255 跟 -1 比永遠不相等，迴圈永遠不會結束
signed讀到值為 255 的 byte（0xFF）時，存進 c 變成 -1，跟 EOF 相等，還沒讀到檔尾迴圈就停了

問題出在 c 的型別：getchar 用 int 才能同時表示 256 種 byte 和 EOF 共 257 種值，塞進只有 256 種值的 char 就一定會有兩種撞在一起。修法就是把 c 宣告成 int，page-42 的程式就是這樣寫的。

page-23#

ferror、feof、clearerr、ungetc#

page-04 說 FILE object 裡有兩個 flag：error flag 和 end-of-file flag。

  • ferror、feof：查這兩個 flag，設了就回傳非 0。getc 回傳 EOF 之後，用它們分辨是出錯還是讀完了。
  • clearerr：把兩個 flag 都清掉。flag 一旦設了會一直留著，例如使用者在終端機按 Ctrl-D 結束輸入後，想再讓他輸入，就得先 clearerr。

ungetc：把一個字元「退回」stream，下次讀的時候會先讀到它。

  • 不能退回 EOF（-1）。
  • 退回的不必是剛剛讀到的那個字元，任何字元都可以。
  • 會清掉 EOF flag：退回一個字元之後，stream 又有東西可讀了。
  • 字元存在 stream 的 buffer 裡，不是寫回檔案，檔案內容完全沒變。C 標準只保證能連續退回一個字元。

用途是「多讀一個才知道要停」的情況，例如讀一串數字：讀到第一個不是數字的字元才知道數字結束了，但那個字元屬於下一個 token，要把它退回去。

page-24#

用 ungetc 去掉每行開頭的空白#

想做的事：一直讀，直到讀到第一個不是空白的字元，然後把它退回去，再用 getline（讀一整行，buffer 不夠會自己 realloc 加大的 POSIX 函式）讀這一行剩下的部分。因為那個字元被退回去了，讀到的這一行正好從第一個非空白字元開始。

這段是示意用的，有幾個地方不能直接拿去編譯或用：While 大寫、ftell 只會在出錯時回傳 -1，不會因為讀到檔尾而回傳 EOF，所以迴圈條件永遠成立。可以用的版本：

page-25#

Character-at-a-Time I/O：輸出#

跟 page-21 對稱：putchar(c) 就是 putc(c, stdout)；putc 可以是 macro，fputc 一定是函式。成功回傳寫出的字元，失敗回傳 EOF。

page-26#

Line-at-a-Time I/O：輸入#

fgets：從 fp 讀一行到 buf，成功回傳 buf，檔尾或出錯回傳 NULL。

  • 最多讀 n - 1 個字元，最後一格留給 '\0'。
  • 換行字元 '\n' 會留在 buf 裡，後面再補 '\0'。
  • 一行太長、n - 1 個字元裝不下時，只回傳前面那段，結尾沒有 '\n'；下一次呼叫從剩下的部分繼續讀。

gets：從 stdin 讀一行。

  • 沒有參數指定 buf 有多大，輸入比 buf 長就會一直寫過頭，蓋掉後面的記憶體（overflow），所以 unsafe，見下一頁。
  • 讀到的 '\n' 會被丟掉，只補 '\0'。

gets 因為太危險，C11 已經把它從標準裡移除了，一律改用 fgets。

page-27～28#

Example of Unsafe gets()#

my.i 明明沒被改過，最後卻變成 12345。看 my 在記憶體裡的樣子（int 要放在 4 的倍數上，所以 buf 後面有 3 byte 的 padding，page-33）：

gets 把 "1234567890" 加上 '\0' 共 11 byte 一路寫下去，最後 3 byte 蓋到了 i 的前 3 byte。x86 是 little-endian（低位的 byte 放在前面），所以 i 變成 0x00 00 30 39：'9' 是 0x39、'0' 是 0x30，0x3039 = 12345。

my.buf 印出完整的 10 位數，也是同一個原因：printf("%s") 從 buf 開始一直印到碰到 '\0' 為止，根本不管 buf 只有 5 格。

那行 warning 是 C library（macOS／FreeBSD 的 libc）在程式第一次呼叫 gets 時印出來的，投影片稱它為「kind compiler」的提醒。

page-29#

Line-at-a-Time I/O：輸出#

（投影片把回傳型別寫成 char *，實際是 int：成功回傳非負數，失敗回傳 EOF。）

  • fputs：把 str 寫到 fp，寫到 '\0' 為止（'\0' 本身不寫）。不會自動加換行：str 裡有 '\n' 就寫，沒有就不寫，所以投影片說 line-at-a-time 的輸出不一定要有換行。
  • puts：把 str 寫到 stdout，然後自動補一個 '\n'。

注意兩組的不對稱：

讀一行時 '\n'寫一行時 '\n'
fgets／fputs保留不加
gets／puts丟掉自動加

所以成對使用就不會出錯：fgets 讀進來再 fputs 寫出去，內容原封不動（page-43）。混用就會多一行或少一行。

page-30#

Binary I/O：fread、fwrite#

目的：一次讀寫一整個 struct 這種 binary 資料。binary 資料裡很可能有值為 0 的 byte 或 '\n'，fputs 碰到 '\0' 就停了，fgets 碰到 '\n' 也會停，所以需要一組「照 byte 數搬、不看內容」的函式。

讀寫 nobj 個物件，每個 size byte，回傳實際讀寫了幾個物件（不是 byte 數）：

  • fread 回傳的比 nobj 少：可能是出錯，也可能是讀到檔尾，用 ferror、feof 分辨（page-23）。
  • fwrite 回傳的比 nobj 少：一定是出錯。

Binary I/O 的例子#

  • Example 1：從 data[2] 開始，寫出 4 個 float，也就是 data[2]～data[5]。
  • Example 2：把整個 item 當成 1 個物件寫出去，大小是 sizeof(item)。

兩個例子都檢查回傳值是不是等於要求的物件數（page-30）。

page-32#

Binary I/O：NOT PORTABLE#

用 fwrite 寫出去的檔案，換一台機器或換一個編譯器，fread 讀回來可能就錯了，原因有兩個：

  1. struct 裡每個欄位的 offset，不同的編譯器和系統可能不一樣，因為 alignment（對齊）的規則不同，見 page-33～34。
  2. 同一種型別的 binary 格式，不同的機器可能不一樣：int 可能是 2 byte 或 4 byte，long 在 64-bit Linux 是 8 byte、在 64-bit Windows 是 4 byte；byte order 也可能不同，這就是 ch16 page-40 要在網路上統一用 network byte order 的原因。

所以 fwrite 一個 struct 只適合「同一台機器上同一支程式自己寫、自己讀」。要跨機器交換資料，就要自己規定格式：轉成文字（例如 JSON、CSV），或明確規定每個欄位的大小和 byte order。

page-33#

Memory Alignment#

編譯器實際排出來是 12 byte，等於自動插了 padding：

規則是：每個欄位都要放在「自己大小的倍數」的 offset 上（page-34 的表）。

欄位大小必須放在實際的 offset
Data11任何位置0
Data222 的倍數1 不行，補 1 byte，放在 2
Data344 的倍數4
Data41任何位置8

最後的 Padding2 是為了陣列：struct MixedData arr[2] 裡，arr[1] 緊接在 arr[0] 後面，struct 的大小必須是 4 的倍數，arr[1].Data3 才會落在 4 的倍數上。所以補到 12。右下角的圖就是以 4 byte 為一列畫出的排法。

在 x86-64 的 Linux 上實際跑一次，sizeof 是 12，三個欄位的 offset 分別是 2、4、8，跟上表一樣。

page-34#

為什麼要 alignment#

CPU 讀記憶體不是一個 byte 一個 byte 讀，而是一次讀一整塊對齊好的區塊（一個 word，也就是 CPU 一次處理的資料大小，例如 4 或 8 byte；或一整條 cache line：CPU 的 cache 和記憶體之間一次搬移的單位，通常 64 byte）。一個 4 byte 的 int 如果跨在兩塊的交界上，就要讀兩次再拼起來，有些 CPU 甚至直接不允許。所以投影片說配置記憶體時對齊 cache line 有好處。

每種型別都有預設的 alignment，除非程式設計師另外要求（例如 GCC 的 __attribute__((packed))），編譯器都會照這個放：

型別大小對齊
char11
short22
int、float44
double8Windows 8；32-bit Linux 4（加 -malign-double 則是 8）
long double1232-bit Linux 4
指標432-bit Linux 4

這張表是 32-bit 系統的數字。現在的 x86-64 Linux 上，double 對齊 8、long double 是 16 byte 對齊 16、指標是 8 byte 對齊 8。這也正是 page-32 說「不同系統排法不同」的實例。

page-35#

Formatted I/O#

formatted I/O：照 format 字串在數值和文字之間轉換（%d、%s）。三個一組，差在資料從哪來、往哪去：

前綴對象
沒有stdin／stdout
f指定的 stream fp
s一個字串 buf，不做任何 I/O

sprintf 可能 overflow：它會把結果加上 '\0' 寫進 buf，但不知道 buf 有多大，結果太長就寫過頭，跟 page-27～28 的 gets 一樣。改用 snprintf(buf, size, format, ...)：最多寫 size - 1 個字元再補 '\0'。

v 開頭的版本：參數不是 ...，而是一個 va_list（可變參數列表）。用途是寫自己的 printf 風格函式，把收到的 ... 原封不動轉交出去。APUE 的 err_sys 就是這樣寫的：

page-36#

Problem: No Range Checking#

strcpy 不檢查大小：strcpy(buf, str) 從 str 開始一直複製，直到碰到 '\0' 為止，完全不管 buf 配了多大。

C library 裡有很多這種不安全的函式，共同點都是 只拿到目的地的位址，不知道它有多大：

不安全改用
strcpy(char *dest, const char *src)snprintf(dest, size, "%s", src)，或 strncpy（但它在裝不下時不補 '\0'，要自己補）
strcat(char *dest, const char *src)strncat，或算好剩餘空間再 snprintf
gets(char *s)fgets（page-26）
sprintf(char *buf, const char *format, ...)snprintf（page-35）

寫過頭的資料不只會改壞旁邊的變數（page-27～28），在 stack 上還可能蓋掉函式的 return address（函式結束後要跳回去繼續執行的位置）。攻擊者精心設計輸入，就能讓程式跳去執行他想要的程式碼，這就是 buffer overflow 攻擊。

page-37#

Interleaved R&W restrictions#

回到 page-09 有 + 的那幾種模式：用 r+、w+、a+ 開的 stream 能讀也能寫，但讀和寫之間切換時有規定：

  • 寫完要讀：中間必須呼叫 fflush、fseek、fsetpos 或 rewind 其中一個。
  • 讀完要寫：中間必須呼叫 fseek、fsetpos 或 rewind；除非剛剛的讀取已經讀到檔尾。

原因在於 standard I/O 是用 system call 實作的（page-05）：

  • fread 在 buffer 不夠時呼叫 read，一次讀一大塊 把 buffer 填滿。
  • fwrite 在需要時呼叫 write，把 buffer 裡的資料送出去。
  • 不需要 system call 的時候，就直接在 buffer 裡讀寫，分別由 R 指標（下一個要讀的位置）和 W 指標（下一個要寫的位置）指著。

問題是只有一塊 buffer。讀的時候 read 多讀了一大塊進來，kernel 的 offset 已經跑到後面去了，程式看到的位置卻還在前面；這時直接寫，資料要寫到哪、buffer 裡哪些是讀進來的、哪些是要寫出去的，R、W 兩個指標就對不上，結果依實作而定。fseek 這類函式會把 buffer 清乾淨、把 kernel 的 offset 調回程式看到的位置，切換才安全。

page-38#

Errors may occur in some systems#

test.txt 的內容是 12345 加一個換行。程式讀一個字元（'1'），然後 沒有 fseek 就直接寫，正好違反 page-37 的第二條規定。照「程式看到的位置」來想，讀完第 0 個 byte 後位置是 1，寫入應該蓋掉第 1 個 byte，結果是 11345。

page-39#

The Results#

系統沒有 fseek有 fseek(fp, 0, SEEK_CUR)
Linux1134511345
macOS1234511345
Windows12345 換行之後多一個 111345

沒有 fseek 時，三個系統三種結果：

  • Linux：glibc 自己處理好了，結果正確（實測 Linux 6.8 也是 11345）。
  • macOS：寫入的那個字元不見了，檔案沒有被改。
  • Windows：'1' 被接在檔尾。原因就是 page-37 說的：fread 呼叫 read 時把整個檔案都讀進 buffer，kernel 的 offset 已經在檔尾；fclose 時 library 把 '1' 用 write 寫出去，寫在 kernel 的 offset 上，也就是檔尾。

C 標準對違反規定的情況沒有定義結果，各家 library 怎麼做都不算錯。在 Linux 上剛好正確，不代表程式是對的。

加上 fseek(fp, 0, SEEK_CUR) 之後三個系統都正確。它看起來什麼都沒做（從目前位置移動 0），實際上會丟掉 buffer 裡讀進來的資料，並把 kernel 的 offset 調回程式看到的位置 1（page-19），之後的寫入就寫在正確的地方。

page-40#

Workaround on the Restrictions#

做法 1：每次寫完都 flush。 這只解決了「寫完要讀」那條；讀完要寫，還是得 fseek。

做法 2：同一個 fd 開兩個 stream，一個專門讀、一個專門寫。

兩個 stream 各有自己的 buffer，讀寫不會在同一塊 buffer 裡打架。但投影片提醒：

  • 兩個 stream 的位置要分開管理：它們共用同一個 fd，也就共用 kernel 裡同一個 offset（ch03 page-09），各自的 buffer 卻會讓兩邊看到的位置不同步。切換之前要對要用的那個 stream fseek 到想要的位置。
  • 最後兩個都要 fclose。
兩次 fclose 會關兩次同一個 fd

fclose 會 close 底下的 fd。先 fclose(fpin) 的話 fd 已經關掉了，fclose(fpout) 要 flush 時寫不出去，資料就不見了。所以要先 fclose(fpout)；或一開始就寫 fpout = fdopen(dup(fd), "w")，讓兩個 stream 各有自己的 fd（ch03 page-52；兩個 fd 仍然共用同一個 offset）。

page-41#

Standard I/O Efficiency#

看完各種讀寫函式，最後比較它們的效率。讀一個 98.5 MB、300 萬行的檔案，複製到另一個檔案，比較各種寫法（單位：秒）：

寫法User CPUSystem CPUClock程式碼大小（byte）
read／write，最佳 buffer 大小0.010.186.67
fgets、fputs2.590.197.15139
getc、putc10.840.2712.07120
fgetc、fputc10.440.2711.42120
read／write，一次 1 byte124.89161.65288.64

這個檔案就是 ch03 page-42 那個 103,316,352 byte 的檔案（= 98.5 MiB），第一列和最後一列也就是那張表的 BUFFSIZE = 8192 和 1。

System CPU 幾乎一樣（投影片的紅字）：standard I/O 的三種寫法都只多了一點點。不管程式一次要一個字元還是一行，library 都是一次 read／write 一整個 buffer，system call 的次數跟最佳的 read／write 差不多。拿 getc 和最後一列比：同樣是一次處理一個字元，System CPU 從 161 秒降到 0.27 秒，這就是 buffer 的效果。

差別在 User CPU：

  • getc／putc 迴圈要跑 1 億次（每個字元一次），每次都有呼叫函式、檢查 buffer 的成本，加起來 10 秒以上。這時 CPU 比磁碟慢，Clock 跟著變成 12 秒（ch03 page-42 的 read-ahead 分析）。
  • fgets／fputs 迴圈只跑 300 萬次（每行一次），每行裡面的字元由 library 內部最佳化過的程式碼一次處理，所以只要 2.6 秒，Clock 也接近磁碟的 6.7 秒。
  • getc（macro）跟 fgetc（函式）幾乎一樣快，macro 在這裡沒帶來好處。

結論：standard I/O 比自己挑好 buffer 大小的 read／write 慢一點，但比天真地一次讀一個 byte 快很多，而且程式好寫。最後一欄是編譯出來的迴圈程式碼大小，三種寫法差不多，不是考量重點。

  • getc 回傳 EOF 跳出迴圈之後，用 ferror 確認是出錯還是正常讀完（page-23）。

page-44#

Multibyte Files：fwide#

先講背景。英文字母一個 byte 就裝得下，中文字不行。C 用兩種方式表示這類字元：

  • multibyte（多位元組）：存在檔案裡的編碼，例如 UTF-8，一個中文字佔 3 byte，每個字的長度不固定。
  • wide character（寬字元，型別 wchar_t）：程式裡用的表示法，每個字元長度固定（Linux 上是 4 byte），方便處理「第幾個字」。

stream 也分兩種 orientation（方向）：

orientation用哪些函式讀寫時
byte-oriented這章前面所有的函式一個一個 byte 原樣搬
wide-orientedfwprintf、fwscanf、fgetwc、fputwc……程式這邊是 wchar_t，檔案那邊是 multibyte，library 依目前的 locale（語系設定）自動轉換

規則：

  • stream 剛開好時 沒有 orientation。
  • 第一次對它用 byte 函式或 wide 函式，就 固定 成那一種，直到 stream 關掉為止都不能改（freopen 會清掉，page-10）。同一個 stream 混用兩種函式是錯的。

fwide 用來設定或查詢 orientation：

mode做什麼回傳值意思
負數設成 byte-oriented正數wide-oriented
正數設成 wide-oriented負數byte-oriented
0不設，只查詢0還沒有 orientation

已經有 orientation 的 stream，fwide 不會改它，只回傳目前的狀態。wmemcpy 是 memcpy 的 wchar_t 版本。
