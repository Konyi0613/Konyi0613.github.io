Example of Unbuffered I/O#

整章的開場程式，功能等同 cat：把標準輸入原封不動倒進標準輸出。

逐項拆開：

  • #include <unistd.h> —— UNIX standard header，read、write、close 的宣告和 STDIN_FILENO 這幾個常數都在這裡。注意 沒有 #include <stdio.h>：這支程式一個 C 標準函式庫的 I/O 函式都沒用到。
  • char buf[100] —— 一塊 user space 的記憶體，read 讀到的資料會被 kernel 複製進來。它是區域變數，所以住在 stack 上（ch01 page-51）。100 這個數字是你自己挑的，不是誰規定的。
  • ssize_t n —— signed size 的意思。size_t 是無號整數（用來表示大小），但 read 失敗時要回傳 -1，無號型別表達不了負數，所以另外定義一個有號版本。
  • read( STDIN_FILENO, buf, 100 ) —— 從 fd 0 讀 最多 100 個 byte 進 buf。回傳值有三種：
回傳值意思
> 0實際讀到的 byte 數，可能少於 100
0EOF，資料讀完了
-1出錯，錯誤碼放在 errno（ch00 page-16 第 10 步）
  • write( STDOUT_FILENO, buf, n ) —— 寫 n 個 byte 到 fd 1。這裡寫的是 n 而不是 100，正是因為上一點：read 不保證讀滿。從鍵盤讀通常一次只拿到一行，從 pipe 讀則看對方寫了多少。寫成 100 就會把 buffer 裡上一輪的殘渣一起送出去。
  • while (…) != 0 —— 讀到 EOF 才停。
投影片簡化掉的地方

這個迴圈沒有檢查 -1。出錯時 n 是 -1，不等於 0，迴圈會繼續，然後 write(1, buf, -1) 也失敗，變成無窮迴圈。正式寫法是 while ( (n = read(...)) > 0 )。

UNIX Standardization#

同一段程式想在不同 UNIX 上都能編譯、都能跑，靠的是兩套標準。它們管的東西不一樣：

誰訂的管什麼代表性的 header
ANSI C美國國家標準協會（1989，後來交給 ISO）C 語言本身：語法、型別，加上一套與作業系統無關的標準函式庫stdio.h、stdlib.h、string.h、math.h、time.h
POSIXIEEE作業系統要提供哪些服務：system call 的名字、參數、行為unistd.h、pwd.h、dirent.h、grp.h、fcntl.h
  • ANSI C — Provide portability of conforming C programs to a wide variety of OS’s：只要用 ANSI C 的東西寫，任何有 C 編譯器的平台都該編得過。printf、malloc、strcpy 在 Windows 上同樣存在，因為它們屬於 C 語言的標準函式庫，不屬於哪個 OS。
  • POSIX — Define the application programming interface for softwares compatible with variants of OS’s：POSIX 是 Portable Operating System Interface 的縮寫（結尾的 X 是為了呼應 UNIX）。早年 UNIX 分裂成 System V 和 BSD 兩大家族（page-14 會再碰到），各家介面不一致，POSIX 就是來收拾這個局面的：只要兩個系統都遵守 POSIX，同一支程式重新編譯就能跑。fork、read(fd, …) 這些在 Windows 上沒有，因為它們是 OS 服務，不是語言的一部分。

這解釋了兩件事：

  1. 為什麼上面那支程式 include 的是 <unistd.h> 而不是 <stdio.h> —— 它用的是 POSIX 那一邊的東西。
  2. 為什麼 ch01 page-25 的 man 章號能拿來分辨函式的身分 —— read(2) 在 section 2（system call，POSIX 管），printf(3) 在 section 3（library 函式，ANSI C 管）。

page-04#

Unbuffered I/O：每次呼叫都真的進一次 kernel#

這張圖是 unbuffered I/O 最素樸的樣子：User Process 每呼叫一次 read()，箭頭就往右穿過 Kernel 一路到 Storage，再原路把資料（圖上的小紅方塊）帶回來。

投影片下方那句 Each read() and write() invokes a system call in the kernel (part of POSIX.1)! 是重點。「一次 system call」不是一句輕描淡寫的話，它是 ch00 page-16 拆過的那完整 11 步：放編號進暫存器 → trap → 切 kernel mode → 查 system call table → 執行 handler → 切回 user mode。ch00 page-14 那支跑一百萬次 write 的程式燒掉 1.32 秒的 sys，燒的就是這個。

所以 page-03 那個 buf[100] 的大小不是隨便選的：buffer 開得越大，同樣的資料量需要的 read 次數越少，付的 system call 成本也越少。

NOTE

這張圖有一點誤導，page-08 會修正：read() 進了 kernel 之後，不一定真的會碰到 Storage。

page-05#

Hard Disk Drive (HDD)#

既然每次 I/O 最終要落到 Storage，就得知道 Storage 有多慢。先看傳統硬碟的構造：

零件是什麼
platter（碟片）一片表面鍍了磁性材料的圓盤，正反兩面都能記錄。一顆硬碟疊好幾片
spindle（主軸）穿過所有碟片中心的軸，帶著它們一起高速旋轉，常見 5400 或 7200 RPM
track（磁軌）碟片上的一個同心圓
sector（磁區）把 track 切成的一小段，傳統是 512 byte，現在多半 4 KB。這是硬碟最小的讀寫單位：你只想改一個 byte，硬碟也得把整個 sector 讀出來、改掉、再整個寫回去
cylinder（磁柱）所有碟片上半徑相同的 track 疊起來的那個圓柱
read-write head（讀寫頭）每個碟面一個，靠氣流浮在碟片上方極近的距離
arm / arm assembly（機械臂）所有讀寫頭固定在同一組機械臂上，只能一起移動

最後一行是 cylinder 為什麼是個有用的概念：讀寫頭連動，所以換到「同一個 cylinder 的另一個碟面」不需要移動機械臂，幾乎不花時間；換到別的 track 就得整組搬過去。

sector 與 block 不是同一件事

sector 是硬碟的單位，由硬體決定，硬碟只認它（透過 LBA 定位：Logical Block Address，硬碟把所有 sector 從 0 開始編號）。block 是檔案系統的單位，格式化時決定（ext4 預設 4 KB，見下方），一個 block 就是連續的幾個 sector。

kernel 從來不跟硬碟要「一個 byte」，它要的是一個 block；page-08 buffer cache 存的也是 block。所以後面講的「disk block」是 kernel 那一側的說法，不是硬碟規格上的單位。（SSD 裡還有另一個也叫 block 的東西，跟這個毫無關係，page-06 會分清楚。）

ext2／ext3／ext4 是什麼

file system（檔案系統） 是一套「資料在磁碟上怎麼排」的格式：block 多大、i-node 長什麼樣、目錄怎麼存。格式化（例如 mkfs.ext4）就是把這套格式寫到磁碟上。

ext（extended file system）是 Linux 最常用的一個家族，三代都沿用 i-node 的設計：

年份重點
ext21993基本款：i-node 用一格一格的指標記內容在哪些 block（page-37）
ext32001ext2 加上 journal（日誌）：改動前先記下要做什麼，當機後照日誌收尾，不必掃整顆磁碟檢查
ext42008現在 Linux 的預設：改用 extent 記 block（page-37），支援更大的檔案和磁碟

其他常見的 file system：Windows 的 NTFS、macOS 的 APFS、隨身碟常用的 FAT32／exFAT。df -T 可以看到每個掛載點用的是哪一種。

投影片標出的兩個延遲#

一次隨機讀取要等三件事：

  1. Seek Time（尋道時間） —— 機械臂把讀寫頭移到目標 track 的時間。典型 5 ~ 10 ms。
  2. Rotational Latency（旋轉延遲） —— 讀寫頭就定位後，還要等目標 sector 轉到底下。平均是轉半圈：7200 RPM 是一秒 120 圈，一圈 8.33 ms，所以平均約 4.17 ms。
  3. Transfer Time（傳輸時間） —— 真正把資料讀出來的時間，相較之下小到可以忽略。

加起來大約 10 ms。把它放進同一把尺上看：

動作量級
CPU 執行一條指令~1 ns
讀一次主記憶體~100 ns
一次 system call 的來回（ch00 page-16）~1,000 ns（1 μs）
HDD 隨機讀一次~10,000,000 ns（10 ms）

慢了四個數量級，而且慢在 機械動作上——這是物理，不是程式寫得好不好的問題。兩個直接的推論：

  • 循序讀遠快於隨機讀：連著讀同一條 track 上的資料只要付一次 seek，隨機跳則是每次都付。
  • 想辦法 不要碰它。這就是 page-08 那個 buffer cache 存在的全部理由。

page-06#

Flash-based SSD (Solid State Drive)#

SSD 沒有任何會動的零件，資料存在 NAND flash 裡，靠電子的方式讀寫。但它有自己一套很反直覺的限制。

階層：block 與 page#

圖上畫的是 NAND Flash Memory 切成 Block 0、Block 1、Block 2…，每個 block 裡有 Page 0 到 Page 127。一個 page 常見 4 ~ 16 KB，所以一個 block 大約幾 MB。

「block」這個字有三種意思
名稱誰的單位大小在哪出現
sectorHDD 硬體512 B 或 4 KBpage-05
block（檔案系統）檔案系統，格式化時決定ext4 預設 4 KBpage-05、08
block（flash）SSD 晶片幾 MB，含 128 個 flash page這一頁

三者互不相干，flash 的 page 也跟虛擬記憶體的 page（page-12）無關。

這份筆記其他地方寫的 block（buffer cache 裡的 block、dirty block）一律指檔案系統的 block，只有這一頁講的是 flash block。

三種操作，三種單位#

操作單位速度限制
Read a page一個 page快，幾十 μs無
Program a page（寫）一個 page中等只能把位元從 1 變成 0
Erase a block（抹除）一整個 block慢，幾 ms把整個 block 全部變回 1

cannot overwrite 就是從這裡來的：寫入只能單向把 1 變 0，所以一個已經寫過的 page 沒辦法直接蓋掉重寫。要讓它回到可寫狀態，唯一的辦法是 erase，而 erase 的單位是 整個 block（128 頁）。

於是 SSD 實際的做法是：erase block before write 這句話反過來理解——與其為了改一頁去抹掉 128 頁，不如根本不原地改。新資料寫到別的空白 page，舊的那頁標記成「無效（invalid）」，等某個 block 裡無效頁多到一定程度，再統一回收。

Write Amplification（寫入放大）#

回收的時候麻煩就來了。假設一個 block 有 128 頁，其中 100 頁無效、28 頁還有效。要抹掉這個 block 之前，得先把那 28 頁 搬到別的 block，這叫 garbage collection。這些搬移都是額外的實體寫入。

寫入放大倍數=實際寫進 flash 的資料量你要求寫入的資料量\text{寫入放大倍數} = \frac{\text{實際寫進 flash 的資料量}}{\text{你要求寫入的資料量}}寫入放大倍數=你要求寫入的資料量實際寫進 flash 的資料量​

你以為只寫了 4 KB，SSD 可能實際寫了幾十 KB。為什麼要在意這個數字：flash 的每個 block 能被 erase 的次數有上限（依製程大約幾千到幾萬次），寫入放大直接等於壽命被加速消耗——這就是下一頁說 SSD「shorter lifespan」的原因。

FTL

「寫到別的 page、記住新位置、適時回收」這整套轉換由 SSD 內部的 FTL（Flash Translation Layer） 負責，對 OS 完全隱形。OS 還是照樣說「給我第 N 個 block」，以為自己在對一顆普通硬碟講話。

page-07#

SSD vs. HDD#

SSDHDD
faster✅ ❌slower
shorter lifespan❌ ✅longer lifespan
more expensive❌ ✅cheaper
non-mechanical (flash)✅ ❌mechanical (moving parts)
shock-resistant✅ ❌fragile

每一項都能從前兩頁推出來：

  • faster —— SSD 沒有 seek time 也沒有 rotational latency（page-05），隨機存取的差距可以到上百倍。
  • shorter lifespan —— erase 次數有上限，再加上寫入放大（page-06）。HDD 則是碟片本身不會因為讀寫而磨損。
  • shock-resistant / fragile —— HDD 運轉時讀寫頭浮在碟片上方極近處，被撞一下就可能刮傷碟面。SSD 沒有這個問題。
  • 用途 —— SSD 放作業系統和常用檔案（在意速度），HDD 放影片、備份這類大而不常動的資料（在意每 GB 的價格）。

但對這門課來說，最重要的一句話是投影片沒寫的：不管底下是哪一種，你的程式看到的都是同一組 read 和 write。 這正是 ch00 page-05「OS 是一台延伸機器」的具體意思——把兩種構造完全不同的硬體包成同一個介面。

page-08#

Unbuffered I/O：加上 buffer cache 的真實版本#

這張圖是 page-04 的修正版。Kernel 方塊裡多了一個 buffer cache：kernel 在主記憶體裡留的一塊空間，存放 最近用過的 disk block。

圖上 11 個編號的順序：

步驟發生什麼
(1)程式呼叫 read()，進 kernel
(2)要的 block 不在 cache 裡（cache miss），kernel 去 Storage 拿
(3)拿回來的 block 放進 buffer cache
(4)從 cache 複製你要的那段到 user 的 buf，read() 返回
(5)程式再呼叫一次 read()
(6)這次要的資料 已經在 cache 裡了（cache hit）
(7)直接從 cache 複製回去 —— 完全沒有碰硬碟
(8)又一次 read()
(9)這次要的是另一個 block，cache 裡沒有，再去 Storage 拿
(10)放進 cache
(11)複製回去，返回

投影片的兩行結論：

  • Buffer cache: cache of recently used disk blocks
  • It’s not necessary to trigger disk I/O for unbuffered I/O —— 「unbuffered」不代表每次呼叫都真的動硬碟。以 page-05 的數字來看，(7) 省掉的是 10 ms，換成一次記憶體複製的 100 ns 等級。
buffer cache 與 kernel buffer

buffer cache 專指暫存 磁碟資料 的那塊記憶體。kernel 裡還有很多別的 buffer，名字各不相同：pipe 有 pipe buffer、終端機有 input／output queue、網路連線有 socket 的收／送 buffer（ch14 page-04）。這些連同 buffer cache 統稱 kernel buffer：kernel 在記憶體裡暫放資料的地方。

省掉的是磁碟，不是 system call

步驟 (5) 和 (8) 依然是完整的 system call：trap、mode switch、查表、檢查參數，ch00 page-16 那 11 步一步都沒少。buffer cache 消掉的只是最慢的那一段。所以 ch00 page-14 程式 2 的 1.32 秒 sys 時間還是跑不掉——那是 system call 本身的成本。

寫的方向#

page-08 這張圖畫的是讀。寫也走同一條路，但有一個更極端的差別，值得單獨講。

讀不能作弊，寫可以。 read() 遇到 cache miss 時，kernel 沒有別的選擇，只能真的去硬碟把資料拿回來，你的 process 就卡在那裡等那 10 ms（ch01 page-43 的 Blocked 狀態）。但 write() 不一樣：資料是你給的，kernel 手上已經有了，它大可以先收下、答應你晚點寫，然後立刻讓你繼續跑。

所以一次 write(fd, buf, n) 實際發生的是：

步驟發生什麼
1trap 進 kernel（system call 的成本還是要付）
2把 buf 裡的 n 個 byte 從 user space 複製到 buffer cache 裡對應的那個 block
3把那個 block 標記成 dirty（髒的）——意思是「記憶體裡這份比硬碟上那份新」
4直接返回。硬碟從頭到尾沒有被碰到

kernel 過一陣子才會把 dirty block 真的寫回硬碟。這種做法叫 write-back，或 delayed write（延遲寫入）。

好處：不只是不用等#

  • 不用等那 10 ms：write() 的成本降成一次記憶體複製。

  • 寫入可以被合併：同一個 block 在短時間內被改 100 次，硬碟只需要寫回 最後那一份，前面 99 次完全省下來。

    這點在 HDD 上特別值錢。page-05 說過 sector 是硬碟最小的讀寫單位，所以「改一個 byte」對硬碟來說其實是「整個 sector 讀出來 → 改掉那個 byte → 整個寫回去」。有了 buffer cache，這組讀-改-寫只要做一次，而不是每次 write() 都做一次。

什麼時候才真的寫回#

kernel 背景定期寫（Linux 預設約 30 秒內）、buffer cache 要騰空間時、umount（卸載，把一個檔案系統從目錄樹上拆下來，ch01 page-54 mount 的反動作）或關機時，或者程式自己開口要求。

代價：write() 返回 ≠ 資料在硬碟上

write() 回來只代表 kernel 收下了。這時斷電，還是 dirty 的那些資料就沒了，而程式從頭到尾以為自己寫成功了。隨身碟拔掉前要「安全移除」就是這個原因——umount 會把 dirty block 全部寫回去。

要自己確保寫回，有三種手段：

做法效果
sync()把全系統的 dirty block 寫回。POSIX 允許它排進寫回佇列就返回、不等寫完；Linux 的 sync 則會等寫完
fsync(fd)只處理這個檔案，等到真的落到硬碟才返回
開檔時加 O_SYNC之後每次 write() 都等資料落地才返回（page-17）

投影片的區分是「等不等」：sync 只是催一下，fsync 盯到寫完為止。Linux 的 sync 其實也會等，兩者剩下的差別是範圍：sync 寫全系統，fsync 只寫這個檔案，所以要保證某個檔案的資料安全還是用 fsync。page-61～65 會再加上 fdatasync，並實測它們有多慢。ch01 page-23 那個 /bin/sync 帳號做的就是第一行。

Process 與 Kernel 的資料結構全圖#

那條橘線#

橘線把圖切成兩半，標題就是 Process 和 Kernel：

  • 左半 Per-process data structures —— 每個 process 各自一份。
  • 右半 Kernel (global & shared) data structures —— 全系統只有一份，所有 process 共用。
WARNING

page-10 也有一條橘線，但畫的位置不一樣、意思也不一樣。這裡分的是「各自一份 vs. 共用一份」，那裡分的是「buffered I/O 從哪開始 vs. unbuffered I/O 從哪開始」。

箭頭怎麼看#

圖上有兩種箭頭，差別很重要：

  • 實線箭頭 = 一個指標。表示「這個欄位裡存著對方的位址」，kernel 順著它就能走到下一個結構。
  • 虛線箭頭 = 資料流的方向，不是指標。

由左到右一共六條：

箭頭從到意思
實線FILE *fpFILE objectfp 這個指標指向的東西
實線FILE object 的 file descriptor 欄fd table 的某一格FILE object 裡存著一個 fd，那個 fd 就是這一格的編號
實線fd table 的某一格open file table 的某一項這個 fd 對應到哪一次開檔（這條跨過了橘線）
實線open file table 的某一項v-node table 的某一項這次開檔，開的是哪個檔案

後兩條之所以是虛線：v-node 裡並沒有存一個指向 buffer cache 的指標。buffer cache 是以 disk block 為單位獨立管理的，不屬於任何一個檔案，所以那兩條只表示「資料會經過這裡」。

三張表分別存什麼#

1. Open file desc. table（每個 process 一份）#

每一格對應一個 fd，格子裡只有兩樣東西：

欄位內容
file descriptor flags目前實際上只有一個旗標 FD_CLOEXEC：exec 換掉程式時，要不要自動關掉這個 fd
指向 open file table 的指標這個 fd 對應哪一次開檔

所以這張表幾乎什麼都不存，它只是「編號 → 開檔」的轉接站。fd 這個整數的全部意義就是「第幾格」。

2. Open file table（全系統一份）#

每一項對應 一次成功的 open()：每呼叫一次 open() 就開一項新的，不管是不是同一個 process、開的是不是同一個檔案。

欄位內容
file status flagsopen() 當初給的那些旗標：O_RDONLY、O_WRONLY、O_APPEND、O_NONBLOCK…
current file offset目前讀寫到第幾個 byte。read／write 做完會自動往後移，lseek 就是直接改這個數字
指向 v-node 的指標開的是哪個檔案
reference count有幾個 fd 指著這一項（page-15）

「這次開檔的狀態」全在這裡，其中 offset 是最關鍵的一欄。

3. v-node table（全系統一份）#

每一項對應 一個正在被開著的檔案：

欄位內容
v-node 資訊檔案型態，以及一組函式指標：要讀這個檔案該呼叫哪支函式。ext4 和 NFS 填的是不同的函式——這就是 virtual 的意思
i-node 資訊檔案真正的 metadata：owner、group、權限、三個時間（atime：最後一次讀取；mtime：最後一次改內容；ctime：最後一次改 i-node 本身，例如 chmod，不是建立時間；ch04 page-58）、檔案大小，以及 內容放在磁碟的哪些 block
reference count有幾項 open file table 指著這個檔案（page-15）

「檔案本身是什麼」全在這裡。 注意檔名不在裡面，原因 page-15 會講。

串起來看#

一次 read(fd, buf, n) 進了 kernel 之後，kernel 做的事就是照著這串箭頭走：

用 fd 當索引查 fd table → 沿指標找到 open file table 那一項 → 讀出 current file offset，知道要從檔案的第幾個 byte 開始 → 沿指標找到 v-node → 由 i-node 資訊算出那個位置對應磁碟的哪個 block → 去 buffer cache 找這個 block，沒有才向 disk 要（page-08）。

既然 read 會自己去 disk 拿，為什麼還要先 open？#

看上面這串就知道：read／write 只收一個 fd，不收檔名。它們一開頭就假設「fd → open file table → v-node」這條路已經接好了。接好這條路的就是 open：

open(path, flags) 做的事結果
照著路徑一層層查目錄，把檔名換成磁碟上的 i-node（ch01 page-53：目錄就是「檔名 → 去哪找」的表）知道是哪個檔案
檢查權限：你能不能用 flags 要求的方式開它（ch01 page-55）不合格就在這裡失敗
把 i-node 讀進記憶體，放進 v-node table（已經有人開著就直接共用那一項）之後找 block 位置不必再碰磁碟上的 i-node
在 open file table 開一項，記下 flags、offset 設為 0這次開檔的狀態
在 fd table 找最小的空格，指向那一項（page-28）回傳這個號碼當 fd

所以分工是：open 處理「哪個檔案、准不准開」，只做一次；read／write 處理「內容」，做很多次。 查路徑、檢查權限都很花時間，如果每次 read 都帶檔名，這些就得每次重做一遍。

open 不會讀檔案內容。內容是在 read／write 真的用到某個 block 時，才照 page-08 的方式搬進 buffer cache。

課堂說的「mirror 到 buffer cache」

mirror（鏡像）指的是「同一份資料在另一個地方有一份副本，而且兩份會保持一致」。這裡是說：磁碟上的檔案內容，會在 buffer cache 裡有一份副本；read／write 都是對這份副本做，改過的部分（dirty block）再由 kernel 寫回 disk。

注意兩件事：這份副本是 一個 block 一個 block、用到才載入 的，不是 open 時把整個檔案複製進來；而且真正觸發載入的是 read／write，不是 open。

為什麼是三層#

三張表的差別在於「一項代表什麼」：

表一項代表這一項裡記著
open fd table一個 fd這個 process 的第 3 號 fd，對應到哪一次開檔
open file table一次 open()這次開檔讀寫到第幾個 byte、當初用什麼模式開的
v-node table一個檔案這個檔案本身的 metadata

由上往下範圍越來越大：一個檔案可以被開好幾次（對到好幾項 open file table），而 一次開檔又可以被好幾個 fd 指著（dup、fork）。為什麼要拆得這麼細，page-29～31 會用例子說明。

v-node 與 i-node

這兩個詞指的是不同層次的東西：

是什麼
on-disk i-nodefile system 在磁碟上記錄一個檔案的固定格式（owner、權限、大小、block 位置），不管檔案有沒有開著都在。格式由各 file system 自己決定（ch04 page-44）
in-memory i-node開檔時讀進記憶體的副本，只有開著的檔案才有，改了再同步回磁碟（page-25）。page-16 圖上的 in-core inode 就是它
v-node（virtual node）kernel 包在 i-node 外面的通用外殼：記 file type、reference count，加上一組「要讀寫這個檔案該呼叫哪支函式」的函式指標。ext4、NFS、/proc 各填自己的函式，上層只跟 v-node 打交道，不必管底下是哪種 file system

SVR4、BSD 把 v-node 和 i-node 分成兩層。Linux 沒有獨立的 v-node：它記憶體裡的 struct inode 自己帶著那組函式指標，兼任 v-node 的角色。所以這門課把 v-node table 記成 i-node table 即可，講的都是「開著的檔案在 kernel 記憶體裡的那一項」。

What “Unbuffered” refers to?#

先把 I/O 這個詞講清楚#

I/O 就是你的程式和外界之間搬資料——外界指檔案、終端機、pipe、網路。而這些東西只有 kernel 碰得到（ch00 page-07），所以每一次 I/O 最後都得請 kernel 代勞，也就是一次 system call。

「buffered / unbuffered」不是兩條不同的路，而是 你從哪一層開口：

unbuffered I/O（ch03）buffered I/O（ch05）
用什麼函式open、read、writefopen、fread、fprintf、printf
操作對象fd，一個小整數FILE *，一個指標
誰提供的OS（POSIX）C 標準函式庫（ANSI C）
user space 有沒有 buffer沒有有，在 FILE object 裡
你呼叫 100 次，進幾次 kernel100 次可能只有 1 次
看到的資料一串沒有格式的 byte可以格式化（%d、%s）

關鍵是最後一件事：buffered I/O 是蓋在 unbuffered I/O 上面的一層，不是另一條路。 printf 自己不會做 I/O，它只是把字放進 FILE object 的 buffer，等累積夠了，照樣去呼叫 write（ch00 page-16 結尾那段）。所以圖上才是一條由左往右的箭頭，而不是兩條並排的路。

為什麼會有兩層 buffer#

因為它們在解決 兩個不同的問題：

解決的問題
buffer cache（kernel 提供）硬碟太慢（page-05 的 10 ms）。把 block 留在記憶體裡，能不碰硬碟就不碰
FILE 裡的 buffer（C library 提供）system call 太貴（ch00 page-14）。把零星的小量資料湊成一大筆，少進幾次 kernel

所以 FILE * 本質上就是 一個 fd 加上一塊 buffer——page-09 圖上的 FILE object 裡裝的正是這兩樣。printf 把字放進那塊 buffer，累積夠了才拿裡面那個 fd 去呼叫一次 write。

反過來說，當你需要「說出去就真的出去」時（寫 log、跟別的 process 即時溝通），那層 buffer 就變成阻礙，這時才直接用 fd。buffer 什麼時候 flush、怎麼關掉它，在 ch05 page-13～17。

同一張圖，這次紅圈圈出了兩個都叫 buffer 的東西：

在哪裡誰提供的
FILE object 裡的 bufferuser space，你的 process 裡C 標準函式庫（投影片：Buffer in user’s process is provided by the C standard library）

橘色那條直線是兩種 I/O 的起點分界，上面的橫箭頭標著 unbuffered I/O (operate on file descriptors)：

  • buffered I/O（ch05） —— 從最左邊出發，fprintf 先把資料放進 FILE object 的 buffer，累積夠了才往右送。
  • unbuffered I/O（ch03） —— 從橘線出發，跳過 C library 那層 buffer，直接拿 file descriptor 呼叫 write。

所以答案是：「unbuffered」少掉的是 user process 裡那層 buffer，不是 kernel 的 buffer cache。 kernel 那層誰都躲不掉。

一個看得出兩層 buffer 的例子#

螢幕上會 先出現 B 再出現 A。A 卡在 user space 的 buffer 裡，要等到 buffer 滿了、遇到換行（輸出到終端機時）、或程式正常結束時被 flush（沖出去：把 buffer 裡累積的資料一次用 write 送進 kernel、清空 buffer；exit() 會自動做，也可以自己呼叫 fflush(stdout)）才會真的送出去。程式當掉就沒有這一步，所以 printf 的輸出常常不見，而 write 的不會。「遇到換行就送出」只在輸出接到終端機時成立；導到檔案或 pipe 時要等 buffer 滿，見 ch05 page-15。

Kernel Space vs. User Space?#

投影片在同一張圖上用紅框把三塊圈起來，問的是：這些結構到底住在哪一邊？

直覺答案是照圖上那條「Per-process | Kernel」的直線切，但那是錯的。正確的分法是：

結構每個 process 一份？住在
FILE object（含它的 buffer）是user space
open file descriptor table是kernel space
open file table否，全系統共用kernel space
v-node / inode table否kernel space
buffer cache否kernel space

重點是那一行反直覺的：per-process 不等於 user space。fd table 確實是每個 process 各一份，但它是 kernel 幫你保管的，你的程式碰不到、也改不了。

這正好解釋了一個之前沒解釋的設計：為什麼 open() 回傳的是一個小整數(fd)，而不是一個指標？

  • 指標是位址，交到 user 手上你可以隨便改、隨便指，kernel 拿到後無從判斷真假 —— 這違反 ch00 page-10 的「OS 不信任 user」。
  • 整數只是一個索引。kernel 每次收到它，都能檢查「這個 process 的 fd table 有這麼多格嗎？那一格真的開著東西嗎？」，這就是 ch00 page-16 第 8 步寫的「檢查 fd 是不是這個 process 真的開著的檔案」。

同樣的道理：FILE * 是真正的指標，因為 FILE object 在 user space，本來就是你自己的東西。

exec 正好沿著這條線切

ch01 page-44 的 exec 是這張表最好的驗證——它把 user space 那一半整個丟掉重建，kernel space 那一半原封不動：

內容
丟掉重建text、initialized data、bss、heap、stack，全部換成新程式檔的內容。所有變數、malloc 來的記憶體、呼叫堆疊都沒了
保留PID、PPID、cwd（current working directory，目前所在目錄）、umask（新檔預設要關掉的權限，page-23）、user／group ID、signal mask（暫時擋住不收的 signal），以及 fd table

fd table 逃得過，是因為它根本不在被換掉的那一半。 所以 shell 設好的 fd 1 才能穿過 exec 活到新程式手上（page-16 的重導向）。反過來，FILE object 在 user space，exec 時跟著被丟掉：printf 放進 buffer 但還沒 flush 的資料，exec 之後就永遠出不去了（ch05 page-11）。

一個更細的例子：exec 之後 signal handler（收到 signal 時要執行的函式）會被重設成預設值，但 signal mask 保留。因為 handler 是 user space 的一個函式位址，那段程式碼已經被蓋掉了；mask 只是 kernel 裡的幾個位元，不受影響。

Virtual Memory for Each Process#

先補：virtual memory 與 page table#

投影片標題的 virtual memory，ch00 page-18 只用一行帶過，這裡補齊——因為它是理解這張圖的前提。

問題：整台機器只有一條實體記憶體，但每個 process 都希望自己從位址 0 開始、獨占一整段空間。

做法：程式裡用到的位址全部都是假的，叫 virtual address（虛擬位址）。CPU 每次存取記憶體，硬體都會即時把它翻譯成真正的 physical address（實體位址）。

翻譯不是一個 byte 一個 byte 做的——記憶體被切成固定大小的塊（x86-64 上是 4 KB），虛擬那邊的一塊叫 page，實體那邊的一塊叫 frame。page table 就是記錄這個對應的表：

page table 的一列意思
第 n 個 page → 第 m 個 frame這個 process 的第 n 塊虛擬記憶體，實際上放在實體記憶體的第 m 塊

每個 process 各有一張自己的 page table，由 kernel 維護。兩個 process 就算用同一個虛擬位址，查的是不同的表，會被翻到不同的 frame，所以誰也看不到誰——這就是「每個 process 以為自己獨占記憶體」的實作方式。

也因此 換 process 就得換一整張 page table，這正是 ch00 page-10 說 context switch 比 mode switch 貴的原因之一。

NOTE

這裡的 page 跟 page-06 那個 flash page 沒有關係，兩邊只是剛好都叫 page。

user space 那幾段 ch01 page-51 已經講過，這頁的新東西是最上面那塊。

關於 kernel space 的三件事#

  1. 每個 process 的位址空間裡都有它，而且都 map 到 同一份實體記憶體——整台機器只有一個 kernel。
  2. user mode 下碰不到。CPU 的模式位元（ch00 page-11）會擋下來，試圖讀取就是 segmentation fault。
  3. 為什麼要塞進來，而不是讓 kernel 完全獨立一個位址空間？ 兩個好處：system call 進 kernel 時不必換 page table（省掉 ch00 page-10 講的 context switch 成本，只要 mode switch 就好）；而且 kernel 可以直接用 user 給的位址讀寫 user 的記憶體，例如 read 把資料複製進 buf（ch00 page-16 第 8 步）。

接回這一章#

page-03 那支程式的每個東西，現在都能在這張圖上指出位置：

  • char buf[100] 在 stack（user space）。
  • buffer cache 在最上面那塊 kernel space。
  • read() 做的事，就是把資料從 kernel space 的 buffer cache 複製到 user space 的 buf。

這次複製是必要的、也是有成本的：因為 user mode 不能直接讀 kernel space，所以資料非得搬一趟不可。（mmap 這類技術就是為了省掉它，但那是後話。）

File Descriptor#

fd 的正式定義，一條一條看。

fd 是什麼樣的一個數字#

投影片第一句 Non-negative integer returned by open() or creat(): 0 .. OPEN_MAX 是一句話，講了三件事。

「非負整數」 —— 正因為負數用不到，-1 才能空出來表示錯誤（page-03 的 read 也是同一個慣例）。

「由 open() 或 creat() 給你」 —— 你不能自己挑一個數字當 fd，只能跟 kernel 要，它從 fd table 裡找一格空的給你。

creat 少一個 e

creat() 是早期專門用來建立新檔的呼叫，效果等於 open(path, O_WRONLY | O_CREAT | O_TRUNC, mode)，現在直接用 open 就好。

這個少了 e 的名字是 UNIX 最有名的手滑。Ken Thompson 被問到如果能重新設計 UNIX 會改什麼，他的回答是：「I’d spell creat with an e.」

「0 .. OPEN_MAX」 —— .. 是表示範圍的寫法，意思是「從 0 到 OPEN_MAX」。fd 的值只會落在這個區間裡。

那為什麼會有上限？因為 page-09 那張 fd table 是一個陣列，而陣列必須有大小。OPEN_MAX 就是它的長度，換句話說就是 一個 process 最多能同時開著幾個檔。

投影片的 compile-time limit 是說這個數字寫死在標頭檔的常數裡，編譯時就固定了；Virtually un-bounded for SVR4 & 4.3+BSD 則是說這兩個系統把它改成可以動態調整，實務上近乎沒有上限。現在的 Linux 屬於後者，用 ulimit -n 查得到，預設常見 1024，可以調高。

SVR4 和 4.3+BSD 是什麼

UNIX 早年分成兩大家族：SVR4 是 System V Release 4（1988），AT&T 那一支；4.3+BSD 是 Berkeley Software Distribution 4.3 版之後，柏克萊那一支。

投影片會特別標明「這兩個系統不一樣」，正是因為當年各家行為分歧——這也就是 page-03 說 POSIX 為什麼要存在的背景（細節是 Ch2 的內容）。

3. RC: Reference Count#

圖上 open file table 和 v-node table 各標了一個 RC，但兩者數的東西不同：

哪一層的 RC數的是誰會改動它

所以 close(fd) 觸發的是一串連鎖，而不是單純「把檔案關掉」：

  1. 清掉 fd table 的第 fd 格。
  2. 把它原本指的那項 open file table 的 RC 減一。沒歸零就到此為止——還有別的 fd 在用（dup、fork 來的）。
  3. 歸零才釋放那一項，並把它指的 v-node 的 RC 再減一。
  4. v-node 的 RC 也歸零，代表 沒有任何 process 還開著這個檔案，這個 v-node 就能從記憶體移除。
v-node 的 RC 歸零 ≠ 檔案從磁碟消失#

這兩件事常被混在一起，但它們是 兩個獨立的計數：

v-node 的 RC記憶體現在有幾個 process 開著它close
link count（st_nlink）磁碟上的 i-node有幾個 檔名 指著它unlink（rm 用的那個）

00沒人叫得出、也沒人拿著 → 存內容的那些磁碟 block 被標記成可用，還給檔案系統。資料到這時才真的消失

中間那一列是重點：檔案處於「沒有名字但還活著」的狀態。做得到是因為持有 fd 的 process 根本不靠檔名找檔案——fd 一路指到 v-node，跟目錄裡有沒有那個名字無關。

所以「磁碟空間釋放」指的是最後一列那件事，df 的可用空間也是那時才變多。一支 daemon 開著幾 GB 的 log 檔，你 rm 掉它空間卻沒回來，就是卡在中間那一列。ch04 page-53～54 用 df 把這個過程實際量了一遍。

這也正是前面說「檔名不在 metadata 裡」的用處：檔名住在目錄裡，i-node 只記「有幾個檔名指著我」，所以「誰還叫得出它」和「誰正在用它」本來就得分開算。

三個 SYNC：等到什麼寫進硬碟才返回#

先回想 page-08：一般的 write() 只把資料複製進 kernel 的 buffer cache 就返回，真正寫進硬碟是之後的事（delayed write）。這樣很快，但 write 返回時資料可能還不在硬碟上，這時斷電資料就沒了。

這三個旗標就是用來改掉這個行為的：開檔時加上它們，之後的 I/O 會 等資料真的寫進硬碟才返回。三者的差別在於要等哪些東西。一次 write 要寫進硬碟的其實有兩種：

  • 資料：你寫的那些 byte。
  • metadata：這次寫入順帶改到的檔案屬性（存在 i-node 裡），例如檔案大小、最後修改時間。
旗標影響要等什麼寫進硬碟才返回
O_DSYNCwrite資料，加上 讀回這些資料所需 的 metadata。例如檔案變長了，新的大小得先寫好，否則讀不到後面那段；修改時間這類不影響讀取的屬性則不等
O_SYNCwrite資料加上 所有 改到的 metadata，包括修改時間。等得最多，也最慢

差別在能做的事：目錄不能 write（只能透過 creat、unlink、rename 間接改），Linux 上也不能直接 read（要列內容得用 readdir，ch04 page-66）；但可以當 openat 的起點、fchdir 切過去、fstat 查屬性。

為什麼 open 和 openat 都存在#

open 是 Unix 一開始就有的；openat 是後來（POSIX.1-2008）才補上的，因為只能從 cwd 算相對路徑有兩個問題。

1. TOCTTOU（time-of-check-to-time-of-use）：「檢查」路徑和「使用」它之間有空檔，別的 process 可能趁機把路徑上的目錄改名或換成 symbolic link（ch01 page-55），讓你檢查的是 A、開到的卻是 B。open 每次都從頭解析整條路徑，任何一段都可能被換掉；openat 的 dirfd 是已經開好的目錄，直接指到它的 v-node，上層怎麼改都不影響。

但它只保護 dirfd 這一段：openat(dirfd, "b/c", …) 途中 b 仍可能被換，.. 和 symbolic link 也能跑出去。要真的安全，得一次只開一層、加 O_NOFOLLOW（遇到 symbolic link 就失敗），且名字不含 ..。

2. cwd 是整個 process 共用的。 同一個 process 裡的 thread 共用一個 cwd，一個 thread chdir 了，其他 thread 的相對路徑也跟著變。改用 openat，每個 thread 各自拿著自己的 dirfd，就不會互相干擾。

至於 open 為什麼沒被淘汰：舊程式都在用，而且多數時候從 cwd 算就夠了。兩者本來就是同一件事，open(path, …) 等於 openat(AT_FDCWD, path, …)；Linux 上的 open 其實也是用 openat 這個 system call 實作的。

為什麼要分 access mode#

就算你對一個檔案同時有讀和寫的權限，開檔時還是要講清楚要哪一種：

  • Integrity / Security / Privacy：process 可能只有讀權限（例如 /etc/passwd，ch01 page-22）。kernel 在 open 時就依 access mode 檢查權限（ch01 page-55 的 rwx），不合格直接失敗；之後每次 read／write 也會檢查這個 fd 當初是用什麼模式開的。只要讀卻用 O_RDWR 開，等於平白多拿了一份能搞砸檔案的權力。
  • Performance：kernel 知道你只讀，就能做 read ahead（預先把後面的 block 讀進 buffer cache，page-43）；只讀的 block 不會變 dirty，需要騰出 buffer cache 空間時直接丟掉即可，不必先寫回（buffer swapping）。

Question

想建立一個新檔，而且要又讀又寫，怎麼辦？

Answer

直接 open(pathname, O_RDWR | O_CREAT | O_TRUNC, mode)。如果只能用 creat，就得先 creat、close，再用 O_RDWR 重新 open——多兩次 system call，而且兩步之間檔案可能被別人動過（又是 TOCTTOU）。

Open File Descriptor Table 與 System Open File Table#

大部分是 page-09 的複習，只列新的重點：

Open File Descriptor Table

  • 每個 process 一張；每一格＝file descriptor flags＋指向 system open file table 的指標。
  • Child inherits from parents：fork 時整張表複製給 child（page-31）。

System Open File Table

  • 所有 process 共用，每一項記 file status flags、current file offset、指向 v-node 的指標。
  • 每一項有一個 reference count：有幾個 fd 指著它（page-15）。
  • Each open file corresponds to an entry, a disk file may be opened multiple times：一項對應的是「一次開檔」，不是「一個檔案」，所以同一個磁碟上的檔案可以同時佔好幾項（page-29、30）。

page-27#

V-node Table#

  • File = metadata + content（page-15）：v-node table 存 metadata，buffer cache 存 content。
  • 每個 開著的 檔案有一個 v-node，所有 process 共用；同一個檔案不管被開幾次都只有一項。
  • v-node 由 Peter Weinberger（Bell Labs）和 Bill Joy（Sun）發明，目的是讓一台機器同時支援多種檔案系統（page-16 的 filesystem independent／dependent 分界）。
  • Linux 沒有 v-node，用的是一個通用的 i-node；SVR4 則是把 i-node 包在 v-node 裡（或乾脆換成 v-node）。這就是為什麼這門課把 v-node table 記成 i-node table 即可（page-09 的 note）。
  • i-node 裡有：owner、file size、檔案在哪個裝置上（residing device）、內容在哪些 block。

lseek#

移動 current file offset。成功時回傳移動後的新位置，一律是 從檔頭（byte 0）算起 的 byte 數，跟 whence 無關；失敗回傳 -1。

whence新 offset
SEEK_SEToffset
SEEK_CUR目前 offset + offset
SEEK_END檔案大小 + offset

參數 offset 可以是負的，代表往前移，例如 lseek(fd, -10, SEEK_END) 移到倒數第 10 byte。但移動後的新位置不能小於 0，一般檔案會失敗（EINVAL）。

  • currpos = lseek(fd, 0, SEEK_CUR)：移動 0 byte，等於查詢目前的 offset。
  • fd 是 pipe 或 FIFO 時會失敗，errno 設成 ESPIPE（投影片寫 EPIPE，那是另一個錯誤）。原因見下方 note。
  • off_t 的大小決定檔案最大能多大：定義成 long（32 bit）時上限約 2312^{31}231 byte＝2 GB；long long（64 bit）時是 2632^{63}263 byte。
  • 例外是某些裝置允許 新位置本身 是負的。例如 SVR4 的 /dev/kmem（代表 kernel 記憶體的裝置檔）把位置當成 kernel 記憶體位址，而 kernel 位址通常在高位址，用有號的 off_t 表示就成了負數。這時成功的回傳值也可能是負的，所以判斷錯誤要寫 == -1，不能寫 < 0。（剛好停在 -1 就分不出成功或失敗；真要區分，得先把 errno 設成 0，呼叫後再看它有沒有被設。）
  • No I/O takes place until next read or write：lseek 只改 open file table 裡的那個數字，完全不碰硬碟。
pipe 與 FIFO

兩者都是讓 process 之間傳資料的通道，不是存資料的檔案。

  • pipe：就是 ch01 page-48 的 |。ls | wc -l 時 shell 呼叫 pipe()，kernel 開一塊 buffer、回傳兩個 fd（一端寫、一端讀），再把 ls 的 fd 1 接到寫端、wc 的 fd 0 接到讀端。pipe 沒有名字，只有透過 fork 繼承到這兩個 fd 的 process 用得到。
  • FIFO（named pipe）：有名字的 pipe。mkfifo myfifo 建出來後會出現在目錄裡（ls -l 的類型是 p），不相關的 process 也能靠路徑 open 它來傳資料，但資料一樣不存在磁碟上。

兩者的資料都是讀走就沒了：讀過的回不去，還沒寫進來的也跳不過去，沒有「第幾個 byte」可言，所以不能 lseek。

Example of Seeking#

指令fd 0 是什麼結果

程式本身完全一樣，只檢查 fd 0 能不能 seek，差別只在 shell 在 exec 前把 fd 0 接到什麼（page-16）：

  1. < /etc/motd：/etc/motd 是登入時顯示歡迎訊息的普通文字檔。shell open 它、放到 fd 0，所以 fd 0 是一般檔案。
  2. cat < /etc/motd | ./a.out：兩個 process。cat 的 fd 0 是 /etc/motd、fd 1 是 pipe 的寫端；a.out 的 fd 0 是 pipe 的讀端。cat 把檔案內容寫進 pipe，所以 a.out 讀到的資料跟 1 一模一樣，但因為來源是 pipe，不能 seek。
  3. < /var/spool/cron/FIFO：舊 SVR4 系統上 cron（定時執行工作的 daemon）用來接收通知的 FIFO。以讀的方式 open FIFO 時，要等到有人從寫端打開才會返回，所以這個指令可能會先卡住。

1 和 2 讀到的資料相同，卻一個能 seek、一個不能。所以從 stdin 讀資料的程式，不能假設自己可以 seek。

Delayed Write#

page-08 講過的 delayed write，這頁換成時間軸來畫：

  • write() 把 Data 交給 kernel，立刻返回；kernel 手上的那份還沒寫進 Disk。

  • 等於 block：一次 read 剛好拿走一整個 block，沒有多餘的呼叫。
  • 比 block 大：一次能拿好幾個 block，次數還會再少，但此時固定成本已經只剩零頭（上表 8192 時約 0.02 秒），再省也省不到什麼，反而多佔記憶體。

讀 103 MB 本來就要花磁碟約 6.7 秒。如果每次 read 都要停下來等磁碟，Clock 應該是 CPU 時間 + 6.7 秒，但表上不是這樣，原因是 read-ahead（page-43）：kernel 看出你在循序讀，會趁 CPU 還在處理這一批時，先把後面的 block 讀進 buffer cache。磁碟和 CPU 同時在做事，所以 Clock 大約是 兩者中比較慢的那個，而不是兩者相加：

  • buffer 小（1）：CPU 要跑 286 秒，比磁碟的 6.7 秒慢得多。CPU 每次要下一批資料時，read-ahead 早就讀好了，process 幾乎沒等過磁碟，所以 Clock ≈ CPU 時間。
  • buffer 大（≥ 64）：CPU 只要幾秒甚至零點幾秒，換成磁碟比較慢。CPU 處理完手上的資料，下一批還沒讀好，只能睡著等，等待的時間不算在 UsrCPU／SysCPU 裡，所以 Clock 停在磁碟的約 6.7 秒，跟 CPU 時間差很多。

投影片的 read-ahead 箭頭指著 buffer 64 的 6.76，就是在標這個轉折點：從這裡開始 CPU 比磁碟快，再怎麼加大 buffer，Clock 都降不下去。

page-43#

Read-ahead#

kernel 發現一個 process 在 循序 讀檔案，就會在它開口之前，先把後面的 block 讀進 buffer cache：

  • 第一次 read()：資料不在 kernel 裡，kernel 去 disk 拿。拿的時候順便把後面幾個 block 也讀進來。
  • 第二次 read()：要的資料 已經在 kernel 裡了，直接複製回去，不必等 disk。

效果是：磁碟在讀下一批資料的同時，CPU 在處理這一批，兩件事同時進行。page-19 說 O_RDONLY 能幫助 performance，指的就是這種預讀。

fork 之後讀到什麼？#

讀 code 前先補兩個函式（細節 Ch8）：

  • fork()：把目前的 process 複製一份成 child，兩邊都 從 fork() 返回的地方繼續往下跑。差別只在回傳值：child 拿到 0，parent 拿到 child 的 PID。所以 if (fork() == 0) 就是在問「我是 child 嗎？」，{ } 裡那段只有 child 會執行，而 child 在裡面 exit(0) 就結束了。
  • wait(NULL)：parent 停在這裡，等 child 結束才繼續。它是 system call：還沒有 child 結束時，kernel 讓 parent 睡著（Blocked）；child exit 時 kernel 會把它叫醒，wait 就返回。如果 child 早就結束了，wait 會立刻返回。

為什麼用 0 當記號：真正的 child PID 不會是 0（0 是 kernel 保留的），所以不會搞混；child 要知道自己或 parent 的 PID 可以另外用 getpid()、getppid() 查，parent 卻沒有別的辦法知道 child 是誰，所以 PID 回傳給 parent。

答案：c = o。

child 繼承 parent 的 fd table，兩邊的 fd 指到 同一項 open file table（page-31），共用 offset。child 讀掉 f，共用的 offset 變成 1；parent 用 wait 等 child 結束後才讀，讀到的是第二個字元 o。

wait(NULL) 確保了順序：child 一定先讀。沒有它，誰先讀就看 scheduler 怎麼排。

答案：螢幕上什麼都沒有，file1 的內容被複製到 file2。

  1. fd 0 改成指向 file1，fd 1 改成指向 file2。
  2. execve 把自己換成不帶任何參數的 cat。cat 沒拿到檔名參數時，就從 stdin 讀、寫到 stdout。
  3. exec 換掉整個 user space，但 fd table 保留（page-11），所以 cat 的 0、1 就是剛剛設好的 file1、file2。
  4. exit(0) 永遠執行不到：execve 成功就不會回來了。

這支程式就是 shell 執行 cat < file1 > file2 時，在 fork 之後的 child 裡做的事（page-16）。

page-61#

sync、fsync、fdatasync#

kernel 在應用程式和磁碟之間維護著 buffer cache（page-08）：write() 只寫到 buffer cache，之後才寫到 Disks。這三個函式讓程式主動要求寫回：

函式範圍等不等
fsync(fd)這個檔案的 資料＋屬性（metadata，例如修改時間）等寫完才返回
fdatasync(fd)這個檔案的 資料（屬性只寫讀取時需要的部分，例如檔案大小）等寫完才返回
sync()全系統 所有被改過的 blockPOSIX：排進寫回佇列就可以返回；Linux：等寫完才返回

sync() 平常由系統的 update daemon（ch01 page-23：在背景常駐的程式）定期呼叫（通常每 30 秒），也就是 page-08 說的「kernel 背景定期寫」；sync 指令（ch01 page-23 那個帳號）呼叫的也是它。

跟 open() 選項的對照#

page-17 那三個 SYNC 旗標，效果相當於每次呼叫後自動做一次這裡的函式：

open 旗標效果相當於
O_DSYNC每次 write 都等資料寫到磁碟；屬性若不影響讀取剛寫的資料就不等每次 write 後 fdatasync
O_SYNC每次 write 都等資料 和 因這次寫入而改變的屬性都寫到磁碟每次 write 後 fsync
O_RSYNC每次 read 前，要讀的那段如果有還沒寫進磁碟的內容，先把它寫進磁碟再讀，保證讀到的東西斷電也不會消失—

這三個函式只管 kernel 的 buffer cache。用 standard I/O 寫的資料，還得先 fflush 才會進到 kernel，見 ch05 page-16。

page-62～64#

O_DSYNC、O_SYNC、O_RSYNC 的時間軸#

三張圖都是 page-39 那種時間軸：左邊是 process，中間是 Kernel，右邊是 Disk。Disk 上除了 Data，還多畫了 File Info（檔案的屬性，也就是 i-node 裡的 metadata）。

旗標圖上看到的
O_DSYNC（page-62）write() 一直等到 Data’ 寫進 Disk 才返回；File Info 則是 之後 才寫過去，write 不等它。接下來的 read() 直接從 kernel 拿到資料
O_SYNC（page-63）write() 要等 Data’ 和 File Info 都寫進 Disk 才返回，等待的時間比 O_DSYNC 更長
O_RSYNC（page-64）read() 要讀的那段還有沒寫進 Disk 的內容（Data’），就先把它寫進 Disk 再返回，所以 read 之前寫入的資料斷電也不會消失

跟 page-39 的 delayed write 對照：一般的 write 是「交給 kernel 就走」，加上這些旗標後才變成「看著它落地才走」，也就是 page-20 的 synchronized I/O。

O_RSYNC 只管斷電，不管別人同時寫

先講清楚它保證什麼：呼叫 read 的當下，如果要讀的那段有「已經寫進 buffer cache、還沒寫到磁碟」的資料，read 會先把它們寫到磁碟才返回。保證的範圍只有 呼叫 read 之前 就寫進去的資料。

所以別的 process 在這段期間又寫同一段，O_RSYNC 不會擋它。例如 process A 用 O_RSYNC 開檔，process B 用一般方式開同一個檔案：

順序AB
1呼叫 read，發現要讀的資料還沒寫到磁碟，送出寫回請求，睡著等磁碟
2（睡著）write 同一段：新資料寫進 buffer cache 就返回，還沒寫到磁碟
3磁碟寫完（寫的是第 1 步時的舊資料），A 醒來，從 buffer cache 複製資料後返回

第 3 步 A 拿到的是 buffer cache 裡 B 剛寫的新資料，而這份資料還沒寫到磁碟，斷電就會消失。這不算違反 O_RSYNC，因為 B 的寫入發生在 A 呼叫 read 之後。A 一次讀的範圍很大時，甚至可能一部分是舊資料、一部分是 B 的新資料。

也就是說，O_RSYNC 處理的是「斷電後資料還在不在」，不處理「讀的時候別人能不能改」。要確保讀的時候沒人改，得用 record lock（ch14 page-19）。

Linux 上其實碰不到這個情況：Linux 沒有實作 O_RSYNC，glibc 把它定義成跟 O_SYNC 同一個值，所以只有寫入會等磁碟，read 不會先寫回。

page-65#

Linux ext2 上的計時#

用 page-41 的程式，BUFFSIZE = 4096，這次把輸出寫到真正的磁碟檔案，比較各種同步方式（ext2 是 Linux 早期的檔案系統）：

操作User CPUSystem CPUClock
只讀（輸出到 /dev/null，page-42）0.030.166.86
一般的 write 寫到磁碟檔0.020.306.87
設了 O_SYNC 的 write0.030.306.83
write 之後呼叫 fdatasync0.030.4218.28
write 之後呼叫 fsync0.030.3717.95
設了 O_SYNC 的 write，之後再呼叫 fsync0.050.4417.95

投影片標的兩點：

  1. 一般 write 的 clock 跟只讀幾乎一樣（6.87 vs. 6.86）：這就是 delayed write（page-39）。資料交給 buffer cache 就返回，寫磁碟的時間完全沒算到程式頭上。
  2. 設了 O_SYNC 卻沒有變慢：照理說每次 write 都要等磁碟，clock 應該大增。投影片的解釋是「Linux 的檔案系統沒有遵守 O_SYNC」。
投影片的解釋不太對

問題不在檔案系統，而是 O_SYNC 根本沒被設上去。這個實驗的輸出是 shell 重導向的（fd 1 由 shell 開好），程式只能事後用 set_fl(STDOUT_FILENO, O_SYNC)（page-67～68）補上；而 Linux 的 F_SETFL 會默默忽略 O_SYNC：不改、也不回傳錯誤。所以那一列其實就是一般的 delayed write。在 open 時直接給 O_SYNC，Linux 是會遵守的（APUE 第三版也改成這個解釋）。

實測（Linux 6.8）：

真的去等磁碟（fdatasync、fsync）之後，clock 變成將近三倍，但 System CPU 只多一點點。多出來的十幾秒是在等磁碟，不是 CPU 在做事——正是 ch00 page-14 說的「disk I/O 不算 CPU time」。

page-66#

fcntl#

改變一個已經開著的檔案的性質。cmd 決定要做什麼，arg 是這個 cmd 需要的額外資訊（不需要就不傳）：

cmd作用arg成功時回傳
F_DUPFD複製 fd，新 fd 是 ≥ arg 的最小可用號碼（page-52 的 dup 就是 arg = 0）。新 fd 的 FD_CLOEXEC 會被清掉，也就是 exec 之後它還會開著最小號碼新的 fd
F_GETFD／F_SETFD讀／設 fd flags，目前只有 FD_CLOEXEC（page-09）GET 不用；SET 給新的 flagsGET 回傳 flags；SET 回傳 0
F_GETFL／F_SETFL讀／設 file status flags（page-24）GET 不用；SET 給新的 flagsGET 回傳 flags；SET 回傳 0
F_GETOWN／F_SETOWN讀／設這個 fd 的 owner：誰要收到它的 SIGIO、SIGURG（見下方）SET 給 PID（正數）或 process group ID（負數）GET 回傳 owner；SET 回傳 0
F_GETLK／F_SETLK／F_SETLKWfile lock（見下方，細節 ch14 page-22）指向 struct flock 的指標，描述要鎖哪一段0

失敗一律回傳 -1。規則是：GET 系列把查到的值當回傳值給你；SET 系列（包括上鎖）只是要 kernel 改東西，沒有值要回傳，成功就回傳 0，所以只要檢查是不是 -1。

  • F_SETFL 能改的只有一部分：投影片用淺藍色標出的 O_APPEND、O_NONBLOCK、O_SYNC、O_ASYNC 可以事後打開或關掉；O_RDONLY、O_WRONLY、O_RDWR 只能讀，開檔之後就改不了。但 Linux 是例外：O_SYNC 標成可改是 POSIX 的說法，Linux 的 F_SETFL 會默默忽略它（page-65），要 O_SYNC 只能在 open 時給。

SIGIO、SIGURG 與 owner#

兩者都是 signal（kernel 送給 process 的通知，ch00 page-18）：

  • SIGIO：「這個 fd 現在可以做 I/O 了」，例如有資料可讀。要先用 F_SETFL 打開 O_ASYNC 才會送。這是 page-20 non-blocking 之外的另一種做法：不用一直去問，等 kernel 來通知。
  • SIGURG：網路連線上收到 緊急資料（TCP 的 out-of-band data，例如遠端登入時按 Ctrl-C，要插隊優先處理）。

kernel 要送 signal，得知道送給誰，這就是 F_SETOWN 設的 owner：arg 為正代表一個 process ID；為負代表一個 process group ID（一群被當成一組管理的 process，例如同一條 pipeline 裡的所有指令），整組都會收到。

file lock#

多個 process 同時讀寫同一個檔案時（例如兩個 process 同時改資料庫的同一筆紀錄），可以先 鎖住檔案的某一段，避免互相蓋掉（完整內容見 ch14 page-19～30）：

  • read lock（共享鎖）：大家都能同時讀，但上鎖期間沒人能寫。
  • write lock（獨佔鎖）：只有自己能讀寫，其他人連讀鎖都拿不到。

上鎖的請求寫在 arg 指向的 struct flock 裡：要哪一種鎖（read lock、write lock，或 F_UNLCK 解鎖），以及鎖檔案的哪一段。三個 cmd 拿這個請求做不同的事：

cmd做什麼
F_SETLK上鎖（或解鎖）。如果這段已經被別人用衝突的鎖鎖住，立刻失敗返回（errno 為 EAGAIN 或 EACCES），不等
F_SETLKW一樣是上鎖，但被擋住時 停下來等（W = wait），等對方釋放後再鎖上
F_GETLK不上鎖，只是問：「如果我要上這個鎖，有沒有人擋著？」有的話，把擋住的那個鎖的資訊（哪個 process、鎖哪一段）填回 struct flock；沒有的話，把類型改成 F_UNLCK 告訴你暢通

這種鎖是 advisory（勸告式） 的：只約束同樣有在用鎖的 process，不理鎖、直接 write 的程式照樣寫得進去（ch14 page-29）。

page-67～68#

印出一個 fd 的 file status flags#

程式的用法是 ./a.out <fd 號碼>：印出 這個 process 的那個 fd 的 file status flags。

1. 一個回傳值怎麼裝得下所有 flag#

fcntl(atoi(argv[1]), F_GETFL, 0)：atoi 把命令列參數字串（例如 "5"）轉成整數 5，再對 fd 5 做 F_GETFL。回傳的 val 是一個整數，每個 flag 佔其中一個 bit，跟 open 時用 | 組合 oflag 是同一個格式（page-17）。以 Linux 的值為例，寫成二進位（bit 從最右邊第 0 個開始數）：

（<fcntl.h> 裡這些常數是用八進位寫的，例如 O_APPEND 是 02000，換成二進位就是上面那樣。）

要問某個 flag 有沒有設，就用 & 把那個 bit 單獨取出來：val & O_APPEND 不是 0 就代表有設。

2. O_ACCMODE 是什麼#

access mode 是例外：O_RDONLY、O_WRONLY、O_RDWR 不是各佔一個 bit，而是 最低兩個 bit 一起表示的三個值（0、1、2）。O_RDONLY 是 0，val & O_RDONLY 永遠是 0，測不出來。

O_ACCMODE 是一個遮罩（mask），值是 3，也就是二進位 11，剛好蓋住這兩個 bit。val & O_ACCMODE 把其他 bit 全部清掉、只留這兩個，再用 == 比它是 0、1 還是 2。

3. #if !defined(_POSIX_SOURCE) && defined(O_SYNC)#

#if … #endif 是 編譯前 的條件判斷（preprocessor），條件不成立時，中間那段程式碼根本不會被編譯：

  • defined(O_SYNC)：系統有定義 O_SYNC 這個常數。早期不是每個系統都有。
  • !defined(_POSIX_SOURCE)：程式沒有要求「只用 POSIX 標準裡的東西」。定義了 _POSIX_SOURCE 時，標頭檔會把標準以外的名字藏起來，而 O_SYNC 當時不在 POSIX.1 裡。

兩者都成立才檢查 O_SYNC，這樣程式在哪個系統上都編得過。

4. 不是只有 0、1、2 才有意義嗎？#

程式自己沒有 open 任何東西，所以它能看的確實只有 從 shell 繼承來的 fd。重點就在這裡：這支程式是用來觀察 shell 的重導向幫你開了什麼。shell 在 fork 之後、exec 之前照指令設好 fd（page-16），重導向可以指定 任何號碼，不只 0、1、2，所以 5<>temp.foo 會讓程式一出生就有 fd 5。沒有重導向的 fd，例如直接跑 ./a.out 5，fcntl 會失敗（EBADF），印出 fcntl error for fd 5。

5. 執行結果（page-68）#

先看懂指令：參數 vs. 重導向#

以 ./a.out 2 2>>temp.foo 為例，這一行裡有兩個 2，意思完全不同：

  • 前面的 2：跟其他字之間用空格隔開，是 普通參數。shell 原封不動交給程式，變成 argv[1]，意思是「請檢查 fd 2」。
  • 後面的 2>>temp.foo：數字 緊貼 著 >>、中間沒有空格，shell 就把它當成 重導向：在 exec 程式之前，先把 fd 2 開到 temp.foo（page-16）。這部分 shell 自己處理掉，程式的 argv 裡看不到。

課本故意讓兩者一致：先用重導向設好某個 fd，再叫程式去檢查同一個 fd。如果寫成 ./a.out 5 2>>temp.foo，程式去檢查的 fd 5 根本沒開，就會出錯。

重導向的語法#

n 是要設定的 fd 號碼，緊貼在符號前面；不寫 n 時用預設值：

寫法預設 n相當於 open 用的 flags意思
n< file0O_RDONLY只讀
n> file1O_WRONLY | O_CREAT | O_TRUNC只寫，檔案原本的內容清空
n>> file1O_WRONLY | O_CREAT | O_APPEND只寫，接在檔尾
n<> file0O_RDWR | O_CREAT讀寫（是 <>，不是 ><）

所以平常寫的 ./a.out > out.txt 就是 ./a.out 1> out.txt、./a.out < in.txt 就是 ./a.out 0< in.txt。想把錯誤訊息導出去就得明寫 2> err.txt，因為預設不是 2。

逐行看#

程式會把它檢查的那個 fd 的 flags 用 printf 印到 fd 1：

  1. ./a.out 0 < /dev/tty
    • 重導向：fd 0 以只讀方式開 /dev/tty（這個 process 所在的終端機）。
    • 參數 0：程式檢查 fd 0 → read only，印到 fd 1，也就是螢幕。
  2. ./a.out 1 > temp.foo
    • 重導向：fd 1 以只寫方式開 temp.foo。
    • 參數 1：程式檢查 fd 1 → write only。但 fd 1 就是 temp.foo，這行字被寫進檔案、螢幕上什麼都沒有，所以投影片接著 cat temp.foo 才看得到。
  3. ./a.out 2 2>>temp.foo
    • 重導向：fd 2 以只寫 + 附加方式開 temp.foo。
    • 參數 2：程式檢查 fd 2 → write only, append。fd 1 沒動，還是螢幕，所以直接印出來。
  4. ./a.out 5 5<>temp.foo
    • 重導向：fd 5 以讀寫方式開 temp.foo。
    • 參數 5：程式檢查 fd 5 → read write，印到螢幕。

page-69#

打開一個或多個旗標#

先讀、再改、再寫回。不能直接 fcntl(fd, F_SETFL, flags)，那會把原本已經設好的其他旗標全部清掉。

  • 要 關掉 旗標，把中間那行改成 val &= ~flags;（課本叫它 clr_fl）。
  • 投影片的使用例 set_fl(STDOUT_FILENO, O_SYNC);：替 stdout 打開 O_SYNC，讓之後每次 write 都等資料寫進磁碟才返回（page-17）。這只在 stdout 被 重導向到檔案 時才有意義（例如 ./a.out > out.txt，page-65 的實驗就是這樣）；stdout 是終端機的話，write 根本不經過磁碟。用 set_fl 而不是在 open 時給，是因為 stdout 是 shell 開好的，程式沒機會自己 open 它。
Linux 上這個例子沒有效果

Linux 的 F_SETFL 會默默忽略 O_SYNC（page-65），所以這行在 Linux 上什麼都沒改。set_fl 本身沒問題，拿來開 O_APPEND、O_NONBLOCK 都正常有效。

page-70#

F_SETFD 和 F_SETFL 各影響哪些 fd？#

fd1、fd2 共用一項 file table（dup），fd3 自己一項（另一次 open），三者指到同一個 v-node。

對 fd1 做影響到原因
F_SETFD只有 fd1fd flags 存在 fd table 的那一格裡，每個 fd 各自一份
F_SETFLfd1 和 fd2file status flags 存在 file table 那一項，fd1、fd2 共用；fd3 是另一項，不受影響

page-71#

ioctl#

I/O 操作的萬用出口（catchall）：塞不進 read／write／lseek／fcntl 的裝置操作都丟給它，例如設定終端機視窗的大小。

request 能用哪些值要看是什麼裝置，所以可能還要 include 各類裝置自己的標頭檔：disk label 用 <disklabel.h>、磁帶用 <mtio.h>，file I/O、socket（網路連線的端點）、terminal I/O 則在 <ioctl.h>。

page-72#

/dev/fd#

/dev/fd/n 是一組特殊的檔名，打開它就等於複製 fd n（假設 n 已經開著）：

（投影片寫成 /dev/df/n，是筆誤。）

  • 給的 mode 會被忽略，或者必須是原本那個 fd 開檔模式的子集——原本只讀的 fd，不能透過它變成可寫。
  • 用途：Uniformity and Cleanliness。有些程式只接受檔名、不會讀 stdin，把 /dev/fd/0 當檔名傳給它，就能讓它讀 stdin。cat /dev/fd/0 就等於 cat。
  • 不在 POSIX.1 裡，但 SVR4 和 4.3+BSD 都支援。/dev/stdin 是指向 fd/0 的連結，/dev/stdout、/dev/stderr 同理。
Linux 上不太一樣

Linux 的 /dev/fd 是指向 /proc/self/fd 的連結。在那裡打開 /dev/fd/n 是 把 fd n 指到的那個檔案重新打開一次，會拿到一項新的 open file table、offset 從 0 開始，不是 dup。
