從鍵盤到螢幕：stdin 與 stdout 走一遍
Unit 5.5

這篇不對應投影片，是把前面幾章散在各頁的東西串成一條線：從 stdin、stdout 被打開開始，到程式用 fgets 讀進一行、再用 printf 把它印到螢幕上為止，每一步在哪裡發生、用到哪個資料結構。每一步後面都標了對應的筆記，想看細節就點過去。

讀 stdin 那段（第一到第三階段）寫得最詳細；寫 stdout（第四階段）走的路大部分一樣，所以只寫不同的地方。

情境：在終端機視窗裡打開 shell，執行 ./a.out，a.out 做的事是：

會出現的角色#

第一階段：stdin、stdout 是怎麼被打開的#

1. 終端機視窗建立 pseudo terminal#

終端機視窗不是真的硬體終端機，所以 kernel 提供了 pseudo terminal（虛擬終端機）：一對互相連通的裝置，一端叫 master，一端叫 slave。

  • 終端機視窗程式打開 /dev/ptmx，kernel 就建立一對新的 pseudo terminal，把 master 那端的 fd 交給終端機視窗程式，slave 那端則出現在檔案系統裡，名字是 /dev/pts/5。
  • 終端機視窗程式往 master 寫的東西，對 slave 那端來說就是「使用者打的字」；slave 那端被寫的東西，終端機視窗程式會從 master 讀出來，畫在視窗上。
  • 兩端中間由 tty driver 處理：input queue、echo、Backspace 這些功能，都是 tty driver 在 slave 這一側做的。

所以對之後要讀 stdin 的程式來說，/dev/pts/5 就是一個終端機，它不需要知道另一端是視窗程式。

2. open("/dev/pts/5")：kernel 在這一步就決定好之後怎麼讀#

終端機視窗程式 fork 出一個 child，child 呼叫 open("/dev/pts/5", O_RDWR)。kernel 照 ch03 page-09 最後那張表的步驟做：

  1. 查路徑：照著 /、dev、pts 一層層查目錄，找到 5 這個名字對應的 i-node（ch01 page-53）。
  2. 檢查權限：O_RDWR 要讀和寫，檢查使用者對 /dev/pts/5 有沒有 r 和 w 權限（ch01 page-55、ch03 page-19）。
  3. 看 file type：i-node 裡的 st_mode 說這是 character special file（ch04 page-08）。這種檔案沒有存在磁碟上的內容，對它 read／write 要交給某個 driver。
  4. 看是哪個裝置：i-node 裡的 st_rdev 記著裝置號碼（ch04 page-07）。/dev/pts/5 的裝置號碼是 (136, 5)：前面的 136 叫 major number，決定由哪個 driver 負責，136 就是 pseudo terminal 的 slave 端；後面的 5 叫 minor number，決定是那個 driver 管的第幾個裝置。tty driver 替每個終端機在 kernel 裡各留一份資料：自己的 input queue、output queue，以及 canonical mode 這類設定。minor number 就是用來選出「5 號終端機的那一份」。
  5. 填 v-node：kernel 把 i-node 放進 v-node table，並把 v-node 裡那組「讀寫要呼叫哪支函式」的函式指標，填成 tty driver 的函式（ch03 page-09 的 v-node 與 i-node note）。一般檔案在這裡填的是 ext4 這類 file system 的函式；裝置檔填的是 driver 的函式。上層的 read／write 程式碼完全一樣，這就是 v-node 的 virtual 的意思。
  6. 開一項 open file table：記下 flags O_RDWR、offset 設成 0（ch03 page-26）。
  7. 配 fd：在 fd table 找最小的空格，指向剛剛那一項 open file table，回傳這個號碼（ch03 page-28）。

接著 child 用 dup2 把這個 fd 複製到 fd 0、1、2（ch03 page-52），讓三個 fd 都接到 /dev/pts/5，然後 exec 成 shell。ch03 page-16 的圖把三個 fd 畫成各自 open 一次、對到三項 open file table；兩種做法最後都走到同一個 v-node，也就是同一個終端機。

重點是第 5 步：「這是終端機，讀的時候要找 tty driver」是在 open 時就決定好的，之後每次 read 都不用再判斷。

所以 /dev/pts/5 本身不裝資料，它像一張寫著「tty driver 的 5 號」的名牌。使用者打的字一直都在 kernel 裡 5 號終端機的 input queue；程式要經過這個裝置檔，是因為 kernel 得靠它知道要去 哪一個 input queue 拿。

3. shell 執行 ./a.out：fd 一路傳下來#

shell 執行指令的步驟在 ch01 page-44：

  1. shell fork 出 child。child 拿到 fd table 的複本，每一格指向跟 shell 同一項 open file table（ch03 page-31）。
  2. child exec 成 a.out。exec 換掉整個 user space，但 fd table 在 kernel space，所以留下來（ch03 page-11 的 note）。

所以 a.out 的 main 還沒執行任何一行，fd 0、1、2 就已經接著 /dev/pts/5 了（ch03 page-14、ch03 page-16）。

4. main 開始之前：C library 準備好 stdin、stdout#

C library 裡已經有三個 FILE object：stdin、stdout、stderr，分別記著 fd 0、1、2（ch05 page-04）。它們是 C library 裡的 static 變數，不是 fopen 開出來的。

這時三個 FILE object 的 stdio buffer 都還沒配置，buffer pointer 是 NULL，要等到第一次 I/O（ch05 page-13）。

第二階段：printf("$ ")#

這是 stdout 第一次做 I/O，所以 C library 先替 stdout 配 stdio buffer：

  1. C library 呼叫 fstat(1, ...) 查 fd 1 是什麼。結果是 character special file，而且是終端機，所以把 stdout 設成 line buffered（ch05 page-15 的表）。
  2. buffer 的大小用 fstat 拿到的 st_blksize，終端機是 1024 byte（ch05 page-03 的 optimal-sized I/O chunks）。C library 用 malloc 配一塊 1024 byte 的 stdio buffer。
  3. "$ " 放進 stdout 的 stdio buffer。它沒有換行，line buffered 的規則不會 flush，所以畫面上還什麼都沒有（ch05 page-08）。

第三階段：fgets(buf, 100, stdin)#

5. C library：準備 stdin 的 stdio buffer#

這也是 stdin 第一次做 I/O，C library 一樣先呼叫 fstat(0, ...)，把 stdin 設成 line buffered，配一塊 1024 byte 的 stdio buffer。

stdin 的 stdio buffer 是空的，fgets 沒有字元可以拿，C library 必須呼叫 read 向 kernel 要資料。

6. C library：read 之前先 flush stdout#

ch05 page-14 第 2 點的規則：讀輸入時如果要向 kernel 要資料，會先把所有 line buffered 的輸出 stream flush 掉。所以 C library 先呼叫 write(1, "$ ", 2)。

這次 write 走的路跟下面第 8 步的 read 一樣：fd 1 → open file table → v-node → tty driver 的 write 函式。tty driver 把 "$ " 放進 output queue，再送到 master 那端，終端機視窗程式讀到後畫在視窗上（寫的細節在第 15、16 步）。使用者這時才看到提示符號。

7. C library 呼叫 read，進入 kernel#

C library 呼叫：

第二個參數是 stdin 的 stdio buffer 本身的位址，所以 kernel 會直接把資料寫進那裡，中間沒有別的 buffer。

read 是 C library 裡的一個 wrapper function，它把 system call 編號和參數放好，執行 trap 指令（ch00 page-16 第 1～6 步）。CPU 切到 kernel mode，跳到 kernel 的固定入口，kernel 再依編號找到 read 的處理函式（ch00 page-11、ch00 page-16 第 7 步）。

8. kernel：從 fd 0 走到 tty driver#

  1. 檢查參數：fd 0 是不是這個 process 真的開著的 fd，buffer 的位址是不是在這個 process 的 user space 裡（ch00 page-16 第 8 步、ch03 page-11）。
  2. fd table：用 0 當索引，找到 fd table 的第 0 格，沿著指標走到 open file table 的那一項（ch03 page-09）。
  3. open file table：檢查 flags。O_RDWR 允許讀，可以繼續（ch03 page-19）。這一項裡的 current file offset 對終端機沒有意義，終端機沒有「第幾個 byte」，資料讀走就沒了。
  4. v-node：沿著指標走到 /dev/pts/5 的 v-node，呼叫 v-node 裡的 read 函式。第 2 步 open 時填的是 tty driver 的函式，所以這裡就進到 tty driver。tty driver 再用裝置號碼裡的 minor number 5，找到 5 號終端機的 input queue 和設定。

到這裡為止，讀終端機和讀一般檔案走的是同一段程式碼。這段程式碼不知道讀的是什麼，也不知道什麼是「一行」，它只負責找到 v-node、呼叫 v-node 裡記的那支 read 函式。要不要等、等什麼，全由那支函式決定：

v-node 接到那支 read 函式的規則
ext4（一般檔案）從 buffer cache 或磁碟拿資料，到檔尾回傳 0，不等「一行」
pipebuffer 空的、還有 writer 開著，就睡著等（ch15 page-75）
tty driver（終端機）canonical mode 下，input queue 裡沒有完整的一行，就睡著等（下一步）

差別從下一步開始：一般檔案會用 offset 和 i-node 算出 block 位置，再去 buffer cache 或磁碟拿資料（ch03 page-08）；終端機完全不經過 buffer cache。

9. tty driver：input queue 裡還沒有一行，process 睡著#

終端機處在 canonical mode，一次處理一行：input queue 裡要有完整的一行（以 \n 結尾），read 才拿得到資料（ch14 page-09）。

使用者還沒打字，input queue 是空的。tty driver 就讓 a.out 這個 process block（睡著）起來，kernel 的 scheduler 改去執行別的 process，這是一次 context switch（ch00 page-16 第 8 步、ch00 page-10）。a.out 停在 read 裡面，不會佔用 CPU。

這就是 blocking I/O（ch14 page-03、ch14 page-04）：blocking 的 read 看的是 kernel buffer（這裡是 input queue）裡有沒有可以讀的資料。有的話，有多少拿多少，馬上返回，就算比要求的少也一樣；完全沒有，process 才會被 block。終端機在 canonical mode 下，「可以讀的資料」指的是完整的一行，所以就算 input queue 裡已經有 hel 三個字元，還沒按 Enter，read 一樣會 block。原因是還沒按 Enter 的那一行還在編輯中，使用者隨時可能按 Backspace 刪掉字；tty driver 要是先把 hel 交出去，使用者再刪掉 l，程式拿走的字就收不回來了。所以 tty driver 把正在編輯的那一行扣著，按下 Enter 這一行才算定案、變成可以讀的資料。一行完成之後，就回到「有多少拿多少」：完成的行是 hi\n（3 byte）而 read 要 10 byte，就拿到 3 byte 返回；完成的行有 150 byte 而 read 只要 100 byte，剩下的 50 byte 留給下一次 read。如果 fd 0 設了 O_NONBLOCK，這裡就不會 block，read 直接回傳 -1，errno 是 EAGAIN。

這個「沒有一行就睡著」的判斷，就寫在 tty driver 的 read 函式裡，所以「進到 tty driver」跟「block 到一行打完」是同一件事。大致是這樣（示意，不是真的 kernel 程式碼）：

10. 使用者打字：字元進到 input queue#

使用者打 h：

  1. 鍵盤的 controller 發出 interrupt（硬體通知 CPU「有事要處理」的訊號），CPU 跳去執行 kernel 裡的 keyboard driver，讀出按了哪個鍵（ch00 page-19）。
  2. 這個按鍵經過桌面環境，送到目前在前景的終端機視窗程式。
  3. 終端機視窗程式把 h 寫進 master 那端。
  4. tty driver 在 slave 這一側收到 h：放進 input queue，並且 echo，把 h 複製一份送回 master，終端機視窗程式讀到後畫在視窗上，所以使用者看得到自己打的字（ch14 page-09）。

e、l、l、o 也一樣。如果使用者按 Backspace，tty driver 就從 input queue 刪掉最後一個字元。這些都在 kernel 裡發生，a.out 一直睡著，完全不知道。

11. 使用者按 Enter：tty driver 叫醒 process，把這一行複製過去#

  1. tty driver 把 \n 放進 input queue。input queue 裡現在有完整的一行 hello\n。
  2. tty driver 叫醒睡在這個終端機等待佇列上的 process，也就是卡在 read 裡的 a.out。scheduler 之後輪到 a.out 時，它從 tty driver 的 read 函式裡接著執行：回到第 9 步那個 while 再檢查一次，這次有完整的一行了，跳出迴圈。
  3. tty driver 把 hello\n 這 6 byte 從 input queue 複製到 stdin 的 stdio buffer。canonical mode 下，一次 read 最多拿一行，所以只複製 6 byte，不會等到湊滿 1024。
  4. kernel 把回傳值 6 放進暫存器，執行從 trap 返回的指令，CPU 切回 user mode，回到 C library 裡 read 的下一條指令（ch00 page-16 第 9 步）。

12. C library：fgets 從 stdio buffer 複製到 buf#

  1. C library 把 stdin 的 remaining chars 設成 6（ch05 page-04）。
  2. fgets 從 stdin 的 stdio buffer 一個個把字元複製到 buf，複製到 \n 為止，再補一個 '\0'（ch05 page-26）。buf 裡現在是 "hello\n"。
  3. fgets 回傳 buf。

這一步只是 user space 裡的記憶體複製，不進 kernel。

讀 stdin 的整理：資料一共被複製了幾次#

從 input queue 開始算，資料被複製兩次：

複製誰做的要不要進 kernel
input queue → stdin 的 stdio buffertty driver，在 read 這個 system call 裡要
stdin 的 stdio buffer → buffgets，C library 的程式碼不用

buffered I/O 省下的是第一種複製的次數（ch05 page-05～page-07）。不過讀終端機時，canonical mode 一次 read 只給一行，所以每讀一行還是要進一次 kernel；buffer 真正省到次數，是在讀檔案的時候（下面最後一種情況）。

讀 stdin 的其他情況#

再呼叫一次 fgets：上一次 read 只拿到一行，fgets 又把整行拿走了，stdin 的 stdio buffer 又是空的，所以從第 7 步再走一次。

一行比 buf 長：使用者打了 150 個字元再按 Enter。read 把 151 byte（含 \n）全部複製進 stdin 的 stdio buffer，fgets 只拿走前 99 個（ch05 page-26）。下一次 fgets 時，stdin 的 stdio buffer 裡還有剩下的 52 byte，直接從那裡拿，不呼叫 read。

使用者先打好字：a.out 還在算別的東西、還沒呼叫 fgets 時，使用者就打了 hello 並按 Enter。這一行會留在 input queue 裡等。之後 read 進到 tty driver 時，input queue 裡已經有完整的一行，tty driver 直接複製，process 不用睡著。如果使用者先打好的是兩行 aaa\n、bbb\n，input queue 裡有 8 byte，read 要的是 1024 byte，tty driver 還是只給第一行 aaa\n，回傳 4；bbb\n 留在 input queue，等下一次 read。canonical mode 下一次 read 最多一行，跟 input queue 裡有幾行無關。

別的 process 也讀這個終端機：例如 a.out 自己 fork 出 child，child 從繼承來的 fd 0 讀。child 的 fd 0 指向同一項 open file table、同一個 v-node（ch03 page-31），第 8 步一樣走到 tty driver 的 5 號終端機，第 9 步一樣等一整行。規則跟「是誰 open 的、是哪個 process 在讀」無關，因為 input queue 和 canonical mode 這些設定都屬於終端機本身，不屬於 process，也不在 open file table 裡。由此有兩個結果：

  • 兩個 process 同時在等時，讀的是同一個 input queue。一行打完只會被其中一個拿走，另一個繼續等下一行。（child 在背景、不是前景那組 process 的話，一讀終端機就會收到 SIGTTIN 被暫停，輪不到它搶。）
  • 設定是大家共用的。vim 這類程式把終端機改成 non-canonical mode，shell 讀到的也會是 non-canonical mode，所以它們結束前一定要改回來。

使用者按 Ctrl-D：在一行的開頭按 Ctrl-D，tty driver 讓 read 回傳 0。C library 看到 0，就設定 stdin 的 end-of-file flag，fgets 回傳 NULL。之後 feof(stdin) 會回傳非 0；要再讓使用者輸入，得先 clearerr(stdin)（ch05 page-23）。如果是在一行中間按 Ctrl-D，tty driver 會把目前打的字直接交給 read，不等 Enter，這時 read 拿到的資料結尾沒有 \n；fgets 沒看到 \n 會繼續呼叫 read 等下去，要再按一次 Ctrl-D 讓 read 回傳 0，fgets 才會把這段沒有 \n 的字回傳（ch05 page-26）。

stdin 換成檔案：./a.out < in.txt 時，shell 在 fork 之後、exec 之前，在 child 裡 open("in.txt") 並把它接到 fd 0（ch03 page-16 的 tip、ch03 page-59）。之後的流程有三個地方不一樣：

步驟終端機檔案
第 2 步 v-node 裡的函式tty driver 的函式ext4 這類 file system 的函式
第 5 步 stdin 的 bufferingline buffered，buffer 1024 bytefully buffered，buffer 是檔案的 st_blksize，通常 4096 byte（ch05 page-15）
第 8～11 步 kernel 怎麼拿資料等使用者按 Enter，一次最多一行用 offset 和 i-node 算出 block，從 buffer cache 拿，沒有才讀磁碟（ch03 page-08）；不用等，一次最多給滿 4096 byte；讀完 offset 往後移；讀到檔尾回傳 0

第四階段：printf("you typed: %s", buf)#

buf 裡是 "hello\n"，所以這次 printf 要印的是 "you typed: hello\n"，共 17 byte。前面的階段已經做好很多事，這裡只需要快速走過：

已經做好的事在哪一步
fd 1 接著 /dev/pts/5，v-node 的函式指標是 tty driver 的函式第 2、3 步
stdout 已經是 line buffered，1024 byte 的 stdio buffer 也配好了第二階段
stdout 的 stdio buffer 是空的，"$ " 在第 6 步已經 flush 出去第 6 步

14. kernel：從 fd 1 走到 tty driver#

跟第 7、8 步一樣：trap 進 kernel、檢查參數、用 fd 1 查 fd table、走到 open file table（O_RDWR 允許寫）、再走到 /dev/pts/5 的 v-node，呼叫 v-node 裡的 write 函式，也就是 tty driver 的 write。

15. tty driver：放進 output queue 就返回#

  1. tty driver 把 17 byte 從 stdout 的 stdio buffer 複製到 output queue（kernel buffer）。
  2. 複製的同時做換行轉換：每個 '\n' 都換成 "\r\n"。'\r' 讓游標回到行首，'\n' 讓游標往下一行，兩個都要，下一行才會從最左邊開始印。
  3. output queue 有空間，資料全部放得進去，tty driver 就讓 write 回傳 17，回到 user mode。

write 不用等字真的畫到螢幕上才返回，只要資料進了 output queue 就算完成。這跟 ch03 page-39 的 delayed write 是同一個想法：寫進 kernel buffer 就返回，之後交給 kernel 處理。

16. 終端機視窗程式把字畫出來#

tty driver 把 output queue 裡的資料送到 master 那端。終端機視窗程式從 master 讀出 "you typed: hello\r\n"，畫在視窗上。這一步跟 a.out 無關，a.out 在第 15 步就已經從 write 返回，繼續往下執行了。

資料一樣被複製兩次：buf → stdout 的 stdio buffer（第 13 步，printf 做的，不進 kernel），stdout 的 stdio buffer → output queue（第 15 步，tty driver 在 write 裡做的，要進 kernel）。

output queue 跟 input queue 的差別#

兩個都是 tty driver 的 kernel buffer，但行為很不一樣：

input queueoutput queue
資料從哪來使用者打的字（經過 master）process 用 write 寫進來

會不會等湊滿一行會：canonical mode 下，正在編輯的那一行不算可以讀的資料（第 9 步）不會：收到什麼就送什麼

讀寫終端機時，是哪一層在等換行#

讀終端機和寫終端機，資料都是以一行為單位交出去的：程式讀 stdin 時，一次 read 拿到一行；程式用 printf 寫 stdout 時，遇到 '\n' 才真的送出去。但「等到換行才把資料交出去」這件事，讀和寫是由不同層做的：

  • 讀的時候，是 kernel 的 tty driver 在等換行。 canonical mode 下，tty driver 把使用者還在編輯的字留在 input queue 裡，不交給 read；使用者按 Enter，tty driver 才把這一行交出去（第 9、11 步）。C library 不管換行：它呼叫的是 read(0, ..., 1024)，要的是 1024 byte，只拿到一行是因為 tty driver 只給一行。
  • 寫的時候，是 C library 在等換行。 stdout 接終端機時是 line buffered，printf 先把字放進 stdout 的 stdio buffer，放進 '\n' 時才呼叫 write（第 13 步）。tty driver 不管換行：write 給它幾個 byte，它就把這幾個 byte 放進 output queue、送到螢幕上，不會等 '\n'（第 15 步）。
等換行的是怎麼等不管換行的是
讀終端機kernel 的 tty driver把還沒按 Enter 的字留在 input queue，不交給 readC library：read 一次要 1024 byte
寫終端機C library把還沒遇到 '\n' 的字留在 stdout 的 stdio buffer，不呼叫 writetty driver：write 給幾個 byte 就送幾個

這也解釋了第二階段的現象：printf("$ ") 之後畫面上沒有 $ ，是因為 "$ " 還留在 user space 的 stdout stdio buffer 裡，C library 還沒呼叫 write，output queue 裡根本還沒有這兩個字元。如果程式不經過 C library，直接呼叫 write(1, "$ ", 2)，tty driver 收到就送，$ 會馬上出現在螢幕上。ch03 page-10 的 printf("A"); write(1, "B", 1); 先印出 B 再印出 A，就是這個原因。

寫 stdout 的其他情況#

output queue 滿了：程式一次印大量資料，終端機視窗程式來不及畫；或使用者按了 Ctrl-S，要 tty driver 暫停送出（按 Ctrl-Q 恢復）。這時 output queue 會被填滿，write 放不進去就 block，等 output queue 空出空間才繼續。這就是 ch14 page-04 的 flow control：寫的一方被迫配合讀的一方的速度。

stdout 換成檔案：./a.out > out.txt 時，fd 1 接的是一般檔案，有三個地方不一樣：

終端機檔案
stdout 的 bufferingline buffered，遇到 '\n' 就 flushfully buffered，stdio buffer 滿了或程式結束才 flush（ch05 page-15）
write 把資料放到哪tty driver 的 output queuebuffer cache，之後由 kernel 寫回磁碟（ch03 page-08、ch03 page-39）
'\n' 會不會轉換會轉成 "\r\n"不會，檔案裡就是 '\n'。換行轉換是 tty driver 做的，寫檔案不經過 tty driver

stderr：stderr 是 unbuffered（ch05 page-15），每次 fprintf(stderr, ...) 都直接呼叫 write，不在 stdio buffer 裡停留。之後的路跟 stdout 一樣，也是經過 fd 2 走到同一個 tty driver、同一個 output queue。

附錄：用 strace 看實際的 system call#

在 pseudo terminal 上跑上面那支程式，輸入 hello 再按 Enter，strace 列出的 system call（只留相關的幾行）：

  • fstat(1, ...)、fstat(0, ...)：第二階段和第 5 步，C library 第一次替 stdout、stdin 配 stdio buffer 前查 fd 是什麼。S_IFCHR 是 character special file，makedev(0x88, 0x5) 就是裝置號碼 (136, 5)。
  • write(1, "$ ", 2)：第 6 步，read 之前先 flush stdout。
  • read(0, ..., 1024)：第 7～11 步。要求 1024 byte，因為終端機的 stdio buffer 是 1024 byte；回傳 6，因為 canonical mode 一次只給一行。
  • write(1, "you typed: hello\n", 17)：第 13～15 步。程式寫出的只有 '\n'，"\r\n" 的轉換發生在 tty driver 裡，所以 strace 看到的還是 '\n'，回傳的也是程式要求的 17。
