page-03#

Process Control#

這章的兩個目標：

  • Process Control：process 的建立與結束（creation and termination）、換成執行另一支程式（program execution）。
  • Process Properties and Accounting：process 身上帶著哪些屬性，例如各種 ID。accounting（記帳）指 kernel 替每個 process 記下它用了多少資源，例如 CPU 時間。

Process ID（PID）：kernel 給每個 process 的編號，是一個 nonnegative unique integer（非負、唯一的整數）。唯一指的是「同一時間活著的 process 不會撞號」；process 結束後，它的 PID 之後可以被新的 process 重複使用，只是 kernel 通常會先把號碼往上用，繞一圈才回頭，避免新 process 剛好拿到一個剛死掉的 PID、被誤認成舊的那個。

有兩個 PID 是固定的：

PID是誰
0kernel 自己的 scheduler process（又叫 swapper），不對應任何磁碟上的程式
1init（現在的 Linux 多半是 systemd），開機時 kernel 建立的第一個 user process，所有其他 process 都是它的後代（ch01 page-45）

投影片舉的 tmpnam 是一個用 PID 的例子：它幫你產生一個還沒被用過的暫存檔名。不同的 process 同時呼叫它，必須拿到不同的名字，所以實作上常把 PID 放進檔名裡，因為 PID 在活著的 process 之間保證不重複。

page-04#

Process Metadata & Content#

ch03 page-15 把檔案拆成 metadata（i-node 裡的屬性）和 content（data block 裡的資料）。process 也可以這樣拆：

是什麼放在哪
Metadata：PCBkernel 用來管理這個 process 的紀錄：狀態、PID、暫存器、開了哪些檔…（page-05）kernel space
Content：Virtual Memory這個 process 自己的記憶體：text、data、bss、heap、stack（ch01 page-51、ch03 page-12）user space

PCB（Process Control Block） 是 kernel 替每個 process 維護的一筆資料結構，process 存在的期間一直都在。kernel 要對一個 process 做任何事（排程、送 signal、查它開了哪些檔），都是去查、去改它的 PCB。

PCB 放在 kernel space，因為它記著 kernel 拿來管這個 process 的資訊，不能讓 process 自己改：process 如果改得到自己的 PCB，就能把 effective user ID 改成 root、把自己的優先權調到最高，或改 page table 去讀寫別人的記憶體。這跟 fd table 的道理一樣，每個 process 各一份，但由 kernel 保管（ch03 page-11）。process 要讀 PCB 裡的資訊，例如自己的 PID，也得透過 system call 請 kernel 讀給它（page-12）。

圖上兩條黃線把 PCB 接到右邊的記憶體：program counter 指向 text 裡下一條要執行的指令，registers 裡的 stack pointer 指向 stack 的頂端。PCB 記著「執行到哪」，記憶體裡是「程式和資料本身」。

右邊記憶體的細節（投影片說 discuss later; Ch.7）ch01 page-51 已經講過。這個拆法後面一直會用到：fork 兩邊都複製（page-14），exec 只換掉 content、PCB 大部分保留（page-60）。

Process Control Block (PCB)#

PCB 裡記的資訊（Information associated with each process）：

欄位內容
Process state目前是 running、ready、waiting 等哪一種狀態（page-07）
Program counter下一條要執行的指令的位址
CPU registersprocess 不在 CPU 上時，它的暫存器內容存在這裡
CPU scheduling informationscheduler（ch00 page-10）挑人要看的東西：優先權（ch01 page-28 的 nice 值）、排在哪條 queue 上（page-10）
Memory-management information這個 process 的 page table（ch03 page-12）、記憶體範圍（圖上的 memory limits）
Accounting information用了多少 CPU 時間、PID 等等
I/O status information開了哪些檔案，也就是 fd table（ch03 page-09，圖上的 list of open files）

program counter 和 CPU registers 為什麼要存在 PCB：CPU 只有一套暫存器，同一時間只屬於正在跑的那個 process。process 被換下 CPU 時，kernel 把暫存器內容存進它的 PCB；之後輪到它時再載回來，它就能從原本停下的地方繼續，完全感覺不到中間被換下來過（page-09）。

page-07#

Process States#

process 從建立到結束會經過五種狀態：

狀態意思
New正在被建立
Running正在 CPU 上執行指令
Waiting在等某個事件發生，例如等 I/O 完成
Ready可以執行，在等 scheduler 把 CPU 分給它
Terminated已經執行完畢

ch01 page-43 的三個狀態（Ready、Running、Blocked）就是中間三個，Blocked 在這裡叫 Waiting。這頁多了頭尾兩個：New 是 kernel 還在準備 PCB 和記憶體、還不能排程的時候；Terminated 是執行完了，但 PCB 還沒被清掉的時候（page-48 的 zombie）。

page-09#

CPU Switch between Processes#

這張圖是 context switch（ch00 page-10）放慢來看，時間由上往下：

  1. process P0 在執行，P1 閒著（idle，在 ready queue 裡等）。
  2. 發生 interrupt 或 system call，CPU 進 kernel。kernel 決定換人：save state into PCB0（把 P0 的暫存器、program counter 存進 P0 的 PCB），再 reload state from PCB1（把 P1 上次存的狀態載回 CPU）。
  3. P1 開始執行，P0 改成 idle。
  4. 又一次 interrupt 或 system call，反過來：存進 PCB1、從 PCB0 載回，P0 從上次停下的地方繼續。

注意中間那段 kernel 在存、載狀態的時間，P0 和 P1 都沒在跑。這段時間是純粹的 overhead（額外成本），context switch 越頻繁，浪費掉的 CPU 時間越多。

PCB 什麼時候更新

圖上只有在換人時才 save state into PCB，但這只適用於 register 和 program counter。PCB 裡的資訊分兩類：

  • register、program counter：每執行一條指令就變，PCB 不會跟著更新。process 在 CPU 上時，最新的值只在 CPU 裡，PCB 裡的是舊值；等它離開 CPU，kernel 才存進 PCB。所以 PCB 裡的 program counter 只在 process 不在 CPU 上時才有意義。
  • 其他資訊（fd table、狀態、pending signal、CPU 時間、exit status）：這些只能由 kernel 改變（PCB 在 kernel space，page-04），kernel 改的當下就直接寫進 PCB，不用等 context switch。例如 open 時 kernel 馬上在 fd table 填上新的一格；read 要等磁碟時，kernel 馬上把狀態改成 waiting。

程式裡變數的值不在 PCB 裡，它們在 process 自己的記憶體（page-04 的 content），改變數不會動到 PCB。

page-10#

Process Scheduling Queues#

page-08 的狀態圖說 process 會在 ready、running、waiting 之間轉換。這頁回答：kernel 怎麼記住「現在哪些 process 是 ready、哪些在等磁碟」？答案是用幾條 queue 把 PCB 分類。

queue 是什麼#

這裡的 queue 是 kernel 裡真正存在的資料結構：一條串著 PCB 的 linked list（page-11 的圖）。「process 在某條 queue 上」的意思是它的 PCB 被串在那條 list 裡。process 本身不會移動，它的記憶體和 PCB 都留在原地，kernel 只是改 PCB 裡的指標，把它從一條 list 拆下來、接到另一條。

queue header 和 PCB 都放在 RAM 的 kernel space（page-05），不在 CPU 上。CPU 上只有正在執行的那個 process 的 register；scheduler 要換人時，去記憶體讀 ready queue，挑出下一個 PCB，再把它存的 register 載進 CPU（page-09）。多核心的機器上，Linux 替每顆 CPU 各維護一條 ready queue，每顆 CPU 只從自己那條挑 process，但這些 queue 一樣放在記憶體裡。

三種 queue#

queue裡面是成員什麼時候變
Job queue系統裡所有的 process只在 process 建立（fork）和被徹底清掉（parent wait 回收 zombie 之後，page-48）時改變
Ready queue已經在主記憶體裡、可以執行、在等 CPU 的 process一直在變：被挑上 CPU 就離開，被換下來或等到事件就回來
Device queues在等某個 I/O 裝置的 process，每個裝置各一條一直在變：開始等就加入，等到了就離開

Processes migrate among the various queues：process 的狀態一改變，kernel 就把它的 PCB 從一條 queue 移到另一條。例如 process 在 CPU 上呼叫 read 要等磁碟，kernel 把它的 PCB 接到磁碟的 device queue，再從 ready queue 挑別的 process 上 CPU；磁碟資料讀好後，再把它的 PCB 移回 ready queue。這就是 page-08 那些箭頭在資料結構上的樣子。正在 CPU 上跑的那個 process，既不在 ready queue 也不在 device queue 上。

ch01 page-29～43 的 event queue，拆開來就是這裡的 device queues：kernel 替每個被等的對象各掛一條。

job queue 的用途#

job queue 跟另外兩種不一樣：process 不會在它上面流動，也不是在排隊等什麼。它是一份 所有 process 的名單，讓 kernel 需要掃過全部 process 時有地方找。光靠 ready queue 和 device queue 做不到，因為正在 CPU 上跑的 process 和 zombie 不在任何一條上。需要掃全部的情況例如：

  • ps 列出所有 process。
  • 一個 process 結束時，kernel 要找出它所有的 child，改由 init（PID 1）當它們的 parent。例如 process A 有兩個 child B 和 C，A 先結束了：
    • B 結束後，要由 B 的 parent 呼叫 wait，kernel 才會清掉 B 最後留下的紀錄（page-48）。B 的 parent 是 A，但 A 已經結束，不可能再呼叫 wait。所以 kernel 把 B 和 C 的 parent 改成 init，因為 init 只要有 child 結束就一定會呼叫 wait。
    • kernel 要找出 B 和 C，只能掃過所有 process 的 PCB，看哪些 PCB 的 parent 欄位是 A 的 PID。原因是每個 PCB 只記著自己的 parent 是誰（page-06 的 p_ppid），A 的 PCB 沒有記著 A 有哪些 child。
  • 送 signal 給整個 process group 時，要找出 group 裡每個成員（page-43）。

所以一個 PCB 會同時掛在兩條 list 上：一定在 job queue 上，另外可能在 ready queue 或某條 device queue 上。PCB 裡有兩組指標欄位，分別給這兩條 list 用。

取得 Process 的 ID#

What’s a fork()#

左邊是 parent，右邊是 child，兩邊是 同一份程式碼：

黃色箭頭標出各自執行到哪：

  • parent 呼叫 fork()，kernel 把 parent 的 PCB 和 VM（virtual memory）各複製一份給 child。
  • child 不是從 main 開始跑，而是跟 parent 一樣 從 fork() 返回的地方 接著跑。child 的記憶體是 parent 的複本，program counter 也是複本，所以它「醒來」的位置就是 fork() 剛返回的那一刻。
  • 兩邊唯一的差別是 fork() 的回傳值：child 拿到 0，所以進 if；parent 拿到 child 的 PID（大於 0），所以進 else。

fork 複製了哪些東西#

圖上畫的「PCB 和 VM 各複製一份」，精確地說是：fork 會複製 parent 所有 per-process（每個 process 各一份）的東西，包括 user space 的全部，以及 kernel space 裡屬於這個 process 的資料結構。kernel 只有一份、所有 process 共用（ch03 page-12），所以 kernel space 裡全系統共用的部分不會被複製。

包含fork 時
user space 的全部data、bss、heap、stack；standard I/O 的 FILE object 和它的 buffer 也在這裡複製（實際上用 copy-on-write，page-16～17）。唯一的例外是 text，它是唯讀的，兩邊直接共用（page-15）
kernel space 裡 per-process 的資料結構PCB、fd table、page table複製
kernel space 裡全系統共用的資料結構open file table、v-node table、buffer cache不複製，child 直接跟 parent 共用（page-20）

投影片的兩句結論：

  • Child is an exact copy of the parent process. 變數、heap、stack、開著的 fd，全部都是一樣的。
  • They have their own memory space. 複製完之後就各過各的：child 改了某個變數，parent 看不到，反過來也一樣（page-18～19 的實驗）。

page-15#

fork#

  • The only way beside the bootstrap process to create a new process：除了開機時 kernel 自己建的那幾個（page-03 的 PID 0、1，bootstrap 指開機的過程），所有 process 都是 fork 出來的。

  • Call once but return twice：呼叫一次，返回兩次，一次在 parent、一次在 child：

    • child 拿到 0。child 要知道 parent 是誰，可以呼叫 getppid()，所以不需要在回傳值裡給。
    • parent 拿到 child 的 PID。一個 parent 可以有很多 child（1），而且沒有函式能查「我的 child 有哪些」，所以 fork 必須當場告訴 parent 這次生出來的是誰，parent 之後才能 waitpid 它（page-43）。
    • 失敗時只返回一次，在 parent，回傳 -1，沒有 child 被建立（page-25）。

  • Cannot predict which process runs first：fork 是 parent 呼叫的 system call，執行期間 CPU 上一直是 parent（在 kernel mode）。kernel 建好 child 的 PCB 後，把 child 放進 ready queue，再讓 parent 從 fork 返回。之後誰先跑，看 scheduler 怎麼決定：

    • scheduler 讓 child 先跑，或 parent 的 time slice 剛好用完：parent 從 running 回到 ready，child 被挑上 CPU。
    • parent 接著呼叫 wait 這類要等的 system call：parent 進入 waiting，讓出 CPU 給 child。
    • 都沒有發生：parent 繼續跑，child 在 ready queue 等。
    • 多核心時，child 可能被另一顆 CPU 挑走，兩邊同時執行。

    程式沒辦法知道會是哪一種。程式的結果如果依賴誰先跑，就是 race condition（page-53）。

  • Copies of almost everything but no sharing of memory, except text：child 拿到 parent 記憶體的複本，兩邊不共用記憶體。唯一的例外是 text（程式碼）：text 是唯讀的，誰都不會改它，所以兩邊直接共用同一份，不用複製。

  • Copy-on-write：其他部分其實也沒有真的立刻複製，見下兩頁。

page-16～17#

Copy-on-Write#

fork 如果真的把 parent 的整個記憶體複製一份，parent 用了 1 GB，fork 就要搬 1 GB。更浪費的是 page-25 那種用法：child 一出生就 exec 換成別的程式，剛複製好的記憶體立刻被丟掉。

copy-on-write（COW，寫入時才複製） 的做法是：fork 時先不複製，parent 和 child 共用同一份記憶體；等到其中一方要寫某一塊時，kernel 才把那一塊複製成一份新的給寫的那一方，這次寫入寫進新的那份，原本那份維持不變，留給另一方繼續用。讀不會觸發複製。這要靠 virtual memory（ch03 page-12）：每個 process 的記憶體是透過 page table 對應到 physical memory 的 frame。

page-16，Before Process 1 Modifies Page C：fork 時，kernel 只複製 parent 的 page table，不複製記憶體內容。所以 process1（parent）和 process2（child）的 page table 指向 physical memory 裡 同一組 page A、B、C。kernel 同時把這些 page 在兩邊都標成 唯讀。

page-17，After Process 1 Modifies Page C：process1 要寫 page C 時，因為 page 被標成唯讀，CPU 產生一個 page fault（存取違反 page table 設定時，CPU 交給 kernel 處理的例外）。kernel 發現這是 COW 的 page，就：

  1. 配一個新的 frame，把 page C 的內容複製過去（圖上的 Copy of page C）。
  2. 把 process1 的 page table 改成指向這份複本，並恢復成可寫。
  3. 回到 process1，讓那條寫入指令重新執行。

page A、B 沒人寫，就一直共用下去。結果是：只有被寫到的 page 才真的被複製，fork 本身只要複製 page table，快很多。對程式來說行為跟「全部複製」完全一樣，兩邊還是看不到對方的修改：複製之後，page C 的 virtual address 沒變，變的只是 process1 的 page table 把它對應到另一個 frame。所以 fork 之後 parent 和 child 印出同一個變數的位址會一樣，值卻可以不同。

投影片寫 Mapping: discussed later (Ch. 7)，page table 怎麼對應的細節在 Ch7。

有了 COW，fork 實際上做了什麼

page-14 說 fork 會複製所有 per-process 的東西，但有了 COW，真正當場複製的只有 kernel 裡的資料結構，content 是之後才按需要複製：

fork 當下
content（user space 的記憶體）不複製，兩邊共用同一組 frame，有人寫才複製被寫的那一頁
PCB新配一個給 child，內容從 parent 複製，PID、PPID 等欄位改成 child 自己的（page-24）
fd table新開一張，內容是 parent 的複本
page table新開一張，內容是 parent 的複本；可寫的 page 在兩邊（包括 parent 自己那張）都改成唯讀

vfork 連 page table 都不開新的，child 直接用 parent 那張；PCB 還是要新配一個，因為 child 是另一個 process。所以在 COW 之下，fork 和 vfork 的成本只差在複製 page table（page-26）。

fork：File sharing#

fork 會複製 parent 的 fd table（ch03 page-31）。圖上 parent 和 child 的 fd 0、1、2 指向 同一組 file table 項，所以兩邊 共用 file offset，包括 stdin、stdout、stderr。

回到 page-18～19 導到檔案的例子：parent 和 child 的 fd 1 共用同一項 file table。child 先寫完它的輸出，offset 往後移；parent 再寫時，從 child 寫完的地方接著寫，不會把 child 的輸出蓋掉。如果兩邊各有自己的 offset，parent 會從檔案開頭寫起，把 child 的輸出覆蓋掉。

fork 之後 fd 的常見處理方式有兩種：

  1. parent 等 child 結束：parent 什麼都不用做，child 寫完之後 offset 已經更新好，parent 接著用就好。
  2. parent 和 child 各做各的：兩邊各自 close 自己不需要的 fd，避免互相干擾。network server 常這樣做（page-25）。

page-24#

fork：常見用法與繼承的屬性#

Normal cases in fork：

  • The parent waits for the child to complete：parent 呼叫 wait 等 child 結束，例如 shell 跑前景指令（ch01 page-44）。
  • The parent and child each go their own way：parent 不等，兩邊各做各的。例如 network server：parent 負責接新連線，每來一個就 fork 一個 child 去服務它（ch16）。

Inherited properties：child 從 parent 繼承這些屬性，因為 PCB 是複製來的。幾個之前沒出現過的先說明：

  • signal（Ch10）：kernel 送給 process 的一種非同步通知，例如按 Ctrl-C 產生的 SIGINT、除以零產生的 SIGFPE。process 收到後要做某個動作，預設多半是結束。
  • resource limit：每個 process 能用多少資源的上限，例如最多開幾個檔、stack 最大多大。shell 的內建指令 ulimit 用來查看和設定它，ulimit -a 會列出目前所有的 resource limit。

表上還有 process group、session、controlling terminal，這三個是一起運作的，要從 shell 怎麼管理指令講起。

在終端機裡你可以同時跑好幾件事：一件在前景，幾件用 & 或 Ctrl-Z 丟到背景。shell 管理的單位叫 job，就是你打的一整行指令。例如 ls | wc 是一個 job，裡面有 ls、wc 兩個 process。kernel 用兩層分組來支援 job：

  • process group：一個 job 在 kernel 裡就是一個 process group。shell 每跑一個 job，就替它開一個新的 group，把 job 裡的 process 都放進去。之後 shell 要對整個 job 做事，例如送 signal 或用 waitpid 等它（page-43），指定一個 group 就涵蓋全部，不用一個個記 PID。
    • 每個 group 有一個 process group ID（PGID），值就是組裡某個 process 的 PID，那個 process 叫 group leader，通常是建立這組的那一個。所以 ls | wc 的 PGID 就是 ls 的 PID。
    • fork 出來的 child 預設跟 parent 同一組，shell 要另外把它移到新的 group（Ch9）。
  • session：一個終端機裡所有的 job，也就是那裡的 shell 加上它跑出來的所有 process group，合起來是一個 session。通常一次登入、或開一個終端機視窗就是一個 session。每個 session 有一個 session ID。
  • controlling terminal：session 連接的那個終端機。一個 session 只連一個終端機，一個終端機也只屬於一個 session。

一個 session 裡有好幾個 process group，終端機會記住其中 剛好一個 是 前景（foreground）process group，其他都是 背景（background）。前景和背景的差別在終端機：

  • 在終端機按 Ctrl-C、Ctrl-Z，kernel 只把 signal 送給前景那一組。
  • 只有前景那一組能讀終端機的輸入。背景的 job 去讀的話會被暫停。

原則是 能繼承就繼承：fork 本來就是照抄一份 PCB，只有不得不改的才改。不得不改的有兩種：

  • 本來就必須不一樣：fork 的回傳值、PID、PPID。這些一樣的話就分不出誰是 parent、誰是 child。CPU 時間也算這種：它記的是這個 process 自己用掉多少，child 才剛出生，還沒用過。
  • 記的是「某一個 process」的東西：file lock 記的是「哪個 process 鎖住了這段檔案」，alarm 和 pending signal 記的是「要送給哪個 process」。child 跟 parent 是不同的 process，這些東西登記在 parent 名下，跟 child 無關。如果照抄，就變成兩個 process 同時持有同一把鎖，lock 就失去意義了。

page-25#

fork：失敗的原因與用途#

Reasons for fork to fail：

  • Too many processes in the system：整個系統的 process 數量到了上限。
  • The total number of processes for the real uid exceeds the limit：同一個 real user ID 同時擁有的 process 數到了上限 CHILD_MAX，可以用 sysconf(_SC_CHILD_MAX) 查（ch04 page-37）。這個限制是為了不讓一個使用者用無限 fork 拖垮整台機器。

Usages of fork：

  • Duplicate a process to run different sections of code：parent 和 child 跑同一支程式的不同段落，例如 network server 的 parent 接連線、child 處理連線。
  • Want to run a different program：child 一出生就 exec 換成別的程式，例如 shell。其他作業系統把這兩步合成一個呼叫，叫 spawn，所以投影片寫 spawn = fork + exec。為什麼 UNIX 要拆成兩步，見 page-70。

page-26#

vfork：設計目標#

Design objective：

  • An optimization on performance：專門為「fork 完馬上 exec」這種用法做的優化。
    • No fully copying of the parent’s address space into the child：反正 child 馬上要 exec，複製來的記憶體一下就丟掉，乾脆不複製。
    • Sharing of address space：child 直接使用 parent 的 address space。

address space（位址空間）指一個 process 能用的那一整段 virtual address，以及每個位址對應到哪塊實體記憶體，也就是 page-04 右邊那張 text、data、heap、stack 的圖，由這個 process 的 page table 記著（ch03 page-12）。每個 process 平常各有一個自己的 address space，所以同一個位址在兩個 process 裡指到不同的資料。

fork 會替 child 建一個新的 address space，內容是 parent 的複本（page-14）；vfork 不建，child 直接用 parent 那一個，兩邊連 page table 都是同一張。所以 child 存取某個變數的位址，碰到的就是 parent 的那個變數本身，不是複本。

可以共用，是因為 exec 本來就會讓 child 改用一張新的 page table（page-60），先複製也是白做；parent 那張不受影響。前提是 child 在 exec 前不碰任何變數，否則改到的就是 parent 的（page-28），所以 child 只能呼叫 exec 或 _exit。

  • Execute exec() right after returns from fork()：前提是 child 一返回就 exec（或 exit），中間不做別的事。

Mechanism – SVR4 & 4.3+BSD：Since 4BSD，vfork 是 BSD 發明的，那時還沒有 copy-on-write（page-16～17），fork 真的會整個複製，所以很慢。一些系統要 include <vfork.h>。

現在 fork 有了 COW，vfork 能省的只剩複製 page table 那一點，差距小很多。

page-27#

vfork 跟 fork 的差別#

vfork() 跟 fork() 一樣，除了兩點：

  • The child runs in the address space of its parent：child 用的是 parent 的記憶體，不是複本。child 改了變數，parent 會看到。
  • The parent waits until the child calls exit() or exec()：parent 會被暫停，直到 child 呼叫 exec 或 exit。也就是說，parent 這邊的 vfork() 要等到那時候才會返回。
    • Child process always executes first：所以 child 一定先跑。這點跟 fork 不一樣，fork 之後誰先跑不確定。
    • A possibility of deadlock if the child waits for the parent to do something before calling exec()：如果 child 在 exec 之前等 parent 做某件事，parent 卻還卡在 vfork() 裡等 child exec，根本執行不到那件事，兩邊就會永遠卡住（page-31～32）。

parent 為什麼一定要暫停：兩邊共用同一份記憶體，包括同一個 stack。如果兩邊同時跑，child 呼叫函式、改區域變數時，會直接改壞 parent 的 stack。

page-31～32#

Deadlock#

Deadlock（死結）：兩個以上互相競爭的動作，都在等對方先完成，結果誰都完成不了。

圖上的例子：P1 持有資源 R1、在等 R2；P2 持有 R2、在等 R1。兩邊都不會放手，就永遠卡住。

上課講的例子把資源換成 檔案某一段的 write lock。process 可以用 fcntl 鎖住檔案的某一段 byte，write lock 是獨占的：某個 process 拿著某一段的 write lock 時，別的 process 再來要這一段的 lock 就會被 block，等到前一個放掉為止（ch14 page-21）。「P1 跟 P2 要 write lock」的意思是 P1 去要 P2 已經鎖住的那一段，所以要等 P2 放手：

時間P1P2
1鎖住 byte 0（write lock）
2鎖住 byte 1（write lock）
3要 byte 1 的 write lock：P2 拿著，P1 被 block
4要 byte 0 的 write lock：P1 拿著，P2 被 block

到第 4 步，P1 在等 P2 放掉 byte 1，但 P2 要先拿到 byte 0 才會往下做、放掉 byte 1；P2 在等 P1 放掉 byte 0，但 P1 也卡住了，不會放。兩邊互等，就是 deadlock。

實際上 kernel 會檢查 record lock 有沒有形成這種互等。發現第 4 步會造成 deadlock 時，它不讓 P2 睡下去，而是讓 P2 的 fcntl 直接失敗，回傳 EDEADLK（ch14 page-22）。P2 收到這個錯誤後，可以放掉自己的鎖再重試。

page-32 用 vfork 做出一個 deadlock：

紅圈標的兩行：

  • child 在 while (var < 100); 空轉，等 var 變成 100。它要等到這件事發生才會 _exit。
  • parent 要執行 var = 100; 才能讓 child 跳出迴圈。但 vfork 規定 parent 要等 child exit 或 exec 之後才能繼續（page-27），所以 parent 一直被暫停，永遠執行不到這一行。

child 等 parent 改 var，parent 等 child 結束，就是 page-27 說的 deadlock。如果把 vfork 換成 fork 也不行：parent 改的是自己那份 var，child 永遠看不到，child 一樣會一直空轉。

page-34#

Process Termination（Ch7.3）#

process 有八種結束方式。

Normal termination（正常結束）：

  1. Return from main()：main 執行 return。它等於 exit(main(argc, argv));：呼叫 main 的那段程式會拿 main 的回傳值去呼叫 exit（page-35）。
  2. Call exit()。
  3. Call _exit() or _Exit()。
  4. Return of the last thread from its start routine。
  5. Calling pthread_exit from the last thread。

4、5 跟 thread（執行緒，Ch11）有關：一個 process 裡可以有好幾條各自執行的 thread，共用同一份記憶體；每條 thread 從一個指定的函式（start routine）開始跑。最後一條 thread 結束時，process 就跟著結束。

Abnormal termination（異常結束，Chapter 10）：

  1. Call abort()：它會送 SIGABRT 這個 signal 給自己。
  2. Be terminated by a signal：收到某個 signal，而那個 signal 的預設動作是結束 process，例如 Ctrl-C 的 SIGINT、除以零的 SIGFPE、存取不合法記憶體的 SIGSEGV。
  3. Response of the last thread to a cancellation request：最後一條 thread 被另一條 thread 用 pthread_cancel 要求取消。

不管是哪一種，最後都會走到 kernel 裡同一段程式碼：關掉所有開著的 fd、釋放記憶體等等（完整步驟在 page-36）。差別在於 parent 之後能拿到什麼：正常結束時拿到 exit status，異常結束時拿到「被哪個 signal 殺掉」（page-41）。

page-35#

How a C program is started and terminated#

這張圖把 C 程式從開始到結束的路徑畫出來，虛線框是 user process，最下面是 kernel：

開始：kernel 執行一支程式（exec）時，第一個跑的不是 main，而是 C start-up routine：編譯器在 link 時自動加進每個執行檔的一小段程式碼。它準備好 argc、argv、環境變數，然後呼叫 main，等 main return 之後拿回傳值去呼叫 exit。這就是 page-34 那行 exit(main(argc, argv));。

結束：圖右邊的 exit handler 是程式結束前要自動執行的清理函式，例如把暫存檔刪掉、把還沒存的設定寫回檔案。程式用 atexit(func) 把函式 func 登記起來，之後程式呼叫 exit 時，exit 會把登記過的函式一個一個叫起來執行。這樣不管程式從哪裡結束，清理工作都不會漏掉，不必在每個結束的地方各寫一次（細節在 page-37）。

page-36#

exit、_exit、_Exit#

exit 會先做 cleanup processing：

  • Call exit handlers：呼叫 atexit 登記的函式（page-37）。
  • Close and flush I/O streams (fclose)：對每個開著的 stream 做 fclose，stdio buffer 裡還沒送出去的資料會被寫出去。
  • Called once, never returns：exit 不會返回。
  • Puts the process into “zombie” status：process 結束後先變成 zombie，等 parent 來 wait（page-48）。這點三個函式都一樣。

_exit 和 _Exit 不做 cleanup，直接進 kernel。兩者效果一樣，只是一個由 POSIX.1 定義、一個由 ANSI C 定義。

_exit 進 kernel 之後做的事#

不管 process 怎麼結束（page-34 的八種），最後都會進到 kernel 裡同一段程式碼。exit 也是做完 cleanup 之後呼叫 _exit 才進來的。kernel 依序做這些事：

  1. 關掉所有 fd：fd table 裡每個開著的 fd 都 close。open file table entry 的 count 減 1，減到 0 就釋放；這個 process 持有的 record lock 也一起放掉。
  2. 放掉記憶體：address space 的 count 減 1，減到 0 才真的收回 page table 和 frame。vfork 的 child 跟 parent 共用 address space，child 結束只會減 1，parent 那邊沒事。
  3. 清掉其他屬於這個 process 的東西：例如還沒響的 alarm（page-24），以及接上來的 shared memory 會解除連接。
  4. 安置自己的 child：還活著或已經是 zombie 的 child，都改由 init 當 parent（page-48）。
  5. 留下一小部分 PCB，變成 zombie：PID、termination status（exit status 包在裡面，page-40）、用掉的 CPU 時間要留給 parent wait 拿，PCB 其他部分都釋放。
  6. 通知 parent：送 SIGCHLD 給 parent；parent 如果正卡在 wait，就把它叫醒，放回 ready queue。
  7. 換別的 process 上 CPU：這個 process 不會再被排上 CPU，所以 _exit 不會返回。

這些都是 kernel 自己記的資源，所以不管用 exit 還是 _exit，kernel 裡都不會有殘留。kernel 不知道 user space 有 stdio buffer 這種東西，所以 _exit 唯一少做的就是 user space 那段：exit handler 和 stdio flush。stdio buffer 在 user space，第 2 步記憶體被收回時就跟著消失，還沒 flush 的資料就遺失了。

Exit status：main 的回傳值#

三個函式的參數 status 叫 exit status：程式結束時交給 parent 的一個整數，表示這次執行的結果。parent 之後可以用 wait 拿到它（page-40）；在 shell 裡，上一個指令的 exit status 存在變數 $?。習慣上 0 代表成功，非 0 代表失敗，不同的非 0 值可以代表不同的錯誤。shell 的 &&、if 就是看這個值決定要不要往下做，例如 make && ./a.out 只有在 make 回傳 0 時才執行 ./a.out。

main 的回傳型別是 int，因為它的回傳值就是 exit status。page-35 說過，C start-up routine 會拿 main 的回傳值去呼叫 exit，所以在 main 裡：

寫法效果

exit(3);直接呼叫 exit(3)

兩者在 main 裡結果一樣。差別在其他函式裡：return 只是回到呼叫它的函式，程式繼續跑；exit 不管在哪一層函式呼叫，都會直接結束整個程式。所以程式在深層的函式裡發現錯誤、想馬上結束時，用的是 exit（APUE 的 err_sys 就是這樣）。

那如果程式沒有明確給 exit status，parent 會拿到什麼？投影片列了幾種情況：

「不確定」的原因：main 的回傳值是放在一個固定的暫存器裡交給 C start-up routine 的（x86-64 是 rax）。main 沒有回傳值的話，就沒有人把值放進那個暫存器，C start-up routine 讀到的是裡面剛好留著的東西，例如最後一次呼叫的 printf 的回傳值。投影片還寫了 exit 沒給值的情況，那是沒有函式原型的舊式 C 才寫得出來，現在的 compiler 會直接報錯。

所以 main 要宣告成 int，結束時明確 return 或 exit 一個值。

  • main 沒有 return，執行到最後一個 } 就結束。照 C99 的規定 exit status 是 0，所以 echo $? 印出 0。

page-37#

atexit#

atexit 用來登記 exit handler（page-35）。「登記」的意思是：呼叫 atexit(func) 的當下 不會執行 func，C library 只是把 func 的位址記進一份清單。等到之後程式呼叫 exit，exit 才照這份清單把登記過的函式一個一個呼叫。

參數型別 void (*func)(void) 是一個函式指標，指向「不收參數、不回傳值」的函式。傳的時候直接寫函式名稱、不加括號，例如 atexit(cleanup)：加了括號就變成當場呼叫 cleanup。成功回傳 0，失敗回傳非 0。

  • At least 32 functions：ANSI C 規定至少能登記 32 個，SVR4 和 4.3+BSD 都支援。
  • The same exit functions can be registered for several times：同一個函式登記幾次，就會被呼叫幾次。
  • Called in reverse order of their registration：呼叫順序跟登記順序相反，最後登記的最先呼叫。這樣後面初始化的東西會先被清理，跟初始化的順序剛好倒過來。
  • Cleared if exec() is called：exec 之後，之前登記的 handler 全部失效。handler 是舊程式裡的函式，exec 把舊程式的 text 整個換掉了，那些函式已經不存在（ch03 page-11 的 note）。
  • fork 的 child 會繼承：這份清單存在 user space，fork 複製 user space 時跟著複製。所以 child 呼叫 exit 時，parent 登記的 handler 也會在 child 裡跑一次。

只有 exit（包括 main return）會呼叫 exit handler；_exit、_Exit 和被 signal 殺掉都不會。

page-40#

wait 與 waitpid#

Called by the parent process to retrieve the termination status of its child process：parent 用它們取得 child 的 termination status（結束狀態）。

termination status 跟 page-36 的 exit status 不一樣：exit status 是 child 傳給 exit 的那個數字；termination status 是 kernel 交給 parent 的一個 int，記著 child 是怎麼結束的。正常結束時，exit status 被包在裡面；被 signal 殺掉時沒有 exit status，裡面記的是哪個 signal（page-41）。

statloc 是一個指標，kernel 把 termination status 寫進它指的那個 int。不在乎結果就傳 NULL。回傳值是結束的那個 child 的 PID。

wait 進到 kernel 之後做的事：

  1. 只看自己的 child：kernel 檢查呼叫者的 child 裡，有沒有已經結束、但還沒被 wait 過的。這種 child 叫 zombie（page-48）：程式已經不跑了，但 kernel 還留著它的一筆紀錄（PID、termination status），等 parent 來拿。
  2. 有的話：把 termination status 交給 parent，然後 回收（reap） 它，也就是刪掉那筆紀錄。child 這時才真正消失，之後再 wait 也找不到它。
  3. 沒有的話：還有 child 在跑就睡著等；一個 child 都沒有就立刻回傳 -1，errno 設成 ECHILD。

所以 wait 其實做兩件事：拿 status 和 回收。WNOWAIT（page-45）就是只拿 status、不回收，zombie 還在，所以之後還能再 wait 它一次。

兩者的差別：

  • wait will block until one child terminates or an error could be returned：等任何一個 child 結束，沒有就一直等。
  • waitpid could wait for a specific one and has an option not to be blocked：waitpid 比 wait 多兩個功能：
    • 指定等哪一個 child：wait 只要任何一個 child 結束就返回；waitpid 可以用第一個參數指定只等某個 PID 的 child（page-43）。
    • 不被 block：加上 WNOHANG 這個 option（page-45），waitpid 就不再「等」，而是「檢查一下」：指定的 child 如果已經結束了，就回收它、回傳它的 PID 和 termination status，跟一般的 waitpid 一樣；如果還沒結束，就 立刻回傳 0，不讓 parent 睡著。parent 可以先去做別的事，之後再回來檢查一次。

SIGCHLD from the kernel if a child terminates：child 結束時，kernel 會送一個 SIGCHLD signal 給 parent（投影片寫成 SIGCHILD，正式名稱是 SIGCHLD）。這個 signal 的 default action is ignoring：parent 沒有特別設定的話，收到它什麼事都不會發生。

parent 可以替 SIGCHLD 設一個 signal handler：收到某個 signal 時要執行的函式，用 signal(SIGCHLD, handler) 登記。跟 atexit（page-37）一樣，登記的當下不會執行，之後每當 SIGCHLD 送到，kernel 會讓 parent 暫停手上正在做的事，跳去執行 handler，執行完再回到原本的地方繼續。parent 不需要寫迴圈去檢查，通知是 kernel 主動送來的。

handler 被叫起來時，一定有 child 已經結束了，這時才呼叫 waitpid，所以不會 block。用 while 加 WNOHANG（page-45），是因為好幾個 child 幾乎同時結束時，parent 可能只收到一次 SIGCHLD，所以要一次把能回收的都回收，沒有了 waitpid 就回傳 0，迴圈結束。

這樣 parent 既不用卡在 wait 上，也不會留下 zombie（page-48）。signal 和 handler 的細節在 Ch10。

waitpid 的錯誤與 options#

Errors：No such child or wrong parent：pid 指定的 process 不存在，或者它存在但不是呼叫者的 child（只有 parent 能等自己的 child），errno 設成 ECHILD。

Option for waitpid：第三個參數 op 是下列常數 OR 起來，不用就給 0：

常數作用
WNOHANG不要 block：pid 指定的 child 還沒結束的話，立刻回傳 0，不等
WUNTRACED有支援 job control 的話，也回報 被暫停 的 child（之前還沒回報過的），用 WIFSTOPPED 判斷
WCONTINUED有支援 job control 的話，也回報暫停後 被繼續 的 child（XSI extension）
WNOWAIT只拿 status、不回收。平常 wait 會拿 status 再回收 child（page-40），所以同一個 child 只能被 wait 到一次；加了 WNOWAIT 就不回收，child 維持 zombie，之後還能再 wait 它一次（SVR4；POSIX 把它放在 waitid 的選項裡）

WNOHANG 讓 parent 可以「看一下有沒有 child 結束了，沒有就去做別的事」，回傳值分三種：大於 0 是某個 child 的 PID，0 是還沒有 child 結束，-1 是錯誤。

第二個 child 用到的 abort()（<stdlib.h>）是「讓程式異常結束」的函式：它送 SIGABRT 這個 signal 給自己，而 SIGABRT 的預設動作是結束 process 並產生 core dump（page-41）。它不會返回，也不會像 exit 那樣呼叫 exit handler（page-34 把它列在 abnormal termination）。程式發現自己進入了不該發生的狀態時會呼叫它，例如 assert 檢查失敗時，內部就是呼叫 abort。

(core file generated) 會不會出現，要看系統有沒有允許寫 core file。現在多數 Linux 預設 ulimit -c（core file 的大小上限）是 0，等於不寫，自己跑的話後兩行通常不會有這段字。

page-48#

Zombie & Orphan#

Zombie（殭屍 process）：

  • The process has terminated, but its parent has not yet waited for it：process 已經結束，但 parent 還沒 wait 它。
  • It keeps the minimal information (e.g., process ID, termination status, and CPU time taken) for the parent process：kernel 已經釋放它的記憶體、關掉它的 fd，只留下 PCB 裡最少的資訊：PID、termination status（page-06 的 p_xstat）、用掉的 CPU 時間。這些要留到 parent 呼叫 wait 來拿；拿走之後，kernel 才把最後這點東西清掉。

kernel 不能在 child 一結束就全部清掉，因為 parent 隨時可能來問「我的 child 是怎麼結束的」，答案必須還在。zombie 就是 page-07 的 Terminated 狀態。

用 ps 可以看到 zombie。例如 a.out fork 出一個 child，child 馬上 exit，parent 卻在 sleep、沒有 wait：

  • STAT 欄是 Z：表示這個 process 是 zombie（S 是 sleeping，R 是 running）。
  • CMD 欄是 [a.out] <defunct>：defunct 是「已經死掉、不再運作」的意思。名稱被方括號包起來、看不到完整的命令列，是因為它的記憶體已經被釋放，命令列參數也跟著沒了，ps 只能顯示 kernel 還留著的程式名稱。這個名稱是 zombie 自己的：child 是 a.out fork 出來的，沒有 exec 別的程式，所以它跑的程式也叫 a.out。parent 是誰要看 PPID 欄。
  • PPID 是 4211：它的 parent a.out 還活著，只是一直沒 wait。等 a.out 呼叫 wait 或結束，這一行就會消失。

What if the parent process terminates before the child process? (orphan)：parent 先死，child 就成了 orphan（孤兒 process）。

  • Inherited by init：orphan 會被 init（PID 1）收養。
    • When a parent terminates, it is done by the kernel：收養是 kernel 做的：一個 process 結束時，kernel 檢查所有 process，凡是 parent 是它的，都把 PPID 改成 1。
    • Clean up of the zombies by the init – wait whenever needed!：init 的工作之一就是：只要有 child 結束，就呼叫 wait 把它回收。所以被 init 收養的 process 結束後，不會一直留著當 zombie。已經是 zombie 的 child 也一樣：parent 結束時，它也會被 init 收養，接著馬上被 init 回收。

現在的 Linux 可以讓別的 process 宣告自己是 subreaper（代替 init 收養孤兒的 process），例如桌面環境的 systemd --user。這種環境下 orphan 的新 parent 不一定是 1。

Troubles from Zombie#

Although zombie processes do not occupy any memory space in the system, it consumes process IDs, which are limited resources too.

zombie 的記憶體已經釋放，但它還占著一個 PID，而且還算在 page-25 的 CHILD_MAX 裡。PID 的數量有上限（Linux 預設由 /proc/sys/kernel/pid_max 決定）。

  • You may not be able to fork new child processes when there are too many zombie processes in the systems. 一個長時間執行、一直 fork 卻從不 wait 的 server，zombie 會越積越多，最後 fork 失敗。

問題來了：How to fork a new child process but

  • not asking the parent process to wait for the child AND：parent 不想卡在 wait 上，例如 server 要繼續接新的連線。
  • not generating zombie process?：又不想留下 zombie。

答案在下一頁。

page-50#

fork 兩次#

做法是讓真正要做事的 process 變成 orphan，交給 init 去回收：

  1. parent fork 出 first child。
  2. first child 再 fork 出 second child，然後 馬上 exit。
  3. parent 用 waitpid 回收 first child。first child 一出生就結束，所以這個 waitpid 幾乎不用等。
  4. second child 的 parent（first child）已經死了，它成了 orphan，被 init 收養。它之後做完事 exit，由 init 去 wait，不會變成 zombie。

結果：parent 只花了一瞬間等 first child，之後就能做自己的事；真正做事的 second child 也不會留下 zombie。

第 3 步的 waitpid 不能省。這個範例的 parent 馬上就 exit，省掉看不出差別（first child 會被 init 收養並回收，page-48）；但這個寫法是給會一直活著的 parent 用的，例如 server。parent 不 wait 的話，一出生就結束的 first child 會變成 zombie，問題只是從 second child 換到 first child 身上。所以 fork 兩次不是不用 wait，而是把要等的對象換成一個馬上會結束的 child：

要 wait 的對象parent 卡多久
只 fork 一次真正做事的 child等它做完，可能很久
fork 兩次first child它一出生就 exit，幾乎不用等

second child 的 sleep(2) 是為了讓 first child 先 exit，這樣印 getppid() 時，parent 已經換成 1 了（page-56 會回頭看這件事）。輸出裡的 $ 出現在前面，是因為原本的 parent 很快就結束，shell 印出提示字元；2 秒後 second child 才印出它那一行。

左邊 parent、右邊 child：

child 做完事就 exit(0)，parent 繼續做自己的事，從不 wait。只要 parent 還活著，child 結束後就一直是 zombie：We get a zombie!!

page-52#

fork 兩次：三個 process#

三欄分別是 Parent、Child、Grandchild，同一份程式碼，黃色箭頭標出各自執行到哪一行：

  • Parent 從第一個 fork 拿到 child 的 PID，進最外層的 else。投影片這裡簡化成 exit(0)；page-50 的真正程式是 waitpid 回收 child 後繼續做自己的事。
  • Child 從第一個 fork 拿到 0，進 if，再 fork 一次，拿到 grandchild 的 PID，進內層的 else 馬上 exit(0)。
  • Grandchild 兩次都拿到 0，走進最裡面的區塊做事。它的 parent（child）已經結束，所以被 init 收養。

page-53#

Race Conditions#

Race condition（競爭條件）的定義：When multiple processes are trying to do something with shared data, the final outcome depends on the order in which the processes run. 多個 process 對共享的資料做事，最後的結果取決於它們執行的順序。

fork 之後誰先跑沒有保證（page-15），所以只要 parent 和 child 會碰到同一份東西（同一個檔案、同一個終端機），而程式又假設了某種順序，就是 race condition。這種 bug 很難抓：大部分時候順序剛好對，結果正確，偶爾順序不同才出錯。

page-54～55#

輸出交錯的例子#

parent 和 child 共用的資料是 同一個終端機（兩邊的 fd 1 指向同一個地方，page-20）。兩邊同時一個字元一個字元地印，kernel 可能在任何一個字元之後切換 process，所以字元會交錯：第一次跑，parent 印了一個 o 就被換下來，child 印完整行之後 parent 才印剩下的 utput from parent。第三次剛好沒有交錯。每次結果不同，正是 race condition。

setbuf(stdout, NULL) 把 stdout 設成 unbuffered（ch05 page-17），每次 putc 都直接呼叫一次 write。page-55 的圖用紅圈標出 buffer，說明為什麼要這樣做：如果 stdout 有 buffer，每個 process 會先把整行放進自己的 buffer，最後用 一次 write 送出去，一行就不會被拆開，看不出交錯。故意關掉 buffer、一次寫一個字元，是為了讓 kernel 有很多機會在中間切換，把 race condition 放大到看得見。有 buffer 只是讓交錯變得少見，race condition 本身還在。

page-56#

Who is the parent of the 2nd child?#

同一支 page-50 的程式。問題是：second child 印出的 parent pid 一定是 1 嗎？

不一定。second child 印 getppid() 的時候，first child 必須 已經 exit，它才會被 init 收養。如果 second child 先跑，first child 還活著，印出來的就是 first child 的 PID。

這又是 race condition：結果取決於 first child 和 second child 誰先跑。程式裡的 sleep(2) 讓 first child 有 2 秒可以先結束，在一般情況下幾乎一定夠，但系統很忙時還是沒有保證。

怎麼同步 parent 和 child#

How to synchronize parent and child processes? 要消除 race condition，就要讓一方等另一方做完某件事再繼續，這叫 synchronization（同步）。

Waiting loops? 例如 child 想等 parent 結束：

parent 結束後，child 被 init 收養，getppid() 變成 1，迴圈就結束。這種一直回去檢查條件的做法叫 polling（輪詢），兩個問題：

  • 浪費 CPU：child 每秒醒來一次檢查，大部分檢查都是白做。
  • 反應慢：條件成立後，最多要等 1 秒才發現。
  • 而且只能用在「等 parent 死掉」這一種情況。

Inter-Process Communication facility, such as pipe (Chapter 15.2), fifo, semaphore, shared memory, etc.：比較好的做法是用 IPC（interprocess communication，process 之間的溝通機制）讓兩邊互相通知：一方做完了就送個訊息，另一方在收到訊息之前 block，不用一直醒來檢查。用 pipe 實作的版本在 Interprocess Communication page-82～85，它用這個方法修好了 page-54 的交錯問題。

page-59#

exec#

Replace the text (i.e., instructions) and data (i.e., global variables, heap, and stack) segments of a process with another program!

exec 把目前 process 的 text 和 data（全域變數、heap、stack）整個換成另一支程式的。exec 不會建立新的 process，PID 不變，換掉的只是 process 在跑的程式。成功的話它 不會返回，因為呼叫它的那段程式碼已經不存在了；回傳 -1 一定是失敗。

「換掉」實際上是換掉 page table（ch03 page-12），不是把新程式複製進原本的記憶體：

  1. 拆掉舊的對應：舊程式各段對應的 frame，沒有別的 process 在用就釋放；還跟 parent 共用的（fork 後的 copy-on-write，page-16～17）就留給 parent。
  2. 建一張新的 page table：一開始幾乎是空的，只記著「這段位址對應到執行檔的哪一段」。程式第一次存取某個 page 時，CPU 在 page table 裡查不到這一頁對應到哪個 frame，沒辦法翻譯位址，就產生一個 page fault，把控制權交給 kernel（跟 page-16～17 寫入唯讀 page 時是同一種例外）。kernel 照它的紀錄把那一頁準備好、填進 page table，再讓那條指令重新執行，這次就查得到了。程式完全感覺不到中間發生過什麼。這種用到才載入的做法叫 demand paging（細節在 Ch7）：
區段第一次存取時
text從執行檔讀進來。text 是唯讀的，同時跑同一支程式的 process 共用同一組 frame
initialized data從執行檔讀進來，用 copy-on-write：只讀就共用，寫了才複製成自己的
bss、heap、stack跟檔案無關，直接配一個全部是 0 的新 frame

所以 exec 本身很快。而且載入是以 page 為單位、用到才載入：執行檔裡如果有一整頁的程式碼這次執行都沒跑到（例如只有出錯時才會呼叫的函式），CPU 從來不會去存取那一頁，它就不會觸發 page fault，也就不會被讀進記憶體。

exec 除了 pathname（要執行的程式檔路徑），還會傳兩樣東西給新程式：命令列參數和環境變數。

命令列參數#

新程式的 main(int argc, char *argv[]) 拿到的就是命令列參數：argv 是一個字串陣列，argc 是裡面有幾個字串。它跟 pathname 是給不同對象看的：

給誰看用途
pathnamekernel決定要載入哪個執行檔
argv新程式kernel 不解讀，原封不動放到新程式的 stack 上；新程式讀它，決定這次要做什麼

例如 shell 執行 ls -l /tmp：pathname 是 /bin/ls，argv 是 {"ls", "-l", "/tmp", NULL}，argc 是 3。ls 讀了 argv[1]、argv[2]，才知道要用長格式列出 /tmp。

  • argv[0]：也就是 exec 參數裡的 arg0，習慣上放程式的名字，但其實可以是任何字串（page-69）。程式會拿它來印錯誤訊息（ls: cannot access ... 開頭的 ls）；有些程式還會看它決定自己的行為，例如 gzip 和 gunzip 是同一個檔案的兩個名字，程式看 argv[0] 是哪一個，決定要壓縮還是解壓縮。
  • 最後一格是 NULL：新程式拿到的 argv 陣列以 NULL 結尾，所以呼叫 exec 時也要給 NULL 結尾：v 版本的陣列最後放 NULL；l 版本最後一個參數寫 (char *) 0，execl 也靠它知道參數列到哪裡結束。要寫成 (char *) 0 而不是單獨的 0：execl 的參數個數不固定，compiler 不知道這個位置應該是指標，單獨的 0 會被當成 int 傳，在 int 和指標大小不同的機器上（例如 64-bit），函式會讀到錯的值。

環境變數#

環境變數（environment variable）是一組 name=value 形式的字串，例如 HOME=/home/alice、PATH=/bin:/usr/bin，是這個 process 的設定：home 目錄在哪、要去哪些目錄找程式。它不是給某一次執行的參數，而是從 parent 一路繼承下來、大家共用的設定，細節在 page-61。

名字裡的字母#

l, v, and e stands for list, vector, and environment，說明上面兩樣東西怎麼給：

字母意思寫法
l（list）命令列參數一個一個列在參數裡execl("/bin/ls", "ls", "-l", (char *)0)
v（vector）命令列參數先放進一個 char * 陣列，傳陣列char *argv[] = {"ls", "-l", NULL}; execv("/bin/ls", argv)

Environment Variables#

environment variable（環境變數）是一組 name=value 形式的字串，例如 HOME=/home/stevens、PATH=/bin:/usr/bin。它們是 process 的設定：shell 在哪、home 目錄在哪、去哪裡找程式。fork 時被複製（page-24），exec 時由呼叫者決定要不要沿用（page-59 的 e），所以會從 parent 一路傳給 child。

圖上三層：

圖上是什麼
extern char **environ;一個全域變數，指向 environment list
Environment list一個 char * 陣列，每格指向一個環境變數字串，最後一格是 NULL
Environment strings字串本身，每個都以 \0 結尾

程式有兩種方式拿到它：

  • 宣告 extern char **environ; 直接用這個全域變數（POSIX 的寫法）。
  • int main(int argc, char **argv, char **envp);：main 的第三個參數。很多系統支援，但不是標準，建議用 environ。

要查單一變數，用 getenv("HOME") 比較方便，不必自己掃整個陣列。

環境變數放在哪：不在 PCB 裡，在 process 自己的 user space：

  • environment list 和 environment strings：在 stack 最上面那一塊，跟命令列參數放在一起（ch01 page-51）。
  • environ 這個變數：在 data／bss，跟其他全域變數一樣。

kernel 只在 exec 時碰它一次：把 envp（或目前的 environ）指向的字串複製到新程式的 stack 頂端。之後：

  • 程式用 setenv、putenv 改環境變數，改的只是自己 user space 裡的資料，kernel 不知道。新增變數時，原本的陣列可能放不下，C library 會在 heap 配一個新陣列，再讓 environ 改指向它。
  • fork 時它跟著被複製，是因為整個 user space 被複製了（page-14）。
  • exec 會丟掉舊的 user space，環境變數也跟著被丟掉，所以 exec 一定會把環境變數重新複製一次到新程式的 stack：沒有 e 的版本自動把目前的 environ 傳過去，看起來就是「沿用」；有 e 的版本則換成 envp 指定的那一組（page-64 的 use environ）。

PATH=/bin:/usr/bin:/usr/local/bin:.：PATH 是用 : 隔開的目錄列表，shell 和 page-62 的 execlp、execvp 會照順序到這些目錄找程式。最後紅色的 . 代表 目前所在目錄。把 . 放進 PATH 有安全風險：如果你 cd 進一個別人能寫的目錄，裡面有人放了一個叫 ls 的惡意程式，你打 ls 就可能執行到它（放在最後比放在最前面安全一點，但還是有風險）。空的項目也代表目前目錄，例如 PATH=:/bin:/usr/bin 開頭的空項目。

page-62#

execlp、execvp#

名字裡的 p 代表 PATH：第一個參數是 filename（檔名），不是完整路徑。

  • With p, a filename is specified unless it contains ’/’：
    • filename 裡沒有 /，例如 "ls"：照 PATH 的順序，到每個目錄找叫這個名字的檔案。例如 PATH=/bin:/usr/bin:.，就依序試 /bin/ls、/usr/bin/ls、./ls。
    • filename 裡有 /，例如 "./a.out"、"/bin/ls"：直接當成路徑，不搜尋 PATH。
  • /bin/sh is invoked with “filename” if the file is not a machine executable：如果找到的檔案不是機器碼的執行檔（例如沒有 #! 開頭的 shell script），execlp、execvp 會改成執行 /bin/sh，把這個檔名當參數交給它，也就是用 shell 去跑這個 script。

shell 跑你打的指令，就是用這種方式：你打 ls，shell 不知道 ls 在哪，交給 PATH 去找。

三個獨立的選擇，各對應一個字母：

  • 程式怎麼指定：路徑（pathname），或檔名加 PATH 搜尋（filename，p）。

  • 環境變數：沿用目前的 environ，或自己給一個 envp（e）。

沒有 execlpe 或 execvpe 這兩個組合（glibc 有非標準的 execvpe）。

page-64#

六個函式的關係#

  • 上面一排的 l 版本，先把一個一個的參數收集成陣列（build argv），再呼叫對應的 v 版本。
  • execvp 照 PATH 一個一個加上目錄前綴（try each PATH prefix）去試，呼叫 execv。
  • execv 把目前的 environ 當成 envp（use environ），呼叫 execve。

In many Unix implementations, execve is a system call：只有 execve 是真正的 system call，其他五個都是 C library 的函式，最後都走到 execve。這也是 ch01 page-49 列的是 execve 的原因。

page-65#

exec 繼承與改變的屬性#

Inherited from the calling process：exec 之後保留的屬性。它們都在 PCB 裡（kernel space），exec 只換 user space，所以不受影響：

  • pid、ppid、real [ug]id、supplementary gid
  • process group id、session id、controlling terminal（page-24）
  • time left until alarm clock：alarm 設的鬧鐘剩下的時間
  • current working dir、root dir、file mode creation mask（umask）、file locks
  • process signal mask、pending signals、resource limits
  • tms_utime、tms_stime、tms_cutime、tms_cstime（投影片最後兩個重複寫成 tms_cutime、tms_ustime，應為 tms_cutime、tms_cstime）
  • FD_CLOEXEC flag：投影片把它列在這裡，意思是「開著的 fd 會不會被新程式繼承，由每個 fd 自己的 FD_CLOEXEC 決定」（page-66）。沒設的 fd（預設）在 exec 之後還開著，新程式可以直接用；設了的 fd 在 exec 時被關掉，新程式拿不到。

跟 fork 對照（page-24）：file locks、pending signals、alarm、CPU 時間，fork 時 child 不繼承，exec 時 保留。因為 fork 產生的是另一個 process，而 exec 之後還是同一個 process，屬於它自己的帳不會因為換程式就被清掉。

Requirements & Changes：exec 會改變的：

  • Closing of open dir streams：opendir 開的 directory stream（ch04 page-66）一定會被關掉。POSIX 要求 opendir 底層用的 fd 設好 FD_CLOEXEC。
  • effective user/group ID：程式檔有 set-user-ID／set-group-ID bit 的話會改變（ch04 page-16），saved set-user-ID 也跟著更新（ch04 page-15）。
  • 投影片的 etc. 還包括：有設 handler 的 signal 被重設成預設動作（handler 在舊程式的 text 裡，已經被換掉了，ch03 page-11 的 note）、atexit 登記的 handler 被清掉（page-37）。

page-66#

FD_CLOEXEC：close-on-exec flag#

close-on-exec flag：每個 fd 各有一個，記在 fd table 裡（圖上紅圈的 fd flags 欄，ch14 page-25）。設了它的 fd，exec 時會被 kernel 自動關掉；沒設的話，fd 會原封不動地留給新程式。

為什麼需要它：page-65 說 fd 預設會穿過 exec 留下來。這對 stdin、stdout、stderr 是好事，shell 的重導向就靠這個（page-70）。但 parent 自己開的其他檔案（設定檔、網路連線、log 檔）也會一起留給新程式，新程式根本不知道有這些 fd，不會去用也不會去關：

  • 白白占著 fd 和 file table 項，檔案或連線也因為 reference count 沒歸零而一直關不掉。
  • 安全問題：set-user-ID 程式用 root 權限開了一個機密檔，接著 exec 一個一般程式，那個程式就能讀這個 fd。

這種「只是自己要用、不打算交給新程式」的 fd，開完就設 close-on-exec。

page-70#

Why keep fork() and exec() separate#

page-25 提到別的作業系統用一個 spawn 就做完「建立 process 並執行新程式」。UNIX 拆成兩步，理由有兩個：

1. In many client-server applications, the server may fork processes that continue to execute the same program.：有時候只要 fork、不要 exec。例如 server 的 parent 接連線，fork 出來的 child 繼續跑同一支程式去服務這個連線。在 thread（multi-threading，Ch11）普及之前，這是讓一支程式同時處理好幾件事的主要方法。

2. Child ensures that the new program to be executed is in the desired state.：fork 和 exec 之間，child 還在跑 parent 的程式碼，可以先替新程式把環境準備好，再 exec。因為 fd、ID、signal 設定都會穿過 exec（page-65），在這裡改好的東西，新程式一啟動就是這個狀態：

  • Redirecting standard input, output, or error：把 stdin、stdout、stderr 換成別的檔案。
  • Closing open files inherited from the parent that are not needed by the new program：關掉新程式用不到的 fd。
  • Changing the UID or process group：改變身分或 process group。
  • Resetting signal handlers：重新設定 signal 的處理方式。
