page-03#

Blocking vs. Nonblocking I/O#

ch03 page-20 已經比較過 blocking 和 nonblocking，這頁把定義講得更精確：

呼叫什麼時候返回
Blocking要求的動作 做完 才返回，例如 read(fd, buf, 100) 要等到真的有資料
NonblockingOS 能做多少就做多少，做不了的部分不等，直接返回，process 不會被 suspend（暫停、讓出 CPU）

拿 pipe 的幾種情況對照，就能看出兩者差在哪：

情況BlockingNonblocking
read 100 byte，pipe 裡有 200 byte讀 100，返回 100同左
read 100 byte，pipe 裡只有 30 byte讀 30，返回 30同左
read 100 byte，pipe 是空的suspend，等另一端寫入資料才讀、才返回立刻返回 -1，errno = EAGAIN
write 100 byte，pipe 只剩 30 byte 空間寫 30 後 suspend，有空間再寫，100 全寫完才返回寫 30，立刻返回 30
write 100 byte，pipe 已滿suspend，等有空間才寫立刻返回 -1，errno = EAGAIN

前兩列兩者一樣。差別只出現在 現在做不了（或做不完） 的時候：

  • Blocking：process 被 suspend。kernel 把它改成 sleeping、CPU 交給別的 process，程式停在這個 system call 裡，後面的程式碼都不會執行，直到條件滿足被叫醒才返回。
  • Nonblocking：一定馬上返回，能做的部分做完就回來。代價是程式要自己處理「只寫了一部分」或 EAGAIN，之後再試一次（page-06 的迴圈就是在做這件事）。

寫了一部分時不會設定 errno。 errno 只在 system call 回傳 -1（失敗）時才會被設定。nonblocking write 寫進 30 byte、回傳 30，對 kernel 來說是 成功，errno 不會被改，裡面留的是之前某次失敗的舊值。所以判斷「只寫了一部分」要看回傳值是否小於要求的 byte 數，不能看 errno；這也是 page-06～07 的程式每次 write 前都先把 errno 設成 0 的原因。

投影片 write 那列只對大的寫入成立

一次寫入不超過 PIPE_BUF byte（Linux 是 4096，ch04 page-37）時，kernel 保證整筆資料一起放進 pipe，不會拆開。所以 pipe 只剩 30 byte 空間時寫 100 byte：blocking 會等到空出 100 byte 再一次寫完；nonblocking 一個 byte 都不寫，直接回傳 -1、errno = EAGAIN。超過 PIPE_BUF 的寫入才會像投影片那樣「能寫多少寫多少」。

哪些呼叫會「卡住」？#

不是每個 system call 都需要擔心這件事。投影片把可能 永遠等下去 的叫 slow system call：

  • 讀寫 pipe：另一端沒寫，你就讀不到（ch03 page-32 的 note）。
  • 讀寫 terminal device（終端機，page-09）：使用者不打字，就沒有資料。
  • 讀寫 network device：對方不傳，就等不到。

共同點是資料要等「別人」送來，什麼時候到沒有保證。讀寫磁碟上的一般檔案則不算：磁碟再慢也會在有限時間內完成（ch03 page-21）。

這也是 nonblocking 存在的理由：等待時間取決於別人的操作，就可能沒有上限。blocking 的 process 會一直卡在那裡，其他事都做不了。等待時間有上限的操作（例如讀寫一般檔案），直接等就好，用不到 nonblocking。

怎麼打開 nonblocking#

兩種方式，對象都是 fd 所指的那一項 open file table（ch03 page-20 的 note）：

  1. open 時加 O_NONBLOCK。
  2. 已經開好的 fd（例如 shell 給的 fd 0、1），用 fcntl 加上 O_NONBLOCK（page-05）。

page-04#

O_NONBLOCK 存在哪#

同一張 ch03 page-09 的全圖，箭頭指著 open file table：O_NONBLOCK 是 file status flag，跟 O_APPEND 存在同一個地方（ch03 page-24）。

右邊那條直的紅線畫在 buffer cache 和 Disk 之間，是 kernel 和外部裝置的分界：

  • 線的左邊：kernel 自己的記憶體（open file table、buffer cache），在這裡搬資料隨時做得到，不用等。
  • 線的右邊：外部裝置（磁碟、終端機、網路另一端），資料什麼時候來、空間什麼時候空出來，kernel 控制不了。

要等，一定是在等線右邊的裝置。所以：

  • Blocking：越過紅線去等裝置，等的期間 process 被 suspend。
  • Nonblocking：不越過紅線。左邊做得到的做完，就順著黃色箭頭（往左）直接回到 process。

所以 page-03 說的「沒資料」「沒空間」，指的都是 線左邊那塊 kernel buffer 的狀態。圖上只畫了磁碟，它的 kernel buffer 叫 buffer cache；其他對象各有自己的 kernel buffer，名字不同（ch03 page-08 的 note）：

對象線左邊的 buffer線右邊在等誰
pipepipe buffer另一端的 process 寫入／讀走
終端機input queue／output queue（page-09）使用者打字／畫面顯示
網路socket 的收／送 buffer對方傳來資料／收走資料
  • nonblocking read：buffer 裡有多少拿多少；buffer 是空的就回 EAGAIN，不等裝置把資料送進來。
  • nonblocking write：buffer 剩多少空間就寫多少；buffer 滿了就回 EAGAIN，不等裝置把資料取走。

那一般檔案呢？#

照上面的說法會有個疑問：用 O_NONBLOCK 開一個一般檔案，資料一開始在磁碟上、不在 buffer cache 裡，要靠 read 叫 kernel 去搬。可是 nonblocking 又說「buffer 沒資料就返回」，那豈不是永遠不會去搬，永遠讀不到？

答案是 Linux 對一般檔案 忽略 O_NONBLOCK：buffer cache 裡沒有，就照樣等磁碟讀進來。這樣等不會有問題，因為磁碟一定會在有限時間內完成，本來就不算 slow system call（page-03）。圖上把紅線畫在磁碟旁，只是示意「等外部裝置」的位置。

write 也一樣用不到 nonblocking。寫一般檔案只要把資料複製進 buffer cache 就返回，寫回磁碟是 kernel 之後自己做的事（delayed write，page-08），所以幾乎不會遇到「沒空間」。就算 buffer cache 裡待寫回的資料太多，kernel 會先寫一部分回磁碟再收你的資料，這也只是有限時間的等待。

那上表三種對象跟一般檔案差在哪？差在 誰在搬 buffer 裡的資料：

read：資料怎麼進 bufferwrite：資料怎麼離開 buffer要等多久
一般檔案read 叫 kernel 去磁碟搬kernel 自己找時間寫回磁碟有限
pipe／終端機／網路別人推進來：另一端 write、使用者按鍵、網卡收到封包別人取走：另一端 read、畫面顯示出去、對方收下看別人，可能永遠

所以對這三種對象，回 EAGAIN 不會擋住資料流動：read 時資料到了就在 buffer 裡等你，write 時別人取走資料就會空出位置，晚點再試就做得到。

為什麼 pipe 和終端機會「沒空間」？#

因為它們 buffer 裡的資料 只能等另一端取走，kernel 自己清不掉，所以只給一塊固定大小的小 buffer：

buffer 大小滿了怎麼辦
一般檔案buffer cache 可以用掉大部分閒置記憶體kernel 自己寫回磁碟，就空出位置
pipe固定大小（Linux 預設 64 KB）只能等讀的那端 read 走，kernel 不能丟、也沒地方放
終端機output queue 固定幾 KB只能等畫面把字顯示出去

為什麼不讓 buffer 無限長大？因為另一端可能讀得很慢，甚至永遠不讀。例如 yes | sleep 100：yes 拚命寫，sleep 一個字都不讀，kernel 要是一直收，記憶體很快就被吃光。

所以 buffer 故意設上限，滿了就讓寫的一方停下來：blocking 被 suspend，nonblocking 回 EAGAIN。這叫 flow control（流量控制，也叫 backpressure），寫的速度被迫配合讀的速度。page-07 的實驗就是這樣：一次要寫 50 萬 byte，終端機的 output queue 只有幾 KB，畫面又顯示得遠比 write 慢，queue 一下就滿了。

page-06～07#

Example of Nonblocking#

這支程式把 stdin 讀到的 500,000 byte，用 nonblocking 的 write 寫到 stdout，並把每次 write 的結果記到 stderr，用來觀察 nonblocking write 實際上怎麼表現。

  1. 讀進來：read 從 stdin 讀最多 500,000 byte 到 buf。執行時 stdin 被 < 接到 /etc/termcap（一個 702,559 byte 的文字檔，只是拿來當輸入），所以讀滿 500,000。

  2. 設成 nonblocking：set_fl 把 fd 1 打開 O_NONBLOCK（page-05）。

  3. 寫出去：ptr 指向還沒寫出去的第一個 byte，ntowrite 是還剩多少。每一輪都試著把剩下的全部寫出去：

    • nwrite > 0：寫進了 nwrite byte（可能只有一部分），ptr 往後移、ntowrite 扣掉這麼多。
    • nwrite == -1：一個 byte 都沒寫進去（EAGAIN），什麼都不改，下一輪再試。

    迴圈裡沒有任何等待，寫不進去就馬上重試，這就是 polling。

  4. 記錄：每次 write 的結果印到 stderr，因為 stdout 正被拿來當實驗對象，訊息不能混進去。stderr 是 unbuffered（ch05 page-15），每筆記錄都會馬上寫出去。每次 write 前先把 errno 設成 0，是因為 errno 成功時不會被清掉（ch00 page-16 的 note），不先歸零就分不出這次有沒有出錯。

  5. 收尾：把 nonblocking 關掉。fd 1 跟 shell 共用同一項 open file table（ch03 page-20 的 note），不關的話 shell 之後也會變成 nonblocking。

stdout 接到哪，結果就不同#

程式裡只寫了 STDOUT_FILENO，沒說它是什麼。fd 1 接到哪是 shell 決定的（> 重導向）。O_NONBLOCK 設在 fd 指到的 open file table 那一項上，任何 fd 都能設；有沒有效果，要看 fd 背後接的是什麼（page-04）。投影片就是讓同一支程式跑兩次，stdout 分別接到一般檔案和終端機：

stdout 接到結果原因
第一次一般檔案 temp.file一次 write 就寫完 500,000 byte只要複製進 buffer cache，碰不到紅線；Linux 也忽略 O_NONBLOCK（page-08）
第二次終端機（沒重導向）寫進 216,041 byte 後，連續上千次回 -1、errno = 11；偶爾又寫進一批output queue 滿了，要等畫面顯示出去才有空間（page-09）

11 就是 Linux 上的 EAGAIN（ch03 page-20）。第二次把 stderr 導到 stderr.out，只是為了不讓上千行記錄跟輸出混在螢幕上。

所以 stdout 設成 nonblocking 根本碰不到磁碟，而這正是重點：nonblocking 要避免的「等」，等的不是磁碟，而是終端機這類 slow device。那上千次 EAGAIN 就是 polling 的代價：CPU 一直在跑迴圈，什麼正事都沒做。

page-08#

為什麼一般檔案一次就寫完：Delayed Write#

箭頭指著 buffer cache：寫一般檔案時，write 只要把資料複製進 buffer cache 就返回，寫回磁碟是之後的事（ch03 page-08 的 delayed write）。

buffer cache 在記憶體裡，複製隨時都做得到，不會出現「空間不夠、要等」的情況。所以對一般檔案來說 nonblocking 沒有意義，write 一次就全收下，這也是 Linux 對一般檔案忽略 O_NONBLOCK 的原因。

終端機就不一樣了，它的 buffer 很小，而且清空的速度取決於畫面能多快顯示，見下一頁。

page-09#

Terminal Device（Ch18.2）#

terminal device（終端機裝置）就是你打指令的那個視窗在 kernel 裡的代表，例如 /dev/pts/0（ch03 page-16）。kernel 裡負責它的程式叫 terminal driver，替每個終端機維護兩條 queue（佇列，先進先出的緩衝區）：

資料從哪來往哪去
input queue你在鍵盤打的字process read 走
output queueprocess write 進來送到螢幕顯示

圖上幾個細節：

  • if echo enabled：打的字除了進 input queue，也會複製一份到 output queue，所以你看得到自己打了什麼（echo，回顯）。輸入密碼時就是把 echo 關掉。
  • MAX_INPUT：input queue 的容量上限。

canonical mode#

shell 讓 stdin 接到終端機時，終端機處在 canonical mode（正規模式，也就是一行一行處理）：你打的字先留在 driver 裡，可以用 backspace 修改，按 Enter 之後整行才交給程式，所以 每次 read 最多回傳一行。相對的是 noncanonical mode，每按一個鍵程式就收到，vim 這類全螢幕程式用的就是它。

vim 需要 noncanonical mode，是因為它的操作都要 按下去馬上生效：normal mode 按 j 游標立刻往下移，dd 立刻刪掉一行，Esc 立刻離開 insert mode。如果是 canonical mode，driver 會把 j 留著，等你按 Enter 才把整行 j\n 交給 vim，根本做不了即時反應。所以 vim 啟動時把終端機切成 noncanonical mode，收到每個鍵後自己決定要做什麼，離開時再切回來。

output queue 滿了怎麼辦#

這就是 page-07 的情況：程式寫得比畫面顯示得快，output queue 很快就滿了。

  • Blocking：讓 process 睡著，等 queue 騰出空間再叫醒它。不佔 CPU。
  • Nonblocking：write 回傳 EAGAIN，程式只能自己一直重試，也就是 polling（busy waiting，空轉等待）。在 multiuser system（多使用者共用一台機器）上，這是在浪費大家共用的 CPU。

所以單純打開 nonblocking 並不是好方法：它解決了「卡住」，卻換來「空轉」。下一頁開始找更好的做法。

page-10#

I/O Multiplexing：要解決什麼問題#

以 PTT（台灣的 BBS 站）為例：server 要在 User 1 和 User 2 之間轉送訊息。server 不知道誰會先講話，只用 blocking I/O 時，如果它正在 read User 1 的連線，User 1 一直不說話，User 2 傳來的訊息就沒人收。

做法問題
Idea 1nonblocking I/O，輪流問每條連線有沒有資料沒資料時一直空轉，浪費 CPU cycle
Idea 2multi-process：每條連線（每個方向）各開一個 server process 專門等，卡住也只卡自己使用者一多，process 數量爆炸；而且這些 process 要共用資料（例如看板內容），得靠 IPC（inter-process communication，ch00 page-19）互相溝通，又是一筆成本

page-11#

I/O Multiplexing#

I/O multiplexing（I/O 多工）：把一整組 fd 交給 kernel，請它「其中任何一個準備好了就叫醒我」。process 在等待時是睡著的（不像 Idea 1 空轉），而且只要一個 process 就能顧所有連線（不像 Idea 2 開一堆 process）。

什麼時候需要它：

  • 一支程式要 同時處理好幾個 descriptor，例如一般檔案加上 socket descriptor（網路連線的 fd，ch16 page-39），或好幾條網路連線。
  • 而且 其中任何一個的 I/O 都可能卡住。

只要兩個條件都成立，就不能隨便對其中一個做 blocking read。下面介紹兩個做這件事的 system call：select 和 poll。

用途：一次等很多個 fd#

你把「想等哪些 fd、等它能讀還是能寫」交給 kernel，process 就睡著，不佔 CPU。只要其中 任何一個 準備好，或時間到了，kernel 才把你叫醒，並告訴你是哪幾個準備好。之後只對那幾個 fd 呼叫 read／write，就保證不會卡住。

「準備好」的意思是 現在去 read／write 不會被 suspend，也就是 page-04 那塊 kernel buffer 有資料可讀、或有空間可寫。讀到 end of file（read 會回傳 0）也算能讀。

writefds同上，檢查「fd Y 能不能寫」

fd_set 與四個巨集#

容量是常數 FD_SETSIZE（通常 1024），所以 select 最多只能看 0～1023 號的 fd。

  1. 新連線也是一個要等的 fd。server 有一個專門接新連線的 socket listenfd，有人連進來時它會變成「能讀」，所以跟用戶的 fd 一起放進 readset，再用 accept 接起來（ch16 page-42～43）。
  2. writeset 只放有東西要送的用戶。select 只要有 任何一個 fd 準備好就返回，而「能寫」的標準是 socket 的發送 buffer 還有空間。你沒在寫的時候這個 buffer 是空的，所以網路連線幾乎永遠「能寫」。如果把每個用戶都放進 writeset，select 每次都會立刻返回、一次都睡不著；但其實沒東西要送，迴圈只能馬上再呼叫一次，又變回空轉（polling）。「能讀」就不一樣，要等對方真的傳資料來才成立，所以 readset 可以放心全放。只有上次 write 沒寫完（發送 buffer 滿了、待送 buffer 還有東西）時，等「能寫」才有意義。

一個 process 就能服務所有用戶，等待時又是睡著的，page-10 的 Idea 1（空轉）和 Idea 2（process 爆炸）的問題都沒有。

Comparison of I/O Models#

一次 read 其實分成兩個階段：

  1. wait for data：等資料到 kernel（例如網路封包抵達）。
  2. copy data：kernel 把資料從自己的 buffer 複製到你的 buf（ch03 page-12）。

三種 model 的差別在第一階段怎麼等：

wait for datacopy data
blocking呼叫 read（initiate）後就睡著，兩個階段都在 read 裡面等完同一個 read 裡，複製完才返回（complete）
nonblocking程式自己一直 read（check, check, check…），每次都立刻拿到 EAGAIN某次 read 終於有資料，在這次呼叫裡複製完返回
I/O multiplexing在 select／poll 裡 睡著 等，直到某個 fd ready再對那個 fd 呼叫 read，複製完返回

可以看出 I/O multiplexing 對 單一 fd 並沒有比 blocking 好，反而多了一次 system call（先 select 再 read）。它的價值在於 一次 select 可以同時等很多個 fd，而且等待時是睡著的，不像 nonblocking 那樣空轉。

Why File Lock#

前面處理的是「一個 process、很多 fd」；接下來換成「很多 process、同一個檔案」。

問題：多個 process 可能同時存取同一個檔案。沒有互斥（exclusive access：同一時間只讓一個人碰）的話，可能有人正讀著舊資料，另一個人已經把它改掉了，造成 data inconsistency（資料不一致）。

投影片最後提示 Think about atomic operation (Ch3)：ch03 page-50～51 的 pread／pwrite 能讓「seek + 讀」或「seek + 寫」變成一步，但這裡的問題是 讀 → 計算 → 寫回 這一整串，跨了好幾個 system call，沒有任何一個 system call 能一次做完。所以需要 lock：A 在讀之前先鎖住這 4 個 byte，寫回後才釋放（release），B 想動同一段就得等。

File Lock in UNIX#

一個 process 用 exclusive lock（獨占鎖）鎖住檔案後，其他 process 就不能讀寫同一段。

上鎖的流程是：process 先向 kernel 申請 一把鎖，kernel 檢查這段範圍有沒有被別人鎖住，再決定結果。granted 和 denied 就是這個申請的兩種結果：

結果什麼時候發生之後
lock granted這段範圍沒有別人的鎖跟你衝突（什麼叫衝突見 page-21），申請通過你成為這把鎖的 lock holder（持有者），可以讀寫被鎖的部分，直到你自己釋放
lock denied已經有別的 process 持有衝突的鎖，申請不通過你拿不到鎖，要等 lock holder 釋放才有機會

投影片說 denied 之後「要等」，但其實 kernel 不一定讓你等：用 F_SETLKW 申請會睡著等到 granted 為止，用 F_SETLK 則立刻回傳錯誤，讓你自己決定要不要再試（page-22），跟 blocking／nonblocking 的差別一樣。

UNIX 上有三種上鎖的方式：

函式鎖的範圍說明
flock()整個檔案源自 BSD
fcntl()檔案裡 任意一段 byte（byte range）POSIX 標準，本章介紹的就是這個
lockf()任意一段包在 fcntl() 上面的簡化介面

fcntl 這種鎖傳統上叫 record locking：只鎖檔案裡的某一段，而不是整個檔案。名字來自資料庫，檔案由一筆筆 record 組成，鎖一筆 record 時，別的 process 還能同時改其他筆。但 UNIX 的檔案只是一串 byte，沒有「record（紀錄）」的概念（ch01 page-53），所以更準確的名字是 byte-range locking：鎖的是「從第幾個 byte 開始、長度多少」的一段。

投影片的表把這個規則整理成：某一段已經有鎖時，新的上鎖要求會被 granted 還是 denied（page-20）：

道理很簡單：大家同時讀不會互相影響，所以 read lock 可以共享；但有人在寫的時候，別人可能讀到寫到一半的資料，所以 write lock 只能有一個。

規則是 一個 byte 一個 byte 看的。A 鎖第 0～9 byte、B 鎖第 10～19 byte，兩段沒有重疊，就算都是 write lock 也不衝突。

這幾頁說的 衝突，就是指上表會被 denied 的情況，三個條件同時成立：

  1. 那把鎖是 別的 process 的（自己的鎖不會跟自己衝突，page-24）。
  2. 兩把鎖的範圍 有重疊 的 byte。
  3. 兩把鎖 至少有一把是 write lock（兩把都是 read lock 就能共存）。

Remarks#

File access：開檔模式要跟鎖的種類對上#

  • 要上 read lock，fd 開檔時要能讀（O_RDONLY 或 O_RDWR）。
  • 要上 write lock，fd 開檔時要能寫（O_WRONLY 或 O_RDWR）。

否則 fcntl 回傳 -1，errno 為 EBADF。

Non-atomic operations：先查再鎖沒有用#

先用 F_GETLK 確認沒有衝突，再用 F_SETLK 上鎖，這兩步之間 不是 atomic 的：查完到上鎖的空檔，別的 process 可能先把它鎖走了（跟 ch03 page-51 的問題一樣）。要上鎖就直接呼叫 F_SETLK／F_SETLKW，看回傳值知道有沒有成功。F_GETLK 只適合用來查「現在是誰鎖著」。

Implied inheritance and release of locks：鎖什麼時候會自動釋放#

情況鎖會怎樣
process 結束它所有的鎖都被釋放
close 任何一個 指到這個檔案的 fd這個 process 在 這個檔案 上的所有鎖都被釋放，不管當初是用哪個 fd 鎖的（page-27）
fork不會繼承：child 沒有 parent 的鎖
exec會繼承：鎖還在；但如果那個 fd 設了 close-on-exec（page-25），exec 時 fd 會被關掉，鎖也跟著釋放

這幾條規則的原因都一樣：鎖記的是「哪個 process 鎖了哪個檔案」，跟用哪個 fd 無關。fork 出來的 child 是另一個 process，所以沒有鎖；exec 還是同一個 process（PID 不變，ch03 page-11），所以鎖還在。

實作上，鎖存在 檔案的 v-node 上：一個 linked list，每個節點記範圍、種類和 PID，沒有記是哪個 fd 鎖的（page-28）。所以 close 時 kernel 分不出哪把鎖是從這個 fd 來的，只能把這個 process 在這個檔案上的鎖全部刪掉。這個行為公認是 POSIX 鎖的設計缺陷，page-27 會看到它造成的問題和後來的修正。

The compatibility rule only applies to different processes#

page-21 那張 granted／denied 的表只用在 不同 process 之間。同一個 process 對自己已經鎖住的範圍再上鎖，不會跟自己衝突，新的鎖會 直接取代 舊的。例如自己原本有 read lock，可以直接換成 write lock。

page-25#

close-on-exec 存在哪#

箭頭指著 open file descriptor table（fd table）：close_on_exec（程式裡寫作 FD_CLOEXEC）是 file descriptor flag，跟著 fd 走，不是存在 open file table 的 file status flag（ch03 page-09、page-24）。

設了它的 fd，在 exec 時會被自動關掉。用 fcntl(fd, F_SETFD, FD_CLOEXEC) 設定（ch03 page-66）。再加上 page-24 的規則：fd 被關掉時，這個 process 在那個檔案上的鎖也會一起釋放。

page-27#

What happens to the locks on fd1?#

答案：兩個例子裡，close(fd2) 之後 fd1 上的鎖都沒了。

照 page-24 的規則，close 任何一個指到這個檔案的 fd，就會釋放這個 process 在這個檔案上的所有鎖：

  • Example 1：fd2 是 dup 出來的，跟 fd1 指到同一項 open file table。
  • Example 2：fd2 是重新 open 的，跟 fd1 各有一項 open file table，只有 v-node 相同。

就算是 Example 2 這種完全獨立的開檔，鎖照樣被釋放，因為規則只看「同一個 process、同一個檔案」。

所以上鎖到底影響什麼？#

鎖 只會影響別的 process 上鎖，其他動作都不會被擋：

動作會不會被鎖擋住
別的 process 對重疊的範圍上鎖會：照 page-21 的表 granted 或 denied
別的 process open、read、write不會，fcntl 的鎖是 advisory（page-29）
自己 dup、open 同一個檔案不會
自己對同一段再上鎖不會，新鎖直接取代舊鎖（page-24）

反過來，會影響鎖的只有兩件事：自己 close 任何一個指到這個檔案的 fd，或 process 結束，鎖都會被釋放。

實務上的陷阱

這表示你呼叫的某個 library 函式只要自己開了同一個檔案、用完 close，你辛苦上的鎖就默默消失了。Linux 後來另外加了 open file description lock（F_OFD_SETLK 等），讓鎖改成跟著 open file table 那一項走，就是為了修這個問題。

page-29#

Advisory vs. Mandatory Lock#

Advisory lock#

advisory lock 的意思是「鎖只是一種約定」：要所有 process 都說好，存取檔案前先上鎖，鎖才有用。

  • kernel 只負責記錄「誰鎖了哪一段」，在別人也來上鎖時判斷 granted 或 denied。
  • 但 kernel 不會攔 read／write。一個 rude process（不守約定的 process）只要對檔案有寫入權限，不上鎖直接 write，一樣寫得進去，資料還是可能被改壞。
  • fcntl() 提供的就是 advisory lock。

圖上的意思：守約定的 process 都先經過中間那層 advisory lock access functions，rude process 則直接繞過去改檔案。

所以 advisory lock 適合「所有存取這個檔案的程式都是自己人」的情況，例如同一套系統裡的幾支程式，或作業裡你自己寫的 server。

看起來 rude process 能直接改檔案很不安全，但「誰能寫這個檔案」本來就由檔案權限控制（ch01 page-55、ch04 page-21）。例如只給信任的 user 或 group 寫入權限（w），其他人連用寫入模式 open 都會失敗。能寫的都是守約定的程式，advisory lock 就夠用了。剩下的風險只有自己人的程式忘了上鎖，那是程式的 bug，不是安全問題。

page-30#

Mandatory lock#

mandatory lock（強制鎖）：kernel 在 每一次 open、read、write 時都檢查這個動作有沒有跟別人的鎖衝突，有衝突就不讓它做。圖上不管從哪個函式進來，都要先經過 kernel 的 locking check 才能碰到檔案。

  • 不是 SUS 的一部分：SUS（Single UNIX Specification）是定義「怎樣才算 UNIX」的標準，跟 ch03 page-03 的 POSIX 同一類。所以各系統支援程度不一：Linux 2.4.22、Solaris 9 有；FreeBSD 5.2.1、Mac OS X 10.3 沒有。
  • specified in file permissions：對哪個檔案用 mandatory lock，是用權限位元標記的：打開 set-group-ID 位元（一個特殊權限位元，平常用途是「執行時以檔案所屬 group 的身分執行」，ch04 page-16）、同時關掉 group 的執行權限。這個組合本身沒有意義，所以被借來當標記，ls -l 會在 group 的 x 位置顯示大寫 S，例如 rw-rwSrw-（ch04 page-31）。
  • involves system overhead：每次 read／write 都要多查一次鎖，會變慢。
現在的 Linux

Linux 上除了設權限，檔案系統還得用 -o mand 選項掛載才會生效；而且 Linux 5.15（2021 年）已經 移除 了 mandatory lock 的支援。實務上用的都是 advisory lock。
