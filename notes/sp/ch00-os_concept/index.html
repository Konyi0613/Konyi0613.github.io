這頁的主旨#

一個電腦系統由三大類東西組成：硬體（hardware）、系統程式（system programs）、應用程式（application programs）。這頁用一張經典的「階層圖」（出自 Tanenbaum 的作業系統教科書）把整台電腦從最底層的電子元件到最上層的使用者程式，一層一層疊起來。每一層只跟相鄰的層打交道，並對上層隱藏下層的細節。

左邊的階層圖（由上往下）#

層內容說明
Application programsBanking system、Airline reservation、Web browser一般使用者真正要用的程式
System programsCompilers、Editors、Command interpreter (shell)幫助開發與操作的工具程式，不是 OS 核心的一部分
Operating system—管理硬體、提供服務給上層
Machine language—這顆 CPU 能直接執行的指令集（binary 指令）
Microarchitecture—實作那套指令集的硬體邏輯：ALU、暫存器、資料路徑、控制單元等
Physical devices—最底層的電晶體、閘、電路

其中下面三層（Machine language / Microarchitecture / Physical devices）屬於硬體，上面三層（OS 以上）屬於軟體。

兩個關鍵「介面」（圖上的兩個紫色標籤）#

這頁想強調的重點是：層與層之間有兩條特別重要的分界線。

  • ISA（Instruction Set Architecture）：位在「machine language」這一層，是硬體與軟體之間的介面。它規定 CPU 提供哪些指令、有哪些暫存器、記憶體怎麼定址。只要 ISA 不變，上層軟體就不必管底下微架構怎麼做（例如 Intel 和 AMD 微架構不同，但都能跑 x86 程式）。

  • System Call：位在「OS」和上層程式之間，是應用程式取得 OS 服務的唯一合法入口。應用程式不能直接碰硬體，要讀檔、開 process、送網路封包都得透過 system call 請 OS 代勞。這也正是這門課（Systems Programming）的主題。

右下角疊上去的硬體方塊圖#

補充說明「machine language / 硬體」那幾層實際長什麼樣：CPU、Memory、Input and Output 三個元件透過 System Bus 相連，而 system bus 又分成：

  • Control bus：傳控制訊號（讀/寫、時脈等）
  • Address bus：指定要存取的記憶體或 I/O 位址
  • Data bus：實際傳輸的資料

page-05#

觀點一：延伸機器 It is an extended machine（vertical，縱向）#

把 OS 看成疊在硬體之上的一層抽象，由下往上把難用的硬體包裝成好用的「虛擬機器」。

  • Presents user with a virtual machine, easier to use（提供虛擬機器，比較好用） 硬體介面非常原始又繁瑣。例如要從磁碟讀一個磁區，得自己操作磁碟控制器的暫存器、設定磁軌/磁頭/磁區、啟動馬達、等中斷、處理錯誤重試。OS 把這些包成一個 read() 呼叫，程式設計師只看到「檔案」這個乾淨的概念。這層乾淨介面就是 user interface / API（system call）。

  • Hides the messy details which must be performed（把必須做、但很髒的細節藏起來） 那些中斷處理、DMA、裝置差異都還是要做，只是 OS 幫你做掉。而且是 safely（安全地）：使用者程式不能直接碰硬體，一律透過 OS 代為執行，OS 會做權限檢查、避免一支程式搞垮整台機器。

對應第 4 頁：OS 就是硬體與應用程式之間那一層，「vertical」指的是它在那個縱向堆疊裡的位置。

觀點二：資源管理者 It is a resource manager（horizontal，橫向）#

把 OS 看成一個仲裁者，橫向協調多支同時執行的程式去共用有限的資源。

  • Resources：CPU、memory、I/O devices（disks、printers） 這些資源數量有限，卻有很多程式同時想用。

  • Each program gets time with the resource（時間多工，time multiplexing） 多支程式輪流用 CPU，每支拿一小段時間片（time slice）後切換；印表機則是排隊，一份印完再印下一份。

  • Each program gets space on the resource（空間多工，space multiplexing） 記憶體切成多塊分給不同程式同時持有；磁碟空間分配給不同檔案；快取分區。

  • OS makes sure programs have a fair use（確保公平使用） OS 負責排程與配置，讓資源被公平分配，並且互相隔離保護——一支程式不能偷用或破壞另一支程式的資源。

page-07#

這頁用一張「同心圓（洋蔥）圖」畫 UNIX 的分層結構。越外圈越接近使用者、越內圈越接近硬體；要往內走一定要穿過中間那條紅線（System Calls）。這正是第 5 頁「延伸機器（vertical）」觀點的具體展開。

由外往內的每一層（對應右邊的說明框）#

1. applications（應用程式，最外圈）#

  • Written by programmer / Compiled by programmer
  • 使用者自己寫、自己編譯的程式。離硬體最遠，權限最低。

2. shell（外殼）#

  • Interactive interface：使用者跟系統互動的介面
  • Users can issue commands (e.g., ls)：你輸入指令，shell 負責解析，再幫你載入並執行對應的程式
  • 本質上 shell 只是一支特殊的應用程式（命令解譯器），但因為是主要的互動入口，所以單獨畫一圈。

3. System Calls（系統呼叫，紅色分界線）#

  • Application program can request service from kernel：上層程式想用核心的功能（開檔、開行程、送封包…），只能透過這組固定介面進入核心（透過 trap / 軟體中斷，從 user mode 切到 kernel mode）
  • Portable OS layer：因為這組介面規格固定，不同硬體平台上都長一樣，所以程式碼可攜——換機器不用改
  • 這條線就是 user space 與 kernel space 的邊界。

4. kernel（核心，最內圈）#

  • Bootstrap, system initialization：開機載入、系統初始化
  • interrupt and exception：處理中斷與例外
  • process, memory & I/O management：行程排程、記憶體管理、I/O 管理
  • 真正直接操作硬體的部分，權限最高。
NOTE

process=一支正在執行中的程式（a program in execution）

5. library routines（函式庫常式）#

  • Provided pre-compiled object codes：預先編譯好的函式庫（例如 C 標準函式庫）
  • Defined in headers (e.g., stdio.h)：函式原型宣告在標頭檔裡
  • 位置介於應用程式與 system call 之間。有些函式純粹在 user space 做事（如 strcpy、memcpy），有些則是 system call 的包裝（如 printf 最終會呼叫 write 這個 system call）。目的是讓程式設計師不必直接寫 system call。
NOTE

整套 OS 就是「一大堆程式碼、函式庫、工具程式」。而 kernel 就是這一大堆裡面最核心、最特別的那一塊——通常是單一一支程式。

kernel 特別的三件事#

  1. 它是單一一個 binary image

    • binary image = 一支已經編譯好、可以被 CPU 直接載入執行的二進位檔案（不是原始碼，也不是很多支程式檔案的集合）
    • Linux：開機時 bootloader 載入的 /boot/vmlinuz-* 那個檔案
    • macOS 是 XNU、Windows 是 ntoskrnl.exe
    • 不是「一堆程式的集合」，就是一支（雖然可以動態載入驅動模組）

  2. 它跑在特權模式（kernel mode / ring 0）

    • CPU 有一個硬體位元區分 user mode / kernel mode
    • 只有 kernel mode 能執行「特權指令」：改分頁表、關中斷、直接對裝置 I/O port 讀寫、停 CPU…
    • user mode 程式想做這些 → 被 CPU 擋下來（trap）
Trap 是什麼

trap 是 CPU 硬體觸發的一種例外（exception），作用是把控制權從 user mode 安全地交給 kernel mode。發生時 CPU 會：

  1. 存下目前狀態（PC、暫存器）
  2. 把模式位元切成 kernel mode
  3. 跳到 kernel 裡事先設好的固定位址（trap handler）開始執行

它有兩種觸發方式：

  • 主動：程式自己執行 syscall 這類指令，要求 kernel 提供服務（這就是上面 page-07 講的 system call）
  • 被動：user mode 程式想執行特權指令，CPU 檢查目前模式位元後直接擋下來，觸發 trap（程式通常會收到錯誤，如 SIGSEGV）

重點是：user mode 程式不能自己跳進 kernel 程式碼的任意位置，只能透過這些固定入口「借道」進入。

  • 所以唯一能直接碰硬體的程式碼就是 kernel
  1. 它常駐、隨時都在
    • 你的程式會結束；kernel 從開機到關機一直躺在記憶體裡
    • 每次中斷、例外、system call 發生，CPU 就跳進 kernel 的程式碼執行

System call vs. function call#

System call：請 OS 代為執行某項工作（a request to the operating system to perform some activity）。

Function call（dp()）System call（open()）
callee 在哪同一支程式裡kernel 裡
怎麼跳過去一般的 call 指令，可跳到任意位址trap 指令（如 syscall），只能進 kernel 事先設好的入口
執行模式不變，都在 user modeuser mode → kernel mode，做完再切回來
信任關係同一個 user、同一個 domain of trustOS 被信任、user 不被信任，kernel 要檢查參數防止濫用
是哪個 process同一個還是同一個

為什麼右圖把 OS 畫成另一個框#

綠框代表的是 保護邊界（domain of trust），不是 process 的邊界。左圖 caller 和 callee 在同一個框裡，權限相同；右圖的 open() 屬於 kernel，跑在較高權限，user 程式不能直接讀寫 kernel 的記憶體、也不能任意跳進去，所以畫在框外。

IMPORTANT

system call 進 kernel mode 不會 產生新的 process：PID 不變，是 kernel 代替這個 process 執行 open()。所以 page-14 的 sys 時間才會算在這支程式頭上。

Mode switch vs. context switch#

這裡只先比較兩者的差別，context switch 的詳細介紹在 page-29 到 page-43。

Mode switchContext switch
換的是什麼同一個 process 的執行模式（user ↔ kernel）CPU 上跑的 process（A → B）
什麼時候發生每次 system call、中斷、例外scheduler 決定換人：時間片用完、process 被 block（等 I/O、sleep）
要存什麼目前的 PC、暫存器，再切模式位元整個 process 的 CPU 狀態，還要換成另一個 process 的記憶體映射（page table）
成本較低（但也不便宜，見 page-14）較高：換了記憶體映射，cache、TLB 裡的資料多半用不上

兩者的關係：context switch 由 kernel 裡的 scheduler 執行，所以 一定先有 mode switch；反過來，mode switch 不一定會造成 context switch。

  • getpid()：進 kernel 拿到 PID 就回原 process，只有 mode switch。
  • read() 要等磁碟、sleep 5（page-15）：kernel 把這個 process block 起來、改跑別的 process，這時才發生 context switch。

page-11#

User mode 與 kernel mode 的保護機制#

這頁把 page-07「System Calls 是 user space 與 kernel space 邊界」的說法， 用「執行模式（mode of execution）」講得更具體：CPU 到底靠什麼分辨現在准不准碰硬體。

  • Modes of Execution (for protection)：大多數 CPU 至少支援兩種執行模式——特權模式（kernel mode）與非特權模式（user mode），這是整套保護機制的硬體基礎。
  • User mode：process 在此模式下被禁止存取分配給 kernel 或其他 process 的記憶體——這就是一支使用者程式不能直接改到 kernel 的資料結構、也碰不到別的 process 記憶體的原因。
  • 當 user mode 的 process 想用 kernel 提供的服務（例如 system call）時，系統必須暫時切換到 kernel mode——這正是前面 page-07 note 裡 trap 觸發時做的第 2 步（把模式位元切成 kernel mode）。
  • Mode Switch：在 user mode 與 kernel mode 之間切換這個動作本身的名稱。

Example (Example 1)

第 14 頁的動畫把兩段程式碼和 real/user/sys 的定義文字疊在一起了。以下是還原：

這頁其實有兩支程式#

程式 1（上面那段，純計算）

一億次加法，完全沒有 I/O、沒有 system call。

程式 2（被文字蓋住的那段，狂做 I/O）

一百萬次 write()，幾乎不算東西，但一直在做 system call。

題目#

用 shell 的 time -p execfile 去量這兩支程式（time = 執行程式並統計耗時），得到兩組數字：

  • A) real 0.43, user 0.42, sys 0.00
  • B) real 2.99, user 0.04, sys 1.32

問：哪一組對應哪一支程式？

先看被蓋住的三個定義#

欄位意思
real牆上時鐘時間（wall-clock）：從開始到結束的實際經過時間，包含等 I/O、被排程器換下去等別人跑的時間
user這支程式在 user mode 執行自己程式碼所花的 CPU 時間
syskernel 代替這支程式執行 system call 所花的 CPU 時間（kernel mode）

答案#

程式 1（純計算）→ A

  • 一直在跑自己的迴圈 → user 幾乎吃滿（0.42）
  • 沒有任何 system call → sys = 0.00
  • 沒有 I/O 等待、CPU 一路跑到底 → real ≈ user（0.43 ≈ 0.42）

程式 2（一百萬次 write）→ B

  • 自己幾乎沒在算 → user 很小（0.04）
  • 每次 write() 都陷入 kernel 執行 → sys 很大（1.32）
  • real(2.99) 遠大於 user + sys(1.36)：因為 process 常常卡在 I/O（等終端機/pipe 把輸出收走）或被換下去，這段等待時間算進 real，但不算 CPU 時間

這頁想教的觀念#

  1. sys 時間大 = 這支程式很依賴 system call（做很多 I/O）。
  2. system call 很貴：程式 2 幾乎不做事，光是切進切出 kernel 一百萬次就燒掉 1.3 秒。
  3. real ≠ user + sys：中間的差就是「沒在用 CPU、純粹在等」的時間。

Example (Example 2)

這頁在比較「讓程式等 5 秒」的兩種寫法，重點看它們對 CPU 時間的影響。

程式：用 busy wait 等 5 秒#

這支程式什麼事都沒做，就是在迴圈裡不停地問現在幾點，直到過了 5 秒才跳出。這叫 busy waiting（空轉等待）。

量測結果#

寫法realusersys評價
busy wait（上面那支）5.605.500.00bad
time -p sleep 55.000.000.00good

（sleep：延遲指定的時間）

差在哪#

busy wait（爛）

  • 迴圈整整 5 秒都在全速跑 → user ≈ 5.5 秒，CPU 被吃滿
  • 這 5 秒的 CPU 完全浪費：沒算出任何東西，只是一直看時鐘
  • 其他程式因此搶不到 CPU；筆電還會耗電發熱
  • real(5.60) 比 user(5.50) 多一點，是因為這是共用主機，中間 CPU 有分給別人

sleep 5（好）

  • sleep 是跟 kernel 說「5 秒後再叫我」，然後 process 進入 blocked 狀態、被踢下 CPU (sleep 期間 cpu 沒有在運行)
  • 睡著的 5 秒完全不佔 CPU → user、sys 都是 0.00
  • 這段時間 CPU 可以讓給別的程式用
  • real 剛好 5.00，又準又不浪費

這頁想教的觀念#

  1. 程式要「等」的時候應該 block (讓 OS 把自己排程下去)，不要 spin (空轉)。
  2. 空轉的成本會直接反映在 user 時間上——燒的是真正的 CPU；阻塞式等待（sleep、等 I/O、等 semaphore）幾乎不花 CPU。
  3. busy-wait 只有在極少數情況才划算（等待極短、或多核心的 spinlock，此時 context switch 比空轉還貴）。

跟 Example 1 的對照#

  • Example 1：sys 時間大 → 程式做很多 system call / I/O。
  • Example 2：user 時間大到不合理（明明沒在算東西）→ 程式在空轉浪費 CPU。

page-16#

這頁在講什麼#

用 read(fd, buffer, nbytes) 當例子，把一次 system call 拆成 11 個步驟，說明為什麼 system call 很貴（呼應 page-14）。

read(fd, buffer, nbytes)：從檔案 fd 讀最多 nbytes 個 byte 放進 buffer，回傳實際讀到幾個 byte。

  • fd（file descriptor，檔案描述子）：一個小整數，代表這支 process 開著的某個檔案。open() 開檔成功時由 kernel 發給你，之後讀寫都用它指定是哪個檔案。0、1、2 預設是鍵盤輸入、螢幕輸出、錯誤輸出，所以 page-14 的 write(1, ...) 是寫到螢幕。
  • buffer：一塊記憶體，kernel 會把讀到的資料放進來。因為 kernel 要寫進去，所以傳的是它的位址（圖上的 &buffer）。

先補三個背景知識#

1. 暫存器、PC、SP#

  • 暫存器（register）：CPU 內部少量、極快的儲存格。CPU 運算的資料都要先放進暫存器。
  • PC（program counter）：一個暫存器，存「下一條要執行的指令在哪個位址」。CPU 就是不斷照 PC 抓指令、執行、再把 PC 移到下一條。function call 和 trap 本質上都是在改 PC；page-07 note 裡 trap 要先存下 PC，就是為了記住回來時要從哪裡繼續。
  • SP（stack pointer）：一個暫存器，存 stack 頂端的位址。

2. Stack（堆疊）#

  • process 記憶體裡的一塊區域，專門給 function call 用：放參數、區域變數、回傳位址。
  • 像疊盤子，只能從頂端放（push）或拿走（pop）。
  • 大多數機器上 stack 是 往低位址長 的：push 一次 SP 就變小；要丟掉 stack 上的東西，只要把 SP 加回去。
  • function call 怎麼用 stack：
    1. caller 把參數 push 上去
    2. call 指令把 return address（回來後該執行的下一條指令位址）push 上去，再把 PC 改成函式的位址
    3. 函式結束時，ret 指令把 return address pop 回 PC，於是回到原處

3. 這張圖怎麼看#

  • 縱軸是記憶體位址：最上面 0xFFFFFFFF（32 位元能表示的最大位址，約 4 GB），最下面 0。
  • 灰色是 kernel space（kernel 的程式碼與資料），上面白色是 user space（你的程式和 C library）。user mode 下碰不到灰色區（page-11）。
  • 每個框是一條機器指令，不是資料；圖上沒有畫出 stack 本身。
    • 下面那組（User program calling read）：你程式裡 read(fd, buffer, nbytes); 這一行編譯出來的指令。
    • 上面那組（Library procedure read）：C library 裡 read 函式的指令。page-07 說過 library 有些函式是 system call 的包裝，你呼叫的 read 就是這種包裝，不是 kernel 本身。
  • 紅色箭頭與數字是 CPU 執行的順序，也就是 PC 跳到哪裡。同一組裡的指令由下往上執行（位址由小到大）。
  • 兩側的藍色標籤只是各步驟的說明。

11 個步驟#

在你的程式裡（user mode）#

1–3. Push nbytes → Push &buffer → Push fd：把三個參數 push 到 stack，順序和寫的相反。

  • 為什麼反過來：這樣第一個參數 fd 會在最上面，被呼叫的函式永遠能在 stack 頂端往下固定距離的地方找到第 1、第 2、第 3 個參數。像 printf 這種參數個數不固定的函式特別需要這樣：它得先讀到第一個參數（格式字串），才知道後面還有幾個。

4. Call read：普通的 function call（page-10 左圖），跳進 C library 的 read，同時 push return address。到這裡都還沒進 kernel。

在 C library 的 read 裡（user mode）#

5. Put code for read in register：每個 system call 都有一個編號（system call number），例如 x86-64 Linux 上 read 是 0、write 是 1、open 是 2。library 把 read 的編號放進一個約定好的暫存器。

  • 為什麼需要編號：所有 system call 都從 同一個 trap 入口進 kernel（page-07 note：只能從固定入口借道），kernel 要靠這個編號才知道你要哪項服務。

6. Trap to the kernel：執行 trap 指令（x86-64 上叫 syscall），流程就是 page-07 note 講的：存下 PC 與暫存器 → 模式位元切成 kernel mode → 跳到 kernel 設好的固定入口。這一步就是 page-11 的 mode switch。

在 kernel 裡（kernel mode）#

7. Dispatch（分派）：入口處的程式讀出暫存器裡的編號，去查 system call table（一張表，第 n 格存著第 n 號 system call 處理函式的位址），再跳過去。圖中那個橫條紋方塊就是這張表。

8. Run handler：真正做事的 kernel 函式。以 read 為例：

  1. 檢查參數：fd 是不是這個 process 真的開著的檔案、buffer 的位址是不是在這個 process 自己的 user space 裡（page-10：OS 不信任 user）。
  2. 去拿資料。如果資料還沒好（要等磁碟、等鍵盤輸入），kernel 就把這個 process block 起來、先讓別的 process 跑（context switch，見 page-10），資料到了再回來繼續。
  3. 把資料複製進 buffer，把回傳值（讀到幾個 byte，或錯誤碼）放進暫存器。

一路回去#

9. Return to user mode：執行「從 trap 返回」的特殊指令（x86-64 上叫 sysret）：恢復第 6 步存下的狀態、模式位元切回 user mode、PC 回到 library 裡 trap 的下一條指令。

10. Return to user program：library 的 read 執行 ret（普通的函式返回），回到你程式裡 call read 的下一條，回傳值也一起帶回來。失敗時 library 會把錯誤碼存進全域變數 errno，然後回傳 -1。

11. Clean up（Increment SP）：丟掉第 1–3 步 push 的三個參數。因為 stack 往低位址長，丟東西就是把 SP 加回去。

整理#

為什麼 system call 很貴：普通 function call 只有 1–4、10–11 這種動作；system call 還多了 5–9：存與恢復 CPU 狀態、兩次 mode switch、查表、檢查參數、在 kernel 和 user space 之間複製資料。page-14 的程式 2 每次 write 都要走完一整圈，一百萬次就燒掉 1.32 秒的 sys。這也是為什麼 C library 的 printf 會先把字存在 user space，攢夠了才呼叫一次 write。

page-18#

UNIX Architecture#

跟 page-07 的洋蔥圖是同一件事，改畫成由上往下的四層：users → 應用程式 → kernel → 硬體。層與層之間各有一個介面（圖左的三個箭頭）：

  • User interface（users ↔ 應用程式）：使用者操作程式的方式，例如在 shell 打指令、點視窗。
  • System call interface（應用程式 ↔ kernel）：紅線，就是 page-07 那條紅線。應用程式只能透過 system call 進 kernel。
  • Kernel interface to the hardware（kernel ↔ 硬體）：kernel 透過它直接操作硬體，只有 kernel 能碰（page-07「kernel 特別的三件事」）。

圖上其他東西：

  • 最上面一堆 user：UNIX 是多人（multi-user）系統，很多人可以同時登入同一台機器。
  • X：X Window System，UNIX 上的圖形介面（視窗、滑鼠）。它也只是一般的應用程式，在紅線之上。
  • terminal（終端機）：早期接到主機上的一組螢幕加鍵盤，使用者透過它打指令。現在電腦上的「終端機」視窗就是在模擬它。

kernel 那一層列的工作，後面章節會細講，這裡先知道名字在說什麼：

名詞意思
CPU scheduling決定下一個讓哪個 process 用 CPU（page-05 的時間多工）
signal handlingsignal 是送給 process 的通知，例如按 Ctrl-C 會送一個 signal 叫程式結束
virtual memory讓每個 process 以為自己獨占一整段記憶體位址（page-16 圖上的 0 到 0xFFFFFFFF），再由 kernel 對應到真正的實體記憶體
paging把記憶體切成固定大小的「頁」來管理，是實作 virtual memory 的方法
swapping實體記憶體不夠時，把暫時不用的資料搬到硬碟，要用時再搬回來
file system用檔案和目錄來組織硬碟上的資料
disk driversdriver（驅動程式）是 kernel 裡專門操作某一種硬體的程式碼
caching/buffering把常用或剛讀寫的資料暫存在記憶體，減少存取慢速硬碟的次數

page-19#

Resource Manager（horizontal viewpoint）#

回到 page-05 的觀點二：OS 是資源管理者。這頁把 OS 做的事分成兩類。

Services for Application Programs：透過 system call 提供給應用程式用的服務，也就是紅線上方看得到的東西。

  • User Identification：辨識是哪個使用者、有什麼權限
  • Process Management：建立、結束、等待 process
  • Memory Management：向 OS 要記憶體、還記憶體
  • File/Directory Management：開、讀、寫、刪除檔案和目錄
  • Inter-process Communication（IPC）：process 之間互相傳資料
  • Signal：送出、接收 signal（page-18）
  • I/O Management：操作終端機、網路等裝置

OS Kernel：kernel 內部為了提供上面那些服務要做的事，應用程式看不到。

  • CPU Scheduling、Virtual Memory、File System：見 page-18
  • Protection：控制誰能存取哪些資源，例如 process 不能碰別人的記憶體（page-11）
  • Security：防禦攻擊，例如密碼驗證、擋掉沒有權限的登入
  • Synchronization：多個 process 同時存取同一份資料時，協調先後順序，避免資料錯亂
  • I/O Control：實際對硬體下指令

下面的硬體圖#

一台 PC 的硬體：CPU、Memory 和各種裝置都接在同一條 bus 上（page-04 的 system bus）。每個裝置前面都有一個 controller（控制器），它是真正操作裝置的一塊晶片。CPU 透過 bus 對 controller 下指令，不直接控制裝置；kernel 裡的 driver（page-18）就是負責跟某一種 controller 溝通的程式碼。

這些裝置就是 OS 要管理、分給各個 process 共用的「資源」。
