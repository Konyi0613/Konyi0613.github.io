stat、fstat、lstat#

ch03 page-15 說過，一個檔案 = content + metadata。content 用 read 拿；metadata 用 stat、fstat、lstat 這三個函式拿。它們把檔案的 metadata 複製一份到你準備好的 struct stat 裡（欄位見 page-07）：

三個做的事一樣，差在怎麼指定檔案：

函式用什麼指定檔案pathname 是 symbolic link 時
statpathname跟過去，拿 目標檔案 的資訊
fstat已經開好的 fd不會遇到：open 時就已經跟過去了
lstatpathname不跟過去，拿 link 本身 的資訊

symbolic link（符號連結）是一種特殊檔案，內容是「另一個檔案的路徑」，類似 Windows 的捷徑。kernel 解析路徑時碰到它，會把那條路徑代進去繼續找，所以大部分程式根本感覺不到中間經過了一個 link。例如：

  • open("link.txt", ...) 會跟過去，拿到的 fd 指向 real.txt：read 讀到 hello，write 改的也是 real.txt。所以 fstat(fd) 只看得到目標，上表才說它不會遇到 link。
  • stat("link.txt") 拿到 real.txt 的資訊（regular file，size 6）；lstat("link.txt") 拿到 link 本身的資訊（file type 是 symbolic link，size 8，正好是 real.txt 這 8 個字元）。
  • 把 real.txt 刪掉，link.txt 還在，只是指向不存在的東西（dangling link）：open 和 stat 都失敗、errno 是 ENOENT，lstat 仍然成功。

symbolic link 為什麼存在、跟 hard link 差在哪、哪些函式會跟過去，page-50～page-57 會細講。

stat、fstat、lstat 成功都回傳 0，失敗回傳 -1 並設 errno。

圖是 ch03 page-09 那張全圖，這次紅圈圈著 v-node table：stat 讀的就是那裡的 i-node 資訊（i-node 是 kernel 存放一個檔案 metadata 的結構，ch03 page-09 用過這個名字；它在磁碟上長什麼樣，是這章後半的主題）。fstat 順著 fd → open file table → v-node 走到它；stat 不需要 fd，kernel 照路徑查目錄找到 i-node 直接讀。

stat 不會 open 這個檔案：不會配 fd，也不會在 open file table 裡建一項。kernel 只是在記憶體裡找這個檔案的 i-node 副本，沒有的話就從磁碟讀進來，把欄位複製到 struct stat，就結束了。圖上圈 v-node table，意思是 metadata 在 kernel 記憶體裡的那份，不代表檔案被開著。

因為讀的是 metadata 而不是內容，stat 不需要檔案的讀取權限，只需要路徑上每一層目錄的 x 權限（page-13）。所以 ls -l 看得到一個你讀不了的檔案有多大、屬於誰。

page-08#

File Types#

UNIX 把很多東西都當成檔案（ch01 page-53），所以「檔案」分好幾種，st_mode 記著它屬於哪一種：

regular file一般檔案。kernel 不分文字檔或執行檔，內容就是一串 byte，怎麼解讀是程式的事/etc/passwd、a.out
directory file內容是一張 {(filename, pointer)} 的表，pointer 就是 i-node number（右上角那張表）。只有 kernel 能寫/etc
character special file代表一個 character device：資料是一串 byte 的資料流，依序讀寫，一次傳幾個 byte 由呼叫者決定終端機 /dev/tty、序列埠、音效卡
block special file代表一個 block device：資料是一串有編號、大小固定的 block，可以直接讀寫任一個 block硬碟 /dev/sda、SSD
FIFOnamed pipe：有檔名的 pipe，讓沒有親屬關係的 process 也能用 pipe 溝通（ch15 page-86）/dev/initctl
socketprocess 之間（同一台或跨網路）溝通的端點/dev/log，ch16 page-39
symbolic link內容是另一個路徑的檔案/dev/cdrom，page-50

file system 要能直接讀第 n 個 block，所以只能建在 block device 上。

為什麼 directory 只有 kernel 能寫？ directory 那張表要是被寫壞（例如指向不存在的 i-node），整個 file system 就亂了。所以不能對 directory 呼叫 write，只能透過 creat、unlink、rename、mkdir 這些 system call 間接修改，由 kernel 保證表永遠是對的（page-66）。

投影片說 socket、symbolic link「not POSIX.1 or SVR4」是很舊的資料，POSIX.1-2001 之後兩者都在標準裡了。

Access Permissions：9 個 permission bit#

file type 講完，接著看 st_mode 的另一部分。所有檔案都有權限，記在 st_mode 的低 9 bit（page-09），分 owner、group、other 三組。這些常數在 ch03 page-23 建檔時用過，這頁多了每組的「全部」：

全部readwriteexecute

groupS_IRWXG = 00070S_IRGRP = 00040S_IWGRP = 00020S_IXGRP = 00010

page-13#

Operations vs. Permissions#

同樣是 r、w、x，對 directory 和一般檔案的意思不同（ch01 page-55 最後那行提過）。原因在於 directory 的內容是右上角那張「檔名 → i-node number」的表，所以它的 r、w、x 都是在講 對這張表能做什麼：

directoryfile
r讀這張表：列出底下有哪些檔名（ls、page-66 的 readdir）用 O_RDONLY 或 O_RDWR 開
w改這張表：新增、刪除、改名 entry用 O_WRONLY、O_RDWR 或 O_TRUNC 開（O_TRUNC 會清掉內容，所以也算寫）
xsearch bit：拿一個檔名查表、找到它的 i-node，也就是「穿過」這個目錄用 exec 執行它，而且必須是 regular file

directory 的 x 用在路徑的每一層。 open("/usr/include/stdio.h", O_RDONLY) 要先在 / 查 usr、在 /usr 查 include、在 /usr/include 查 stdio.h，每一步都是查表，所以 /、/usr、/usr/include 三個目錄都要有 x。任何一層少了 x，就算 stdio.h 是 0644 也開不了。

r 和 x 是兩回事：只有 r 沒有 x，看得到裡面有哪些檔名，但 stat、open 不了裡面的檔案（ls -l 會印出一排 ?）；只有 x 沒有 r，列不出內容，但知道確切檔名就能直接開。

  • 只有 r：ls d 只要讀目錄的表，所以列得出 file。ls -l 還要對每個名字 stat，這需要 x 才能穿過 d，所以除了檔名以外全是 ?；cat 要 open，同樣失敗。
  • 只有 x：讀不了表，ls d 和 ls -l d 都失敗：ls -l 得先讀表知道有哪些名字，才能對它們 stat；但直接給完整路徑 d/file，kernel 只要在表裡查這個名字，x 就夠了，所以 stat 和 open 都成功。

規則：r 只讓你讀目錄那張表，知道裡面有哪些檔名；要拿到目錄裡某個檔案的 i-node 資訊，那個目錄就必須有 x。stat 要讀 i-node 裡的屬性，open 要從 i-node 找到內容在哪，chdir 要切到那個目錄的 i-node，所以都需要 x。路徑上每一層都一樣：d 只有 r 時，d/sub/f 也開不了，因為拿不到 sub 的 i-node，就算 sub 和 f 的權限都是開的。

建檔和刪檔要對目錄有 w+x。 只有 w 不夠，因為改表之前一定要先查表：touch w/new 得先在 w 的表裡查 new 存不存在（存在就直接打開，不存在才新增），rm w/old 得先找到 old 那筆 entry 才能拿掉。查表是 x，改表是 w。就算已經 cd 進目錄、用相對路徑 touch new，也是在 cwd 的表裡查，一樣要 x。

刪檔時 檔案本身的權限不重要：刪掉一個檔名只是從目錄的表裡拿掉一筆 entry，根本沒碰到檔案（ch01 page-56 的 unlink）。rm 遇到唯讀檔案會先問你，那是 rm 自己好心，kernel 並不在乎。

那內容什麼時候被清掉？unlink 拿掉名字時，i-node 的 link count 減 1；要等 link count 變 0、而且沒有 process 開著這個檔案，kernel 才把它的 i-node 和 data block 標記成可用，還給 file system。標記而已，block 裡的資料不會被覆寫，之後被分給新檔案時才會蓋掉。兩個計數和三種狀態見 ch03 page-15，unlink 的細節在 page-52，page-53～54 用 df 實際量了一次空間什麼時候釋放。

投影片黃字的問題：/tmp 人人都有 w，那豈不是誰都能刪掉別人放在 /tmp 的檔案？ 照上面的規則確實如此，答案在 page-32 的 sticky bit。

page-14#

改密碼的難題：一個 process 有好幾個 ID#

page-12～13 講了 permission bit：owner、group、other 各有一組 rwx。但 kernel 檢查權限時，要拿 誰 來跟檔案的 owner（st_uid）和 group（st_gid）比？答案是 發出這個 system call 的 process。每個 process 身上都記著它代表哪個 user、哪個 group，kernel 拿這些 ID 跟檔案的 st_uid、st_gid 比，決定要看 owner、group 還是 other 那組 bit（完整規則在 page-21）。

直覺上，process 的身分就是執行它的那個人。但這樣會遇到一個問題。看兩個系統檔案（ch01 page-22）：

  • /etc/passwd：帳號清單，每個 user 一行，記著 UID、GID、home 目錄等等。很多程式要查它，所以人人可讀。
  • /etc/shadow：每個帳號加密後的密碼，只有 root 讀得到。

兩個檔案的 owner 都是 root，一般使用者完全不能寫。可是任何人都能用 passwd 指令改自己的密碼，而改密碼就是改 /etc/shadow 裡自己那一行。如果 process 的身分就是執行它的人，那你執行的 passwd 只有你的權限，根本寫不了 /etc/shadow。它是怎麼做到的？

解法是把身分拆開：一個 process 身上不只一組 ID，「實際是誰在跑」和「檢查權限時用哪個身分」是分開記的：

ID代表用途
real user ID、real group IDwho we really are：實際執行這個 process 的人記錄是誰在跑，權限檢查不看它
effective user ID、effective group ID、supplementary group IDs檢查檔案權限時用的身分kernel 拿它跟 st_uid、st_gid 比（page-21）
saved set-user-ID、saved set-group-IDexec 時存下的 effective ID 副本讓程式可以暫時放下權限、之後再拿回來（page-15）

平常 real 和 effective 一樣，所以感覺不到差別。passwd 的做法就是讓兩者不一樣：你執行它時，real user ID 還是你，effective user ID 卻變成 root。

  • kernel 看 effective user ID 檢查權限，所以 passwd 寫得了 /etc/shadow。
  • passwd 自己看 real user ID，知道是誰在執行，只讓你改自己的密碼。

怎麼讓 effective user ID 變成 root，就是 page-16 的 set-user-ID。

page-15#

Real、Effective、Saved ID 從哪來#

page-14 說每個 process 身上帶著三組 ID。這頁回答：這些 ID 一開始是誰設的？之後什麼時候會變？

順著你登入、執行程式的過程看：

  1. 登入：login 程式驗證完密碼，到 /etc/passwd 找到你那一行，把 process 的 user ID、group ID 設成第 3、4 欄（UID、GID），supplementary group IDs 設成你在 /etc/group 裡所屬的 group，然後 exec 你的 shell。此時 real 和 effective 都是你。
  2. 在 shell 裡執行程式：shell 先 fork，child 繼承 parent 的所有 ID；再 exec 那支程式。所以你跑的每支程式，real user ID 都是你。
  3. exec 時：一般的程式，effective ID 維持不變，還是你；如果程式檔設了 set-user-ID，effective user ID 會換成程式檔的 owner（page-16）。換完之後，kernel 再把 換過之後 的 effective user ID 複製一份，存成 saved set-user-ID。所以執行設了 set-user-ID 的 passwd 時，saved set-user-ID 是 root（程式檔的 owner）；執行一般的程式時，effective user ID 沒換，saved set-user-ID 就是你。

set-user-ID 是檔案上的一個 bit：程式檔 st_mode 裡的 S_ISUID（八進位 04000），存在檔案的 i-node 上，跟 rwx 一樣用 chmod 設定（chmod u+s、chmod 4755）。它平常不做任何事，只有 kernel exec 這個檔案時會檢查：

注意名字很像的兩樣東西是不同層次的：set-user-ID 是 檔案 的一個 bit；saved set-user-ID 是 process 身上的一個 ID 值。後者叫這個名字，是因為它原本就是用來記住 set-user-ID 程式 exec 後拿到的那個 effective user ID。

從哪來什麼時候會變

saved set-user／group-IDexec 時複製當時的 effective ID每次 exec

supplementary group IDs：一個使用者可以同時屬於好幾個 group。主要的那個是 /etc/passwd 第 4 欄的 GID；其他的記在 /etc/group，每行是「group 名稱:密碼:GID:成員列表」，例如 sudo:x:27:alice 表示 alice 屬於 sudo 這個 group。密碼欄是這個 group 的密碼：不在成員列表裡的人，可以用 newgrp sudo 輸入這個密碼，暫時加入這個 group。寫 x 表示真正的密碼放在只有 root 讀得到的 /etc/gshadow，跟 /etc/passwd 和 /etc/shadow 的關係一樣；現在幾乎沒人設 group 密碼。

它怎麼設定：

  • 登入時：login 還是 root 身分時，掃一遍 /etc/group，把成員列表裡有你的 group 全部收集起來，用 setgroups 設成 process 的 supplementary group IDs（initgroups 這個函式包好了這一步）。之後 fork、exec 一路繼承。
  • 之後改不了：setgroups 只有 superuser 能呼叫，一般 process 不能替自己加 group。
  • 管理者把你加進 group：usermod -aG sudo alice 改的是 /etc/group，已經在跑的 process 不受影響，要重新登入才會生效。

檢查權限時，你所屬的 每一個 group 都可以用：檔案的 group 只要是其中任何一個（主要 group 或任一個 supplementary group），kernel 就把你當成這個檔案的 group 成員，看 group 那組 bit（page-21 第 3 條）。例如 alice 屬於 alice、sudo、users 三個 group，一個 group 是 users、權限 rw-rw---- 的檔案，alice 就能用 group 那組的 rw- 讀寫它，不必是主要 group。

saved set-user-ID 存在的理由：以 passwd 為例，它的 effective user ID 是 root，但只有最後寫 /etc/shadow 那一步需要 root 權限，其他步驟（讀使用者輸入、檢查新密碼夠不夠強）都不需要。帶著 root 權限做這些事，萬一程式有 bug 就可能被利用。比較謹慎的做法是：

  1. 一開始就把 effective user ID 降回 real user ID，只用使用者本人的權限做事。
  2. 真的要寫 /etc/shadow 時，再把 effective user ID 換回 root。

問題是第 2 步：一般使用者的 process 不能隨便把 effective user ID 設成 root，否則誰都能變成 root。kernel 只允許換回 saved set-user-ID 裡記著的那個值，因為那代表「這個 process 本來就合法拿過這個身分」。所以沒有 saved set-user-ID，降下去就回不來了。實際的函式（setuid、seteuid）在 Ch8。

舊版 POSIX 把 saved ID 列為選配，所以投影片說可以在編譯時檢查 _POSIX_SAVED_IDS，或執行時呼叫 sysconf(_SC_SAVED_IDS)（page-37）。現在的 POSIX 已經規定一定要有。

page-16#

Set-User-ID 與 Set-Group-ID#

page-14 的問題還沒解決：你執行 passwd，effective user ID 要怎麼變成 root？page-15 說 effective ID 只在 exec 時可能改變，改變的條件就是這頁的 bit。

set-user-ID 是執行檔上的一個 bit（st_mode 裡的 S_ISUID）。設了它的檔案被 exec 時，kernel 把 process 的 effective user ID 換成這個檔案的 owner，而不是執行它的人。real user ID 不變。

set-group-ID（S_ISGID）同理：exec 時 effective group ID 換成程式檔的 group（st_gid），saved set-group-ID 也記成這個值；real group ID 和 supplementary group IDs 不變。看的是 檔案的 group，不是 owner 的：一個檔案只有一個 group，就算 owner 同時屬於好幾個 group，執行的人拿到的也只有檔案的那一個。檔案屬於哪個 group，由建檔時的規則決定（page-22），owner 也可以用 chgrp 改成自己所屬的任何一個 group（page-35）。

回到 page-14 的問題。/usr/bin/passwd 屬於 root 並設了 set-user-ID，所以：

時間點檢查什麼當下的 effective user ID
① 你 exec /usr/bin/passwd能不能 執行 passwd 這個程式檔（passwd 對 other 有 x，通過）還沒換，是 你（從 shell 繼承來的）
② 通過後，kernel 把 effective user ID 換成 0（root），real user ID 還是你，程式開始跑——
③ passwd 呼叫 open("/etc/shadow", O_WRONLY)能不能 寫 /etc/shadow（是 0，通過，page-21）已經換成 root

① 和 ③ 是兩次不同的檢查，但規則一樣：kernel 一律看 process 當下 的 effective user ID。① 問「你能不能啟動這支程式」，發生在換之前，所以看到的是你；③ 是程式跑起來後開的檔案，發生在換之後，所以看到的是 root。set-user-ID 就是在兩者之間換身分：你只要有權限 啟動 這支程式，它啟動後就能用 owner 的權限 做事。

passwd 自己則看 real user ID 知道是誰在執行，只讓你改 你自己 的密碼。

這樣權限交出去了，但只透過一支可信任的程式交出去：使用者能做的事，就是 passwd 這支程式允許的那些。這也是為什麼 bit 設在 執行檔 上，而不是設在使用者身上：借出權限的單位是一支程式，程式寫好什麼能做、什麼不能做，使用者沒辦法拿這份權限去做別的事。

page-18～19#

Real 與 Effective User ID 的例子#

用一個具體場景，比較同一支程式有沒有設 set-user-ID，權限檢查的結果差在哪。兩頁同一個場景，只差 A1 的權限：

  • File A1：執行檔，owner 是 user A。
  • File A2：資料檔，owner 是 user A，權限 0400（只有 owner 能讀）。
  • user B 執行 ./A1，A1 嘗試讀 A2。

page-18：A1 是 0755。 沒有 set-user-ID，所以 process 的所有 ID 都是 B。檢查 A2：effective user ID 是 B，不是 owner A；B 也不在 A2 的 group 裡；只剩 other 那組，而 0400 的 other 是 ---。結果 讀不了。如果 A2 改成 0644，other 有 r，就讀得了。

page-19：A1 是 4755。 有 set-user-ID，exec 時 effective user ID 換成 A1 的 owner，也就是 A；real user ID 仍是 B。檢查 A2：effective user ID 是 A，等於 owner，看 owner 那組 r--，讀得了。

重點：權限檢查看 effective user ID；real user ID 只記錄是誰在跑。

這也表示 A 必須信任 A1：設了 set-user-ID，就等於讓任何執行它的人借用 A 的身分，A1 能做什麼，那個人就能做什麼。

page-21#

File Access Test#

page-18～19 用例子看了權限怎麼檢查，這頁是完整的規則。每次 process 開檔、建檔或刪檔，kernel 依序檢查，在第一個符合的情況就停下：

  1. effective user ID 是 0：superuser（root），直接允許。
  2. effective user ID 等於檔案的 owner：看 owner 那組 bit，允許就過，不允許就拒絕。
  3. effective group ID 或任一個 supplementary group ID 等於檔案的 group：看 group 那組 bit。
  4. 以上都不是：看 other 那組 bit。

「第一個符合就停」有個反直覺的結果：owner 那組不允許時，不會再往下看 group 和 other。例如你自己的檔案權限是 ----r--r--，別人都能讀，你自己反而讀不了（你當然可以 chmod 改回來，page-28）。

檢查的對象依動作而定：open 檢查檔案本身的 bit；建檔、刪檔檢查的是所在目錄的 w+x（page-13）；而路徑上每一層目錄都要先通過 x 的檢查。

課堂故事：關掉 w 之後，成績還是被改了

一位老師在登記考試成績，登記到一半發現檔案的 other 開著 w，趕快 chmod o-w，再檢查一次內容，沒有被改過。可是隔天回來一看，有成績被改掉了。為什麼？

因為 權限只在 open 時檢查一次。某個學生趁 other 還有 w 時 open 了這個檔案，拿到一個寫入用的 fd。老師之後的 chmod 只改了 i-node 裡的權限 bit；學生的 fd 早就接好「fd → open file table → v-node」這條路（ch03 page-09），之後的 write 只看這個 fd 當初是不是用寫入模式開的，不會再檢查檔案現在的權限。學生只要讓這個 process 一直開著，等老師檢查完再改就行了。

所以 chmod 擋得住之後新的 open，擋不住已經開著的 fd。發現權限開錯時，比較安全的做法是把內容複製成一個新檔案（新的 i-node），設好權限再蓋掉舊檔名，讓舊的 fd 寫不到新檔案裡。

註記的 IEEE 1003.1-1990 就是 POSIX.1（ch03 page-03）：supplementary group 也算數，是從這版標準開始規定的。相關指令 chmod、umask 分別在 page-28 和 page-26。

    1. 建檔 process 的 effective group ID。
    2. 新檔所在目錄的 group ID。

第 2 種適合共用目錄：例如專案目錄屬於 group proj 並設了 set-group-ID，誰在裡面建檔，檔案都自動屬於 proj，組員都能存取。投影片的例子 /var/spool/mail（存放每個人信件的目錄）也是這樣，信件檔都屬於 group mail，負責投遞信件的程式才處理得到。

page-23#

access#

問題：set-user-ID 程式會帶來一個新的風險。一支 set-user-ID 為 root 的程式，effective user ID 是 0，open 什麼都打得開。假設它是一支印表程式，使用者叫它印 /etc/shadow，它就會照印，使用者等於借它的手讀到了自己本來讀不了的檔案。所以這種程式在打開 使用者指定 的檔案之前，需要先問：「使用者本人有沒有權限讀這個檔案？」可是 kernel 的權限檢查一律看 effective ID（page-21），open 回答不了這個問題。

access 就是為此設計的：它照 page-21 的流程檢查權限，但用的是 real user／group ID，而不是 effective。也就是問：「執行我的那個人，自己有沒有權限碰這個檔案？」

mode檢查
R_OK能不能讀
W_OK能不能寫
X_OK能不能執行
F_OK檔案存不存在

R_OK、W_OK、X_OK 可以用 | 組合。access 全部通過回傳 0，否則回傳 -1（沒權限是 EACCES，檔案不存在是 ENOENT）。

先 access 再 open 有空檔

access 和 open 是兩次 system call，中間有空檔：攻擊者可以在 access 通過之後、open 之前，把檔名換成一個指向 /etc/shadow 的 symbolic link。這就是 ch03 page-18 提過的 TOCTTOU。比較安全的做法是暫時把 effective user ID 降成 real user ID 再直接 open，讓 kernel 用使用者本人的身分檢查；之後再靠 saved set-user-ID 換回來（page-15）。

page-24～25#

chmod、fchmod#

改 已經存在 的檔案的權限：chmod 用路徑指定，fchmod 用已經開好的 fd。成功回傳 0，失敗 -1。投影片說 fchmod 不在 POSIX.1 裡，那是舊資料，現在已經是標準了。

跟 page-26 的 umask 一樣，chmod 這個名字也同時指兩樣東西：這頁講的是 system call chmod()；你在 shell 打的 chmod 755 file 是另一支 獨立的程式 /usr/bin/chmod，它把參數解析完，再呼叫 chmod()。不同的是，chmod 指令 不需要 內建在 shell 裡：它改的是檔案的 i-node，存在磁碟上，不是 process 的屬性，所以由 child process 去改，shell 之後一樣看得到結果。

  • 誰能改：只有兩種 process 能 chmod 一個檔案：effective user ID 等於這個檔案的 owner，或是 superuser。
    • 對檔案有 w 權限 不夠。w 允許的是改檔案的 內容；權限記在 i-node 裡，屬於檔案的 metadata，不歸 w 管。
    • 為什麼要這樣規定：假設 alice 的檔案是 rw-rw-r--，group 裡的 bob 能寫它。如果有 w 就能 chmod，bob 就能把它改成 rwxrwxrwx，讓所有人都能讀寫，甚至把 alice 自己的權限拿掉。決定誰能存取一個檔案，只有 owner 能做。
  • mode：page-29 的常數用 | 組合，包括三個特殊 bit S_ISUID、S_ISGID、S_ISVTX。
  • mode 是 絕對值，直接取代原本的 12 個 bit；只想改其中幾個，要先 stat 讀出來再改（page-31）。
  • chmod 不受 umask 影響：umask 只管建新檔。

chmod 會自動清掉的 bit#

chmod 改的是 i-node，不碰內容，所以只有 ctime 會變（page-58）。

另外，有幾種情況 kernel 會 默默清掉 特殊 bit，chmod 照樣回傳成功。三條規則都是為了不讓一般使用者藉此拿到不該有的權限：

  1. 非 superuser 對 regular file 設 sticky bit：sticky bit 被清掉。它在執行檔上的舊意義（page-32）會佔用系統的 swap 空間，所以只有 superuser 能設。現在的 OS 已經不做這件事了：sticky bit 在一般檔案上已經沒有作用，清不清都無所謂。Linux 不清，一般使用者 chmod 1644 會得到 -rw-r--r-T。
  2. 檔案的 group 不是自己的 group 時設 set-group-ID：檔案的 group 既不是 process 的 effective group ID、也不在 supplementary group IDs 裡，而且不是 superuser，set-group-ID 被清掉。
  3. 非 superuser 寫入一個 set-user-ID／set-group-ID 檔案：寫入後這兩個 bit 被清掉。

第 2 條對應左邊的圖：process P（effective group ID 3）在目錄 D（group 5，設了 set-group-ID）裡建了 F，F 照 page-22 的規則屬於 group 5，可是 P 根本不在 group 5。如果 P 能把 F 設成 set-group-ID，任何人執行 F 都會拿到 group 5 的權限，等於 P 送出了一個它自己沒有的身分。

第 3 條的理由類似：有寫入權限的人如果能改內容又保留 bit，就能把 set-user-ID 程式換成自己寫的程式碼，然後以 owner 的身分執行。

page-32#

Sticky Bit（S_ISVTX）#

sticky bit 有一新一舊兩種意義：

先說明 swap area：它是硬碟上保留給 kernel 用的一塊空間，通常是一個獨立的 partition（page-43 的 hda3 就是）。實體記憶體不夠時，kernel 把暫時用不到的記憶體內容搬到這裡，要用時再搬回來，就是 ch00 page-18 的 swapping。swap area 不是 file system：沒有目錄、檔名、i-node，kernel 自己記著每份資料放在哪幾個連續的 block，直接讀寫，所以比透過 file system 找一個檔案再讀出來快。

舊意義：設在執行檔上，saved-text bit。 程式結束後，把它的 text（機器碼，ch01 page-51）留一份在 swap area，下次啟動直接從那裡載入，比從 file system 讀快。

為什麼會比較快：以前的硬碟讀寫頭要移到資料所在的位置，存取 不連續 的位置非常慢（ch03 page-05 的 seek time）。程式檔在 file system 裡，它的 block 可能散在磁碟各處（page-46），每次啟動都要讀寫頭跳來跳去；swap area 則可以把整段 text 連續 存在一起。所以第一次執行之後，把 text 連續放進 swap area，之後每次啟動都能一口氣快速讀進來。當年給編輯器、編譯器這種常用程式用，「sticky」就是「黏在記憶體附近不走」。有了 virtual memory 和夠快的 file system 之後就不需要了，Linux 直接忽略它。

新意義：設在目錄上。 目錄裡的檔案只有在你對目錄有 w+x（page-13），而且 符合下面其中一項時，才能刪除或改名：

  • 你是這個檔案的 owner
  • 你是這個目錄的 owner
  • 你是 superuser

這就是 page-13 那個問題的答案。/tmp 給所有人 w+x（rwxrwxrwt），因為大家都要在裡面建暫存檔；但刪檔只需要對目錄有 w+x，沒有 sticky bit 的話誰都能刪別人的檔案。設了 sticky bit 之後，每個人只能刪自己的。

投影片說它不在 POSIX.1 裡；現在它是 POSIX 的 XSI 擴充的一部分，各系統都支援目錄上的用法。

chown、fchown、lchown#

（投影片寫成 gid_t, grp，多了一個逗號。）

chown、fchown、lchown 改檔案的 owner 和 group，三者的差別跟 page-06 的 stat 家族一樣：fchown 用 fd；lchown 遇到 symbolic link 時改的是 link 本身，不跟過去（page-57）。投影片說 lchown 是 SVR4 獨有，同樣是舊資料，現在是 POSIX 標準。

page-35#

誰能改 owner：_POSIX_CHOWN_RESTRICTED#

如果 _POSIX_CHOWN_RESTRICTED 生效（各 file system 可能不同，用 pathconf 查，page-37；Linux 一律生效）：

  • 只有 superuser 能改檔案的 owner。
  • 一般使用者能改檔案的 group，條件是：
    • 這個 process 是檔案的 owner（effective user ID 等於 owner），而且
    • owner 參數是 -1 或檔案目前的 owner（也就是不改 owner），而且
    • group 參數是自己的 effective group ID 或 supplementary group ID 之一。

白話：別人的檔案，你不能動它的 owner；自己的檔案，只能把 group 改成你所屬的 group。

如果 沒生效（早期的 System V 就是這樣），規則寬鬆很多：檔案的 owner 可以把 owner 和 group 改成任何值，包括把檔案送給別人、改成自己不屬於的 group。不是 owner 的人一樣什麼都不能改，superuser 則兩種情況下都能改。

為什麼生效時連「把自己的檔案送給別人」都不准？因為系統會依 owner 計算每個人用了多少磁碟空間（disk quota），能把檔案送人就能規避上限；也可能設一個陷阱程式再把 owner 改成別人，讓檔案看起來是對方建的。

另外，非 superuser 呼叫 chown 成功時，set-user-ID 和 set-group-ID bit 會被清掉。投影片只寫了 set-group-ID；Linux 對執行檔兩個都清，而且 superuser 呼叫也一樣會清。所以 page-24～25 裡 root 要先 chown 再 chmod u+s，順序反過來，剛設好的 bit 就被 chown 清掉了。

接下來三頁暫時離開權限，插進課本 Ch2 的 limits，因為後面的 page-38 path_alloc 和 page-73 getcwd 需要知道「一條路徑最長多長」。

程式常需要知道系統的上限：檔名最長幾個字、一個 process 最多開幾個檔案。這些上限分兩種：

什麼時候確定例子怎麼拿
compile-time編譯時就固定，寫在 header 裡short 的最大值（<limits.h> 的 SHRT_MAX）、陣列大小#include 進來直接用

為什麼有些上限要執行時才問？同一個執行檔會在設定不同的機器上跑，而同一台機器上也會掛著不同的 file system（page-43），檔名長度上限各不相同，編譯時無從得知。

有些 run-time 上限是 indeterminate（沒有確定值），例如某些系統上的 _SC_CHILD_MAX，取決於當下的系統資源。遇到這種情況 sysconf、pathconf 會用特殊方式回報（page-37），程式只能自己猜一個值（page-38）。最後一行 Remark 的意思是：這些數字都依實作而定，不要寫死在程式裡。

（GNU 的 du 預設以 1024 byte 為單位，在 Linux 上跑會是投影片數字的一半。）

反過來：實際佔用也可能比 st_size 大

file system 配空間的單位是一整個 block，檔案最後一個 block 就算只用到幾個 byte，也是整塊配給它。所以沒有 hole 的小檔案反而是 st_blocks × 512 大於 st_size：在 block size 4096 的 ext4 上，一個只有 10 byte 的檔案，st_size 是 10，st_blocks 是 8（8 × 512 = 4096）。

block 和檔案內容也不是一對一

上面「一個 block 只給一個檔案用」是最常見的做法，但不是每個 file system 都這樣，有兩個方向的例外：

  • 很多小檔案擠同一個 block。 為了不讓小檔案每個都浪費大半個 block，有些 Unix file system 會把多個小檔案的內容塞進同一個 block。例如 BSD 的 FFS 把 block 再切成 fragment，好幾個檔案的尾巴可以共用一個 block；ext4 甚至能把很小的檔案直接存在 i-node 裡，一個 data block 都不用。
  • 大檔案要額外的 block 記結構。 檔案大到 i-node 裡的指標放不下時，要另外配 block 專門存「內容放在哪些 block」的指標，就是 page-48 的 indirect block。這些 block 不放檔案內容，但一樣算在 st_blocks 裡，所以大檔案的 st_blocks × 512 會比內容本身再多一點。

truncate、ftruncate#

truncate（用路徑）和 ftruncate（用 fd）把檔案大小設成 length：

  • length 比原本小：超過的部分丟掉。
  • length 比原本大：檔案變長，多出來的部分讀起來是 0。SVR4 的做法是用 hole 補上，不配 block；4.3+BSD 則只能縮短。現在 POSIX 規定的是 SVR4 的行為。

ch03 page-17 的 O_TRUNC 就是 length = 0 的特例。投影片說 truncate、ftruncate 不在 POSIX.1 裡，同樣是舊資料。

最後一行：Solaris 能用 fcntl 的 F_FREESP 釋放檔案中間任意一段，也就是在已有的檔案裡挖出 hole。Linux 對應的是 fallocate 加 FALLOC_FL_PUNCH_HOLE。

每個 partition 都有 boot block，為什麼只有 hda1 標 *？

page-42 說每個 file system 開頭都有 boot block，這是 格式統一：每個 file system 都預留這塊位置，但只有真的拿來開機的那個會在裡面放程式，其他的空著不用。

開機時電腦要決定用 哪一個 boot block，靠的就是 *。整顆磁碟最前面還有一個 sector 叫 MBR（Master Boot Record），不屬於任何 partition，裡面放 partition table（就是 fdisk -l 印出來的那張表）和一小段開機程式。開機流程是：

  1. BIOS 讀進 MBR，執行裡面那段程式。
  2. 那段程式查 partition table，找到標成 可開機（active） 的 partition，也就是 Boot 欄有 * 的 hda1。
  3. 讀進 hda1 的 boot block 並執行，由它再去載入 kernel。

所以 * 是 partition table 裡的一個旗標，不是說只有 hda1 有 boot block，而是「開機時用 hda1 的那一份」。hda1 被掛在 /boot，裡面放 kernel 檔案和開機設定，boot block 的程式載入的就是這裡的 kernel。

（這是投影片那個年代的 BIOS 開機方式。現在的電腦大多用 UEFI：它直接讀一個 FAT 格式的 partition 裡的開機程式，也就是 page-41 例子中掛在 /boot/efi 的那個，不再看 boot block 和 *。）

圖上的箭頭：

  • 中間那個 i-node 往上指向三個 data block：這個檔案的內容放在這三塊。
  • 兩個 dir block 裡各有一筆 entry 指回 同一個 i-node：同一個檔案有兩個名字，這就是 hard link（硬連結，page-50），它的 link count 是 2。

i-node 是固定大小的（Version 7 是 64 byte、4.3+BSD 是 128 byte，ext4 是 256 byte），裡面有 file type、權限、大小、data block 在哪等等，也就是 struct stat 裡的東西。少了兩樣：檔名（在目錄裡）和 i-node number 本身（它在 i-list 裡的位置就是編號）。

Moving files among directories#

mv 底下有兩種做法：

  • rename：一個 system call（page-55），只改目錄裡的 entry：在新目錄加一筆指向 同一個 i-node 的 entry，再把舊目錄那筆拿掉。i-node 和資料完全不動，所以 10 GB 的檔案也是瞬間完成。
  • 複製再刪除：在目的地 open 一個新檔案（拿到新的 i-node），把舊檔的內容 read 出來、write 進去，複製權限和時間，最後 unlink 舊檔。資料要整份搬一次，檔案越大越慢。

同一個 file system 裡用 rename；跨 file system 只能複製再刪除。因為 i-node number 只在自己的 file system 的 i-list（page-42）裡有意義，另一個 file system 的目錄沒辦法指向它。這時 rename 會失敗並回傳 EXDEV，mv 看到就自動改用複製再刪除。

hard link 不能跨 file system 也是同一個原因（page-50）。

File System：4.4BSD i-node#

i-node 前面幾欄是 mode、owner、timestamp、size，後面是記錄「內容在哪些 block」的指標（ch03 page-37 的 block 對照表）。以 block 4 KB、一個 block 指標 4 byte 計算：

指標怎麼指能涵蓋
12 個 direct每個直接指向一個 data block12 × 4 KB = 48 KB
1 個 single indirect指向一個裝滿指標的 block：4 KB ÷ 4 byte = 1024 個指標，每個指向 data block1024 × 4 KB = 4 MB
1 個 double indirect指向一個指標 block，裡面每個指標再指向一個 single indirect block1024 × 1024 × 4 KB = 4 GB
1 個 triple indirect再多一層1024³ × 4 KB = 4 TB
這裡的「指標」是 block number，不是記憶體位址

C 的指標是記憶體位址，但 block 讀進記憶體時放在哪是 kernel 當下決定的，每次都可能不同，磁碟上不可能存這種東西。所以 i-node 和 indirect block 裡存的是 block number：「這個 file system 的第幾個 block」，第 N 個 block 就在 partition 開頭往後 N × block size 的位置。一個 indirect block 其實就是一個整數陣列，例如 [5012, 5013, 8840, ...]。

kernel 跟著這些數字往下走時，靠的是 buffer cache 用 （裝置, block number） 當 key 的查詢表：

  1. i-node 說 double indirect 在 block 7300。
  2. 查 cache 有沒有（這顆磁碟, 7300）：有就直接用記憶體裡那份，不管它放在哪；沒有就配一塊 buffer、從磁碟讀進來，再登記到表裡。
  3. 在這個 block 裡找到要的那一格，寫著 9021，對 9021 重複第 2 步，拿到 single indirect block。
  4. 它裡面寫著 5013，就是要找的 data block。

block 在記憶體的哪裡，只有 cache 的查詢表需要知道；磁碟上記的永遠是磁碟上的位置。所以一個 file system 拔下來接到別台機器還是能用。目錄 entry 裡的 i-node number 也是同樣的道理。

這種設計讓小檔案很快：48 KB 以內只靠 i-node 本身就找得到所有 block。大檔案要多讀幾個指標 block，例如讀第 1 GB 處的資料，要先讀 double indirect block、再讀 single indirect block，才知道 data block 在哪（這些指標 block 通常已經在 buffer cache 裡）。

指標 block 讀一次就留在 cache，寫回只寫有改的

從磁碟讀第一次時，路上 每一層 指標 block 都得讀進 buffer cache（ch03 page-08），才找得到最裡面的 data block。但讀進來之後它們就留在 cache 裡，之後讀同一區的資料，查指標都在記憶體裡完成，不用再碰磁碟。

寫回磁碟（flush）時，kernel 只寫 被改過的 dirty block。改寫檔案既有的內容，只有最裡面的 data block 變了，外面那幾層指標沒變，就不用寫；只有配了新 block、指標真的改了，那一層指標 block 才要寫回。所以外層的指標 block 不會跟著每次讀寫反覆進出磁碟。

這就是好的記憶體管理省下的 disk I/O：常用的東西留在記憶體，寫回時只寫真的變了的部分。（現在的 Linux 把 buffer cache 和 virtual memory 整合成同一套 page cache。）

「>> 4GB for the largest file」：這個結構能記的遠超過 4 GB，可是當時的 file offset 是 32 bit，只能表示到 2³² = 4G。所以檔案大小的上限卡在 off_t，而不是 i-node，這就是後來 off_t 要改成 64 bit 的原因（ch05 page-19 的 fseeko 也是為此）。

Hard Link vs. Soft Link#

要讓一個檔案多一個名字，有兩種做法：

hard link：在某個目錄裡多加一筆 entry，指向 同一個 i-node number（page-44）。所有名字地位相同，沒有哪一個是「本尊」。

為什麼目錄不能隨便建 hard link#

整個系統能當成一棵 樹 來用，靠的是每個目錄只有 一個 parent。對目錄建 hard link 等於讓它有第二個 parent，會壞掉三件事：

1. 出現迴圈，走訪整棵樹的程式跑不完。 假設允許：

現在 a/b 就是 a，a/b/b、a/b/b/b……全都是 a。find、du、rm -r 這種「看到目錄就往裡面走」的程式會一直走下去。它們分不出 b 是「回頭的路」，因為 hard link 跟原本的名字地位完全相同，沒有任何標記。

2. 迴圈裡的目錄刪不掉。 接著用 unlink 把上層那個名字 a 拿掉（rmdir 會因為 a 裡還有 b 而失敗），a 從 / 已經走不到了；可是 a/b 這筆 entry 還指著 a，link count 不會歸零，空間永遠不會被回收。link count 只會數「有幾個名字指著我」，分不出這些名字是不是只有迴圈自己在指自己。

3. .. 不知道該指哪裡。 一個目錄只有一筆 ..。如果 /x/d 和 /y/e 是同一個目錄，它的 .. 只能指向 /x 或 /y 其中一個，於是 cd /y/e 再 cd ..，可能跑到 /x。

那為什麼 superuser 可以？ 這是歷史包袱：早期 UNIX 沒有 mkdir 這個 system call，mkdir 指令要自己用 link 建出 . 和 ..，所以 kernel 得允許對目錄建 hard link，只是限定 superuser，相信他不會亂建。現在有 mkdir 和 rename 這兩個 system call（page-55、page-65），就沒有理由再留，Linux 直接回傳 EPERM。

symbolic link 指向目錄就沒有這些問題：它有自己的 file type，程式用 lstat 一看就知道「這是 link」，可以選擇不跟進去（find 預設就不跟）；它也不算進目標的 link count，不影響回收；kernel 跟著 symbolic link 走的層數也有上限，超過就回傳 ELOOP。

Sharing of Files#

上半（hard link）：/usr/joe/foo 和 /usr/sue/bar 兩筆 entry 指向同一個 i-node，Reference = 2（link count）。刪掉其中一個名字，link count 變 1，檔案還在。

下半（symbolic link）：/usr/sue/bar 指向自己的 i-node（Reference = 1），它的資料是字串 /usr/joe/foo。打開 bar 時，kernel 讀出這串路徑，再去找 /usr/joe/foo。投影片拿 Windows 的捷徑比喻；差別是 symbolic link 由 kernel 處理，所有程式打開它都會自動跟過去。

symbolic link 有兩個 hard link 沒有的問題：

1. 無窮迴圈。 右下角的圖：目錄 foo 底下有 a 和 testdir，testdir 是指回 foo 的 symbolic link（虛線）。那麼 foo/testdir/testdir/testdir/... 每一層都合法，永遠走不完。所以 kernel 限制一次路徑解析最多跟幾個 symbolic link：4.3BSD 是 8 個（投影片的「no 8 passings」），Linux 是 40 個，超過就回傳 ELOOP。

會走訪整棵樹的程式（page-68）則用 lstat，看到 symbolic link 就不跟進去。

2. Dangling pointer（懸空指標）。 把 /usr/joe/foo 刪掉，bar 還在，但指向一個不存在的路徑：ls 看得到 bar（lstat 讀的是 link 本身），open 它卻得到 ENOENT。hard link 不會有這個問題，只要還有一個名字，內容就不會消失。

link 與 unlink#

簡單說：link 就是建立 hard link，unlink 就是刪掉一個 hard link（shell 的 ln a b 和 rm 底下呼叫的就是它們）。檔案最初的那個名字也是一個 hard link，跟後來 link 建的地位相同（page-50），所以 rm 刪檔其實只是 unlink 掉其中一個名字；名字全刪光、又沒人開著，檔案才真的消失。

link：建立新的 entry newpath，指向 existingpath 的 i-node，並把 link count 加 1。

這兩步 必須是 atomic：如果建好 entry 之後、加 link count 之前系統當機，link count 就比實際的名字數少 1，之後 unlink 會在還有名字指著它的時候把內容釋放掉。newpath 已經存在會失敗（EEXIST），跨 file system 也會失敗（EXDEV）。

unlink：刪掉 pathname 這筆 entry，link count 減 1。

  • 需要對所在目錄有 w+x（page-13）；如果目錄設了 sticky bit，還要是檔案的 owner、目錄的 owner 或 superuser（page-32）。
  • pathname 是 symbolic link 時，刪的是 link 本身，不會跟過去刪掉目標（page-57）。
  • pathname 是 目錄 時不能用 unlink（Linux 回傳 EISDIR；早期 UNIX 只准 superuser 這樣做），要改用 rmdir（page-65），而且 目錄必須是空的（只剩 . 和 ..）。否則裡面的檔案會失去唯一能找到它們的路徑，又因為 link count 不是 0 而永遠不會被回收，就是 page-50 說的那種刪不掉的情況。
  • 「Checking if any process has the file open」：link count 歸零時，kernel 還要檢查有沒有 process 開著這個檔案。link count 是 0、而且沒有人開著，內容才會真的釋放，就是 ch03 page-15 那張三種狀態的表。

remove 與 rename#

remove 和 rename 宣告在 <stdio.h>，屬於 ANSI C，所以在非 UNIX 的系統上也能用（ch03 page-03）。

remove：pathname 是檔案就等於 unlink，是目錄就等於 rmdir（page-65）。ANSI C 不知道 unlink、rmdir 這兩個 POSIX 函式，所以另外定義了它。

rename：把 oldname 改成 newname。newname 已經存在時，規則如下：

oldname 是newname 不存在newname 是檔案newname 是目錄

另外幾條：

  • oldname 是 newname 的前綴時錯誤：例如 rename("/usr/foo", "/usr/foo/testdir") 會把目錄搬進它自己底下，那棵子樹從此跟 / 斷開，形成一個沒有出口的迴圈。
  • 對兩個所在目錄都要有 w+x：兩邊的 directory block 都會被修改。
  • 不會幫你建目錄：newname 只有最後一段可以不存在，前面每一層目錄都得已經存在，否則回傳 ENOENT。例如 rename("f", "no/such/dir/g") 會失敗，要先 mkdir 出每一層（shell 的 mkdir -p）。因為 rename 只是把 entry 搬進「newname 所在的那個目錄」，那個目錄得先找得到。

newname 已經存在時，「刪掉舊的、換上新的」是一個 atomic 的動作，任何時刻去看 newname，不是舊內容就是新內容。所以常見的安全寫檔方式是：先寫到一個暫存檔、fsync（ch03 page-61），再 rename 蓋過正式的檔案，別人永遠不會讀到寫到一半的版本。

傳一個 symbolic link 的路徑給函式時，函式要嘛 跟過去，對目標檔案做事；要嘛 不跟，對 link 本身做事：

lchown、lstat、readlink、remove、rename、unlinkaccess、chdir、chmod、creat、exec、link、open、opendir、pathconf、stat、truncate

規律是：工作本來就跟「名字」或「link 本身」有關的不跟（刪掉一個名字、改名、讀 link 的內容、查 link 本身的屬性），其他對檔案內容或屬性做事的都跟。

幾個要注意的：

  • chown 兩欄都打點：依實作而定。早期有些系統的 chown 不跟過去，Linux 的會跟；不想跟就用 lchown。
  • link：表上是跟過去，但 POSIX 允許兩種都行，Linux 的 link 其實不跟，會建出一個指向那個 symbolic link 的 hard link。
  • 「No functions take filedes as input」：表上只列用 pathname 的函式。用 fd 的函式（fstat、fchmod、fchown）不在表上，因為 fd 是 open 給的，而 open 已經跟過去了，fd 指的一定是目標。
  • mkdir、mkfifo、rmdir 不在表上：pathname 是一個 symbolic link 時，它們直接回傳錯誤。

page-07 的 struct stat 還剩三個時間欄位沒講。每個 i-node 記三個時間：

欄位意思例子ls 的選項
st_atimelast-access-time：最後一次 讀內容read-u

mtime 管 內容，ctime 管 i-node。改權限、改 owner、link count 變了，都只動到 i-node，所以只改 ctime。反過來，write 改了內容，i-node 裡的大小和 mtime 也跟著變，所以 mtime 和 ctime 都會更新。

ctime 不是建立時間（creation time）。傳統的 UNIX 根本不記建立時間；Linux 的 ext4 另外記了一個 birth time，要用 statx 才拿得到。

現在的 atime

每次讀檔都要更新 atime，等於每次讀都要寫一次 i-node，很浪費。所以 Linux 預設用 relatime 掛載：只有 atime 比 mtime 舊、或已經超過 24 小時沒更新時，讀檔才會更新它。

utime#

utime 設定檔案的 atime 和 mtime。時間的單位是 calendar time：從 Epoch（1970 年 1 月 1 日 00:00:00 UTC）起算的秒數。

為什麼需要手動改時間？例如從網路下載一包 source code 解開，新建出來的檔案 mtime 本來都是「現在」，但我們希望它保留 原作者當初最後修改的時間，才看得出每個檔案是什麼時候改的，make 判斷哪些檔案需要重新編譯（比較 mtime 新舊）也才不會亂掉。所以 tar 解壓縮時會把壓縮檔裡記的時間用 utime 設回去（tar 是把一堆檔案打包成一個 .tar 檔的指令，原始碼常以 .tar.gz 的形式發布；打包時會記下每個檔案的權限和時間，解開時照著還原）。cp 是複製檔案的指令，cp a b 會建一個新檔 b，把 a 的內容整份抄過去；新檔的時間預設是「現在」，加上 -p（preserve）才會用 utime 把時間設成跟 a 一樣（權限、owner 也會一起保留）。

times設成什麼誰可以做
NULL兩個都設成現在檔案的 owner，或對檔案有寫入權限的人（superuser 當然也可以）
非 NULL設成 struct 裡的值只有檔案的 owner 或 superuser，光有寫入權限不夠

差別在於：設成「現在」跟寫一次檔案的效果差不多，能寫的人本來就做得到；設成任意值則等於竄改紀錄，所以只有 owner 可以。（投影片在第二種情況寫「而且要有 W」，POSIX 和 Linux 的 man page 只要求 owner 或 superuser，重點在「W 不夠」。）

ctime 不能指定：呼叫 utime 本身就改了 i-node，ctime 會自動變成現在。touch 指令用的就是 utime；現在的程式多半改用精確到 nanosecond 的 utimensat。

Year 2038 problem#

time_t 存的是從 Epoch 起算的秒數（page-61）。在大部分 32-bit 系統上，它是 signed 32-bit 整數：

  • 範圍是 -2³¹ 到 2³¹ - 1 秒，前後各約 68 年，總共約 136 年。
  • 最小值 -2³¹ 是 1901 年 12 月 13 日 20:45:52 UTC。
  • 最大值 2³¹ - 1 是 2038 年 1 月 19 日 03:14:07 UTC。再過一秒就 overflow 成 -2³¹，時間跳回 1901 年。

投影片問的兩種解法：

做法結果問題
改成 unsigned可以用到 2106 年不能表示 1970 年以前；而且很多函式用 -1 代表錯誤（例如 time() 失敗回傳 (time_t)-1），兩個時間相減的程式也預期結果可以是負的

實際採用的是 64 bit。64-bit Linux 的 time_t 一開始就是 64 bit；32-bit Linux 也在 kernel 5.6、glibc 2.34 之後提供 64-bit time_t。存在磁碟上的時間也要跟著改，例如 ext4 用 256 byte 的 i-node 時，時間欄位可以用到 2446 年。

  3. utime 把 atime、mtime 設回第 1 步存的值。

檔案都變成 0 byte 了，ls -l（mtime）和 ls -lu（atime）卻跟執行前一模一樣，看起來像沒被動過。只有 ls -lc 露了餡：ctime 是程式執行的那一刻 Jan 22 06:55。

ctime 改不回去，所以它是可靠的「這個 i-node 什麼時候被動過」的紀錄。備份程式靠它判斷哪些檔案需要重新備份，調查入侵時也靠它。反過來，tar 解壓縮、cp -p 保留原本時間，用的就是這支程式的做法。

page-65#

mkdir、rmdir#

最後一部分是操作目錄本身的函式：建立和刪除（這頁）、讀取內容（page-66～69）、切換 cwd（page-70～73）。

mkdir：建一個空目錄。

  • 權限是 mode & ~umask（ch03 page-23），owner 和 group 的規則跟建檔一樣，包括目錄的 set-group-ID 繼承（page-22）。
  • . 和 .. 自動建好（page-45），所以新目錄的 link count 是 2，parent 的 link count 加 1。
  • mode 通常要包含 x，例如 0755。沒有 x 的目錄連穿過都不行（page-13），給 0666 是常見的錯誤。

rmdir：刪掉一個 空 目錄（只剩 . 和 ..），不空就回傳錯誤。刪掉後 link count 歸零；如果沒有 process 開著它，空間馬上釋放。如果還有 process 開著它（例如把它當作 cwd，或正在 readdir），就等最後一個關掉時才釋放，這段期間目錄裡的 .、.. 已經被移除，也不能再在裡面建新檔。這跟 page-53～54 的檔案是同一套規則。

page-66#

opendir、readdir、rewinddir、closedir#

讀一個目錄，就是讀它那張「名字 → i-node」的表。用法很像 FILE *（ch05）：DIR 是 library 的一個 struct，裡面包著一個 fd 和一塊暫存 entry 的 buffer。

函式做什麼
opendir打開目錄，回傳 DIR *；失敗回傳 NULL
readdir回傳下一筆 entry；讀完了回傳 NULL
rewinddir回到第一筆
closedir關閉

投影片的三點：

  • Only the kernel can write to a dir：沒有 writedir 這種函式，只能用 creat、link、unlink、rename、mkdir、rmdir 間接修改（page-08）。
  • WX for creating/deleting a file：page-13。
  • Implementation-dependent：目錄 entry 在磁碟上的格式，各個 file system 都不一樣（ext4 用雜湊樹、XFS 用 B-tree）。readdir 把這些差異藏起來，所以不要用 read 直接讀目錄；Linux 上對目錄 read 會直接得到 EISDIR（ch03 page-18）。

readdir 跟 read 一樣有一個 cursor：opendir 時指在第一筆 entry，每呼叫一次 readdir 就回傳 cursor 指的那筆、再往後移一格，rewinddir 把它拉回開頭。（DIR 裡面其實就是一個 fd，cursor 就是那個 fd 的 file offset。）

但目錄的內容是一個 集合：只規定「裡面有哪些名字」，沒規定誰在前面。cursor 走的是 file system 實際存放的順序，例如 ext4 是照檔名的雜湊值排，POSIX 也沒保證任何順序，所以 不一定照字母，也不一定照建立的先後。ls 的輸出有排序，是 ls 讀完之後自己排的。

ftw／nftw（file tree walk）：C library 提供的函式，自動遞迴走訪整棵目錄樹，page-69。

page-68#

Example of Directory Traversal#

這是 APUE 一支遞迴走訪程式的片段。fullpath 是用 path_alloc（page-38）配的 buffer，裡面放著目前所在目錄的路徑，例如 /usr。

  1. ptr 指到字串結尾，補上 /：fullpath 變成 /usr/，ptr 指在 / 後面。
  2. opendir，逐筆 readdir。
  3. 跳過 . 和 ..：. 是自己、.. 是上一層，不跳過就會一直繞圈。
  4. strcpy(ptr, d_name)：把檔名接在 / 後面，fullpath 變成 /usr/lib 這種完整路徑。每一輪都從同一個 ptr 開始覆蓋，不必另外配記憶體。
  5. lstat(fullpath, ...) 拿這個 entry 的屬性。完整的程式在這裡判斷：如果是目錄（S_ISDIR），就用新的 fullpath 遞迴呼叫自己，進到下一層；其他的就依 file type 計數。用 lstat 而不是 stat，碰到指向目錄的 symbolic link 時才不會跟進去，避開 page-51 的迴圈。
  6. ptr[-1] = 0：把剛補上的 / 改回 '\0'，fullpath 恢復成 /usr，回到上一層的呼叫者手上時路徑才是對的。
  7. closedir。

遞迴每深一層就多開一個 DIR，也就多佔一個 fd，目錄樹很深時要注意 fd 的上限，這就是 page-69 nopenfd 參數的由來。

page-69#

ftw、nftw#

page-68 那套「opendir、跳過 . 和 ..、接路徑、lstat、遞迴」由 library 幫你做完：ftw 走訪 dirpath 底下的整棵樹，每碰到一個 entry 就呼叫一次你的函式 fn，傳入它的路徑、stat 結果和 type（FTW_F 檔案、FTW_D 目錄……）。fn 回傳 0 代表繼續，非 0 代表停下。預設是 preorder：先處理目錄本身，再處理它底下的東西。

nopenfd：最多同時開著幾個目錄。ftw 每一層最多用一個 fd，樹比這個深時就得關掉、之後再重新打開，會變慢，但不會把 fd table 用光（page-37 的 _SC_OPEN_MAX）。

page-70#

chdir、fchdir#

每個 process 都有一個 current working directory（cwd）：路徑不是 / 開頭時，就從 cwd 開始找。chdir 改 cwd，fchdir 用一個已經開好的目錄的 fd 指定（投影片說不在 POSIX.1 裡，現在已經是標準）。目標目錄要有 x 權限（page-13）。

投影片的重點：

  • Per-process attribute：跟 umask 一樣，cwd 是每個 process 各自記著的一份（page-26 的整理）。fork 時 child 複製一份 parent 的 cwd，exec 也不會清掉（ch03 page-11）；之後 child chdir 只改自己那份，parent 的 cwd 不變。
  • kernel 只記 cwd 的 i-node number 和所在裝置，不記路徑字串。這是 page-72 getcwd 要大費周章的原因。
  • chdir must be built into shells：跟 page-26 的 umask 同樣的理由，cd 如果是獨立程式，改到的只是那個 child 的 cwd。所以 cd 是 shell 的內建指令，page-71 示範了不內建會怎樣。

page-72#

getcwd#

getcwd 把 cwd 的絕對路徑寫進 buf，成功回傳 buf，失敗回傳 NULL。

  • buffer 要夠大，包括結尾的 '\0'，不然回傳 NULL（errno 是 ERANGE）。該配多大就是 page-38 path_alloc 要回答的問題。
  • getcwd 怎麼做：kernel 只記 cwd 的 i-node（page-70），所以傳統的做法是往上爬：stat(".") 拿到自己的 i-node number，打開 .. 用 readdir 找出哪一筆 entry 是這個 number，那筆的名字就是路徑的最後一段；再對上一層做同樣的事，一路爬到 /（. 和 .. 是同一個 i-node 的地方），最後把名字倒過來接起來。現在的 Linux 由 kernel 直接算，但結果一樣。
  • chdir 會跟 symbolic link，getcwd 卻不知道有 symbolic link：chdir 到一個 link，最後停在目標目錄的 i-node 上；getcwd 從那裡沿著真正的 .. 往上爬，得到的是 實際的路徑，不是你當初打的那條（page-73）。

page-73#

Example of getcwd()#

程式 chdir 到 /usr/spool/uucppublic，getcwd 卻回答 /var/spool/uucppublic：/usr/spool 是指向 ../var/spool 的 symbolic link，getcwd 只看得到實際的路徑（page-72）。ls -l 那行的 size 12，就是 ../var/spool 這 12 個字元（page-39）。

在 bash 裡 cd /usr/spool/uucppublic 再打 pwd，看到的卻是 /usr/spool/uucppublic：shell 的內建 pwd 印的是 shell 自己記下的路徑（環境變數 PWD），pwd -P 才會跟 getcwd 一樣印出實際的路徑。

page-74#

st_ino（i-node number）#

  • 每個檔案都有一個 i-node number，也就是它的 i-node 在 i-list 裡的編號（page-44）。
  • kernel 用這個編號到 i-list 查出檔案的 i-node。
  • i-node 裡有 owner 的 user ID 和 group ID、permission bit 等等（page-48）。

投影片說 i-node number 是 unique 的，但只在 同一個 file system 裡成立：每個 file system 有自己的 i-list，兩個 file system 都可以有 2 號 i-node（ext 系列的根目錄就是 2 號）。全系統唯一的是 (st_dev, st_ino) 這一對（page-07）。

所以要判斷兩條路徑是不是同一個檔案，就比較這一對是否相同。只比檔名不夠，因為同一個檔案可以有好幾個名字（hard link、symbolic link、./a 和 a）。

例如 cp a b。cp 複製的做法是：用 O_TRUNC 打開 b（把 b 清空），再從 a 讀、往 b 寫。如果 b 其實是 a 的 hard link，清空 b 就等於清空 a，接著從 a 什麼也讀不到，結果檔案內容全沒了。所以 cp 在動手之前 先 stat 兩邊，(st_dev, st_ino) 相同就直接拒絕：

du 和 tar 也用這一對，避免同一個檔案被處理兩次。du 加總一個目錄佔的空間時，如果 a、b 是同一個檔案的兩個 hard link，兩個都算就會多算一份，所以它記下看過的 (st_dev, st_ino)，第二次遇到就跳過。tar 打包時也一樣，第二個名字不再存一份內容，只記「b 是 a 的 hard link」，解開時再用 link 接回去。
