page-74#

Interprocess Communication#

Except for communicating via the file system, processes can communicate via various IPCs.

最直接的溝通方式是透過檔案：一個 process 寫檔，另一個讀檔。但這有兩個問題：讀的一方不知道對方什麼時候寫完，只能一直回去檢查；資料還要經過磁碟。IPC（interprocess communication，行程間通訊） 是 kernel 提供的、專門讓 process 互相傳資料或互相通知的機制。

表格列出各種 IPC，以及哪些標準或系統支援（POSIX.1、XPG3 是標準；V7、SVR2、SVR3.2、SVR4、4.3BSD、4.3+BSD 是不同年代的 UNIX 版本）：

IPC是什麼
pipes (half duplex)單向的資料通道，只能在有共同祖先的 process 之間用（page-75）。每個系統都有
FIFOs有名字的 pipe，沒有親屬關係的 process 也能用（page-86）
stream pipes (full duplex)雙向的 pipe
named stream pipes有名字的雙向 pipe
message queueskernel 裡的一個訊息佇列，一次放進、取出一整則訊息
semaphores一個由 kernel 保管的計數器，用來同步，不是用來傳資料
shared memory讓兩個 process 的 page table 指向同一塊實體記憶體，直接共用變數，最快
sockets透過網路傳資料的端點，可以跨機器溝通（ch16）
streamsSVR4 的一套 I/O 架構，也可以跨機器溝通

表格最下面 sockets 和 streams 兩列用粉紅色標出來，意思是：這兩種 IPC 可以讓不同 host（不同台機器）上的 process 互相溝通。上面其他的 IPC（pipe、FIFO、message queue、semaphore、shared memory）都只能用在同一台機器上的 process 之間，因為它們都靠同一個 kernel 裡的東西：pipe 是那個 kernel 裡的 buffer，shared memory 是那台機器的實體記憶體，另一台機器的 process 根本碰不到。sockets 和 streams 則可以把資料經過網路送到另一台機器的 kernel。

duplex 指傳輸的方向：half duplex（半雙工）是同一時間只能單向傳，full duplex（全雙工）是兩個方向可以同時傳。

這份投影片只講 pipe 和 FIFO。

page-75#

Pipes（Ch15.2）#

pipe 是 kernel 提供的一條單向資料通道。它的本體是 kernel 裡的一塊 buffer：一個 process 把資料寫進這塊 buffer，另一個 process 再從這塊 buffer 把資料讀出來，兩個 process 不用直接碰對方的記憶體。

資料從 pipe 的一頭進去、另一頭出來，這兩頭叫做 pipe 的兩端：

  • 寫端（write end）：資料從 process 進入 pipe 的那一頭。process 對指向寫端的 fd 呼叫 write，kernel 就把資料從 process 的記憶體複製進 pipe 的 buffer。
  • 讀端（read end）：資料從 pipe 出來、回到 process 的那一頭。process 對指向讀端的 fd 呼叫 read，kernel 就把資料從 pipe 的 buffer 複製到 process 的記憶體。先寫進 buffer 的資料先被讀出來（first in, first out）。

process 碰不到 pipe 本身，手上只有指向某一端的 fd。同一端可以同時被好幾個 fd 指著，例如 fork 之後，parent 和 child 各有一個 fd 指向同一個寫端（page-77）。kernel 會記錄每一端目前還有幾個 fd 開著，下面兩張表都會用到這個數字。

對讀端 read：

buffer寫端還開著的 fdread 的結果
有資料不管幾個把現有的資料讀走（最多讀到要求的 byte 數），馬上回傳
空的至少 1 個block，等有人寫進來
空的0 個回傳 0（EOF）：不可能再有資料了

對寫端 write：

buffer讀端還開著的 fdwrite 的結果
有空位至少 1 個把資料放進 buffer，回傳
滿了至少 1 個block，等讀的一方讀走資料、空出位置
不管0 個收到 SIGPIPE：已經沒有人會讀了（page-79）

兩張表合起來，pipe 的行為是：

  • 寫的一方和讀的一方同時進行，一邊寫一邊讀。read 不用等寫端關掉：buffer 有資料，read 就把資料讀走並馬上回傳，回傳值是這次讀到的 byte 數；buffer 滿了，write 等對方讀走一些就能繼續。
  • 寫端還開著幾個 fd，只決定 buffer 空了之後的事：還有 fd 開著，read 就等；全部關了，read 回傳 0（EOF）。

所以讀的一方通常寫成迴圈，每次 read 拿到一段資料就處理，直到 read 回傳 0 才知道資料結束：

Pipes have two limitations：

  • They are half-duplex：資料只能單向流動。要雙向溝通，就得開兩個 pipe（page-82）。
  • They can be used between processes that have a common ancestor：pipe 沒有名字，在檔案系統裡找不到，要拿到它的 fd 只有一種辦法：從建立它的 process 那裡繼承。所以典型用法是一個 process 先建 pipe，再 fork，讓 child 繼承 fd（page-77）。

另外兩種解決這兩個限制的東西（Chap 17.2 是 APUE 的章節）：

  • Stream pipes are duplex：雙向的 pipe。
  • Named pipes/FIFOs and named stream pipes can be used between process not having the same ancestor：有名字的 pipe 在檔案系統裡有一個路徑，任何 process 都可以用路徑打開它（page-86）。

pipe function：

  • 功能：在 kernel 裡建立一個 pipe，並幫這個 process 開好兩個 fd，一個指向讀端、一個指向寫端。
  • 參數 filedes：呼叫者準備的兩格 int 陣列，pipe 會把開好的 fd 填進去：filedes[0] 指向讀端，filedes[1] 指向寫端（page-76）。
  • 回傳值：成功回傳 0；失敗回傳 -1 並設定 errno，例如 fd 數量已到上限（EMFILE）。

例子：shell 怎麼做 ls | wc -l

shell 的 ls | wc -l（ch01 page-48）就是用 pipe 把 ls 的輸出接到 wc 的輸入：

  1. shell 呼叫 pipe(fd)，拿到 fd[0]（指向讀端）和 fd[1]（指向寫端）。
  2. shell fork 兩次。兩個 child 都繼承 shell 的 fd table，所以都有 fd[0] 和 fd[1]。
  3. 要跑 ls 的 child：dup2(fd[1], STDOUT_FILENO) 讓 fd 1 指向寫端（dup2 見 ch03 page-52、page-81），關掉 fd[0]、fd[1]，再 exec ls。
  4. 要跑 wc 的 child：dup2(fd[0], STDIN_FILENO) 讓 fd 0 指向讀端，關掉 fd[0]、fd[1]，再 exec wc。
  5. shell 自己關掉 fd[0]、fd[1]，然後 wait 兩個 child。

ls 照常寫 fd 1、wc 照常讀 fd 0，兩支程式都不知道中間有 pipe，是 shell 在 exec 前先把 fd 接好。這也是 ch08 page-70 說 fork 和 exec 分開的好處。

用不到的 fd 一定要關，因為 wc 要讀到 EOF 才知道資料結束、印出結果。fork 之後指向寫端的 fd 有三個：shell、ls、wc 各一個。ls 寫完結束時，kernel 會關掉它所有的 fd；但如果 shell 和 wc 沒關自己的 fd[1]，寫端就還有 fd 開著，照上面的讀端表，wc 讀完資料後會一直 block 在 read，shell 也會卡在 wait 等 wc。

page-76#

Unix Pipes#

pipe 給的兩個 fd：

  • fd[0]: open for reading, file type is FIFO：指向讀端。
  • fd[1]: open for writing, file type is FIFO：指向寫端。

記法：0 是讀、1 是寫，跟 stdin（fd 0）、stdout（fd 1）的方向一樣。

這兩個 fd 用 fstat 查，st_mode 的 file type 是 FIFO（ch04 page-08，用 S_ISFIFO 判斷）。對程式來說，它們跟一般檔案的 fd 一樣，用 read、write、close 操作。

圖有兩種畫法：

  • 左邊：一個 user process，資料從 fd[1] 寫出去，從 fd[0] 讀回來。
  • 右邊：比較真實的畫法，pipe 在 kernel 裡（虛線以下）。write(fd[1], ...) 把資料從 user space 複製進 kernel 的 pipe buffer，read(fd[0], ...) 再從 pipe buffer 複製出來。

只有一個 process 自己讀寫自己的 pipe 沒什麼用，下一頁加上 fork。

page-77#

Pipes between Processes#

Half-duplex pipe after a fork：parent 先 pipe，再 fork。child 複製了 parent 的 fd table（ch08 page-20），所以兩邊都有 fd[0] 和 fd[1]，四個 fd 都指向 kernel 裡 同一個 pipe：

parentchild
fd[0]指向讀端指向讀端
fd[1]指向寫端指向寫端

這時 parent 和 child 都能寫、也都能讀同一個 pipe。但 buffer 只有一塊，兩邊都寫又都讀的話，哪筆資料被誰讀走，要看誰先 read，parent 甚至可能讀回自己剛寫的資料。所以要先決定資料往哪個方向流，再把不用的端點關掉（下一頁）。

page-78#

Useful Pipe#

Pipe from parent process to child process：決定好方向後，每一邊各關掉一個 fd：

  • parent 只寫，所以 close(fd[0])。
  • child 只讀，所以 close(fd[1])。

剩下 parent 的 fd[1] → pipe → child 的 fd[0]，一條單向通道。要從 child 傳到 parent，就反過來關。

關掉不用的 fd 還有一個原因：EOF 和 SIGPIPE 看的都是「另一端還有沒有 fd 開著」（page-75 的兩張表）。沒關的話，讀的一方永遠等不到 EOF（下一頁）。

page-79#

Read from／Write to Pipes#

這頁講的是 page-75 兩張表的最後一列，也就是另一端全部關掉之後會怎樣。

When the write end is closed, after all the data has been read, reading from a pipe returns 0 (end of file)：所有指向寫端的 fd 都關掉，而且 buffer 裡的資料都讀完了，read 才回傳 0（EOF）。這句講的是 EOF 什麼時候出現，不是 read 什麼時候讀得到資料：buffer 有資料時，read 不用等寫端關掉就能讀。

要注意是 所有 指向寫端的 fd 都關掉才算。如果 child 忘了關自己那份 fd[1]，就算 parent 已經寫完、關掉了它的 fd[1]，child 讀完資料後還是會卡在 read 裡：kernel 認為還有人（child 自己）可能會寫，就繼續等。這就是 page-78 要關掉不用的 fd 的原因。

When the read end of a pipe is closed, writing to a pipe triggers SIGPIPE signal：所有指向讀端的 fd 都關掉之後還往 pipe 寫，寫進去的資料永遠不會有人讀，kernel 就送 SIGPIPE signal 給寫的 process。SIGPIPE 的預設動作是結束 process。如果程式選擇忽略這個 signal 或設了 handler，write 會回傳 -1，errno 設成 EPIPE。

例如 cat bigfile | head -1：cat 反覆做「從 bigfile 讀一段，寫進 pipe 的寫端」，head 從讀端讀。head 讀到第一行就印出來、結束，它的讀端 fd 跟著關掉。cat 下一次寫進 pipe 時就收到 SIGPIPE 而結束，於是不會再往 pipe 寫，也不會再從 bigfile 讀剩下的部分。如果沒有 SIGPIPE，cat 會把整個 bigfile 讀完、寫完，但寫進 pipe 的資料根本沒人要。

Kernel’s pipe buffer size：

  • Constant PIPE_BUF specifies the pipe buffer size：投影片說它是 pipe buffer 的大小。更精確地說，PIPE_BUF 是「保證 atomic 的寫入大小上限」，Linux 是 4096 byte（ch04 page-37）；Linux 的 pipe buffer 實際容量預設是 64 KB，比 PIPE_BUF 大。
  • Writing PIPE_BUF or less will not be interleaved：好幾個 process 同時寫同一個 pipe 時，一次 write 不超過 PIPE_BUF byte，kernel 保證這筆資料整個一次放進 buffer（空位不夠就先 block，等空位夠了再整筆放），不會被別人的資料插在中間。超過 PIPE_BUF 的寫入沒有這個保證：buffer 空位不夠時，kernel 可能先放一部分、讓寫的 process block，這時別的 process 的資料可能先放進去，讀的一方就會讀到交錯的資料。這就是 page-92 說的 intermixing problem（ch14 page-03 的 caution）。

page-80#

從 parent 傳資料給 child#

就是 page-78 的圖寫成程式：

  1. pipe(fd) 建 pipe，再 fork。順序很重要：先 pipe 再 fork，child 才會繼承到這兩個 fd。
  2. parent 關掉讀端 fd[0]，往寫端寫 "hello world\n"（12 byte）。
  3. child 關掉寫端 fd[1]，從讀端讀，讀到什麼就寫到 stdout。

誰先跑都沒關係：

  • child 先跑到 read：buffer 是空的，parent 的寫端還開著，所以 child 的 read 會 block，等 parent 寫進來才讀到資料、回傳。child 不用 sleep，就自動等到了 parent。
  • parent 先寫完、甚至先 exit：資料已經放在 kernel 的 buffer 裡，不會跟著 parent 消失，child 之後 read 一樣讀得到。

MAXLINE 是 APUE 定義的常數（4096），err_sys 見 ch08。

page-81#

Connecting Pipes to Standard I/O#

跟 page-78 一樣是 parent → child 的 pipe，差別是 child 讓自己的 STDIN_FILENO（fd 0）改指向 pipe 的讀端，這樣 child 從 stdin 讀，就是從 pipe 讀。

做法是在 child 裡用 dup2（ch03 page-52）：

dup2 之後，child 的 fd 0 指向 pipe 的讀端。接著 child exec 一支從 stdin 讀資料的程式（例如 more）。exec 會把程式換掉，但 fd table 保留不變（ch08 page-65），所以新程式讀 fd 0，讀到的就是 parent 寫進 pipe 的資料；新程式完全不知道 stdin 是一個 pipe。

if (fd[0] != STDIN_FILENO) 這個檢查是防萬一：如果 parent 呼叫 pipe 前 fd 0 剛好是關著的，pipe 給讀端的 fd 就會是 0（新的 fd 一律用最小的可用號碼），也就是 fd[0] 本來就是 0。這時 dup2(0, 0) 什麼都不做，接著的 close(fd[0]) 等於 close(0)，會把唯一指向讀端的 fd 關掉，child 就讀不到 pipe 了。

shell 處理 ls | wc -l 就是用這招，完整步驟見 page-75 的例子。

page-82#

Using Pipes for Parent-child Synchronization#

pipe 也可以只用來 通知，不傳真正的資料。ch08 page-57 說要用 IPC 取代 polling，這頁就是做法：開 兩個 pipe，一個方向一個（pipe 是 half-duplex）：

pipe方向用途
pfd1parent pfd1[1] → child pfd1[0]TELL_CHILD()：parent 寫一個字元 "p"，通知 child
pfd2child pfd2[1] → parent pfd2[0]TELL_PARENT()：child 寫一個字元 "c"，通知 parent

等待的一方就去 read 對應的 pipe。對方還沒寫，pipe 是空的，read 會 block；對方一寫，read 就返回。block 期間 process 在睡覺，不占 CPU，對方寫入後 kernel 立刻叫醒它，沒有 polling 的浪費和延遲。

page-83#

Avoid Race Condition（Chap 8）#

把 ch08 page-54 那支輸出交錯的程式加上同步，綠底的是新加的行：

  1. TELL_WAIT() 在 fork 之前建好兩個 pipe，這樣兩邊都繼承得到。
  2. child 先 WAIT_PARENT()：對 pfd1 的讀端 read。parent 還沒寫，buffer 是空的，所以 child block 在這裡。
  3. parent 印完整行，才 TELL_CHILD(pid)。
  4. parent 寫進 pfd1 的那一個字元讓 child 的 read 回傳，child 這時才開始印。

不管 scheduler 先讓誰跑，parent 的輸出一定整行都在 child 前面，不會再交錯。

page-84～85#

用 pipe 實作 TELL_WAIT、TELL_PARENT、WAIT_PARENT、TELL_CHILD、WAIT_CHILD#

五個函式對應 page-82 的表：

函式做什麼
TELL_WAIT建 pfd1、pfd2 兩個 pipe。要在 fork 之前呼叫：fork 會複製記憶體和 fd table，child 才有同樣的 pfd1、pfd2 陣列，裡面的 fd 也指向同樣的 pipe
TELL_PARENTchild 往 pfd2[1] 寫一個 'c'
WAIT_PARENTchild 從 pfd1[0] 讀一個 byte，沒資料就 block；讀到的不是 'p' 就是出錯了
TELL_CHILDparent 往 pfd1[1] 寫一個 'p'
WAIT_CHILDparent 從 pfd2[0] 讀一個 byte，沒資料就 block；讀到的必須是 'c'

TELL_PARENT、TELL_CHILD 的 pid 參數在這個版本裡沒用到。這組函式在 APUE 裡有好幾種實作（另一種用 signal，Ch10），介面要一樣，所以保留這個參數。

這個版本沒有關掉不用的 fd（page-78）。關 fd 是為了讓讀的一方等得到 EOF，但這裡等的一方只要讀到 1 byte 就夠了：對方寫進 1 byte，read 就回傳，從來不需要等 EOF，所以沒關也不會卡住。

page-86#

FIFOs（Ch15.5）#

FIFOs – named pipes for (un-)related processes to exchange data：FIFO 就是 有名字的 pipe。page-75 的 pipe 只能靠 fork 繼承，FIFO 在檔案系統裡有一個路徑，任何知道路徑、有權限的 process 都可以 open 它，不需要有共同祖先。

  • A file type – st_mode (S_ISFIFO macro)：FIFO 是一種檔案類型（ch04 page-08），ls -l 第一個字元顯示 p。
  • Data in a FIFO removed when the last referencing process terminates：FIFO 在磁碟上只有名字和 i-node，資料一樣放在 kernel 的 buffer 裡，跟 pipe 一樣。所有開著這個 FIFO 的 fd 都關掉之後（例如用它的 process 都結束了），buffer 裡還沒被讀的資料就被丟掉；但 FIFO 這個檔案（路徑和 i-node）還在，要 unlink 才會刪掉。

建立一個 FIFO，成功回傳 0，失敗回傳 -1。shell 指令也叫 mkfifo。

  • mode and usr/grp ownership = those of a file：mode 是權限，規則跟 open 建檔時的 mode 一樣（會被 umask 遮掉，ch04 page-26）；owner 和 group 的決定方式也跟一般新檔案一樣（ch04 page-22）。

  • Op’s: open, close, read, write, unlink, etc.：mkfifo 只負責建立。之後跟一般檔案一樣，用 open 打開，再 read、write、close，不要了就 unlink。

    open 的 flag 決定拿到的 fd 指向 FIFO 的哪一端：以 O_RDONLY 打開，拿到的 fd 指向讀端；以 O_WRONLY 打開，拿到的 fd 指向寫端。下面說的 讀者（reader） 是手上有指向讀端 fd 的 process，寫者（writer） 是手上有指向寫端 fd 的 process。

    以 O_RDWR 打開 FIFO，POSIX 沒有定義會怎樣；Linux 允許，拿到的這一個 fd 同時指向讀端和寫端，這個 process 同時算讀者和寫者：

    • open 不會 block（page-87），因為它自己就是另一端。
    • 它的 read 永遠讀不到 EOF：它自己的 fd 還開著寫端。buffer 空了就 block。
    • 它的 write 永遠不會收到 SIGPIPE：它自己的 fd 還開著讀端。
    • 它可能讀回自己剛寫進去的資料，因為 buffer 只有一塊，誰先 read 誰拿走。

page-87#

FIFO 的讀寫規則#

O_NONBLOCK：open 一個 FIFO 時，有沒有給 O_NONBLOCK 會影響 open 本身的行為：

沒有 O_NONBLOCK（NO）有 O_NONBLOCK（Yes）
以 O_RDONLY 打開block，直到有別的 process 以 O_WRONLY 打開這個 FIFO立刻返回
以 O_WRONLY 打開block，直到有別的 process 以 O_RDONLY 打開這個 FIFO如果還沒有任何 process 以 O_RDONLY 打開它，回傳 -1，errno 設成 ENXIO

為什麼這樣設計，要回到 page-75 的兩張表：讀端和寫端，只要有一邊沒有 fd 開著，另一邊的讀寫就沒有意義。

  • 沒有寫者時去 read：寫端沒有 fd 開著，buffer 又是空的，read 會馬上回傳 0（EOF），讀的一方會誤以為資料已經結束了，但寫的一方其實只是還沒來。
  • 沒有讀者時去 write：讀端沒有 fd 開著，write 會收到 SIGPIPE。

所以預設（沒有 O_NONBLOCK）時，open 會等到另一邊也打開才回傳。先到的一方等後到的一方，兩邊在 open 這一步會合，之後的 read／write 就不會碰到上面兩種情況。

有 O_NONBLOCK 時 open 不等，但讀和寫的處理方式不同：

  • 以 O_RDONLY 打開一定成功：讀者先開好、還沒有寫者，是正常的狀態，例如 server 先開好 FIFO 等 client 來寫。讀者之後可以用 select 等資料進來，不會出事。
  • 以 O_WRONLY 打開，沒有讀者就失敗（ENXIO）：就算讓這個 open 成功，第一次 write 也只會收到 SIGPIPE，寫的資料沒有地方去。所以 kernel 在 open 這一步就直接回報錯誤。

之後的讀寫規則跟 pipe 一樣（page-79）：

  • Write for a no-reader FIFO → SIGPIPE：指向讀端的 fd（以 O_RDONLY 打開得到的）全部關掉之後還寫，寫的 process 收到 SIGPIPE。
  • Closing of the last writer → EOF：指向寫端的 fd（以 O_WRONLY 打開得到的）全部關掉之後，讀的一方把 buffer 裡剩下的資料讀完，再 read 就回傳 0（EOF）。
  • Atomic writes — PIPE_BUF：一次寫不超過 PIPE_BUF byte 是 atomic 的，多個 process 同時寫同一個 FIFO 也不會互相夾雜。

page-88#

FIFO 的用途一：Stream Duplication#

How to pipe the standard output of a process to more than one file/process? shell 的 pipe 是一條直線，一個程式的輸出只能接給下一個程式。如果想讓 prog1 的輸出 同時 給 prog2 和 prog3 處理呢？

先介紹 tee：copies stdin to stdout, making a copy in files。它從 stdin 讀，原封不動寫到 stdout，同時另外寫一份到參數指定的檔案。

  1. mkfifo fifo1：建立一個 FIFO。
  2. prog3 < fifo1 &：在背景執行 prog3，stdin 接到 fifo1。shell 要先以 O_RDONLY open fifo1，才能把它接到 prog3 的 fd 0；這時還沒有任何 process 以 O_WRONLY 打開 fifo1，所以這個 open 會 block（page-87），prog3 還沒開始跑。
  3. prog1 < infile | tee fifo1 | prog2：prog1 的輸出經過 pipe 給 tee。tee 以 O_WRONLY 打開 fifo1，上一步卡住的 open 這時就回傳，prog3 開始跑。之後 tee 每讀到一段資料，就寫一份到 stdout（經過 pipe 給 prog2），再寫一份到 fifo1（給 prog3）。

tee 只會寫「檔案」，FIFO 剛好是一種檔案，所以 tee 不用改，就能把資料送給另一個 process。這種事一般的 pipe 做不到，因為 pipe 沒有名字，tee 沒辦法用路徑打開它。

page-89～90#

FIFO 的用途二：Client-Server Communication#

One server & multiple clients：一個 server process 服務好幾個 client process，它們彼此沒有親屬關係，所以要用 FIFO。

page-89，送 request：server 建一個大家都知道路徑的 well-known FIFO（例如 /tmp/server.fifo）。每個 client 都打開它，往裡面寫 request；server 從這個 FIFO 讀 request。

  • 每個 request 要 不超過 PIPE_BUF：好幾個 client 同時寫同一個 FIFO，只有這樣才能保證每個 request 是完整的一塊，不會跟別的 client 的 request 夾在一起（page-87）。

page-90，送 reply：reply 不能也寫進 well-known FIFO，因為所有 client 都從同一個 FIFO 讀的話，不知道讀到的是不是給自己的。所以每個 client 另外建一個 client-specific FIFO，名字裡放自己的 PID（例如 /tmp/client.12345），並在 request 裡告訴 server 這個 PID。server 處理完，打開那個 client 專屬的 FIFO 寫 reply，client 從自己的 FIFO 讀。

投影片列的 Issues：

  • replies：就是上面說的，reply 要分開送，每個 client 一個 FIFO。
  • SIGPIPE：server 打開某個 client 的 FIFO、正要寫 reply 時，那個 client 結束了，它開著的讀端 fd 跟著關掉，這個 FIFO 就沒有讀者。server 再寫就收到 SIGPIPE（page-87）。server 預設會因此結束，所以 server 必須忽略或處理 SIGPIPE，一個 client 出問題才不會害整個 server 掛掉。
  • removing of all clients：client 都是以 O_WRONLY 打開 well-known FIFO，手上的 fd 指向寫端。所有 client 都關掉之後，指向寫端的 fd 全沒了，server 讀完剩下的 request，read 就回傳 0（EOF，page-87 的 closing of the last writer）。server 如果把 EOF 當成結束，就會在沒有 client 時退出；常見的處理方式是 server 自己也以 O_WRONLY 打開 well-known FIFO 一次，這樣寫端永遠不會全部關掉，server 就不會讀到 EOF，只會 block 等下一個 client。

What You Should Know（Pipe and FIFO）#

  • limitations：pipe 是 half-duplex，只能用在有共同祖先的 process 之間（page-75）；FIFO 解決了第二個限制（page-86）。
  • I/O：
    • read (EOF)：所有指向寫端的 fd 都關掉、buffer 也讀空了，read 才回傳 0（EOF），所以不用的 fd 要關（page-79）。
    • write (SIGPIPE)：指向讀端的 fd 全部關掉後還寫，寫的 process 會收到 SIGPIPE（page-79）。
    • blocking/nonblocking：pipe 空了 read 會 block、滿了 write 會 block（ch14 page-03）；FIFO 的 open 本身也會 block，O_NONBLOCK 改變這個行為（page-87）。
  • intermixing problem：多個 process 寫同一個 pipe 或 FIFO 時，超過 PIPE_BUF 的寫入可能被別人的資料插進來（page-79）。
